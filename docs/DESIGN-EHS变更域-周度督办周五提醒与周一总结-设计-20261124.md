### 1.3 隐患催办是怎么做的（本设计的参照）

- 每周三 10:00，对督办中、未关闭的隐患算「未更新进展」：进展文本超过 7 天没变，或从未填过进展且离检查日期超过 7 天。
- 一卡一隐患，私发给责任人和分管安全员。卡内有输入框，提交后回写隐患表「目前进展」。
- 发完后往当日安全速递总卡投一格简报。**0 条也投**（有无均报）。

变更这边和它的差别只有两处：范围是"全部未验收完毕的变更"，不设 7 天阈值；一人一卡，不一卡一变更（最多的安全员名下有十几项，一卡一变更会一次收到十几张卡）。

## 2. 怎么判"已验收完毕关闭"（已定稿）

### 2.1 口径

- **已验收完毕 = 这项变更名下有「已通过」的验收单。** 「变更状态」列不参与判定。
- **中止有两种，都算关闭，不督办（2026-11-24 用户定稿）：**
  1. **变更申请撤回**——申请状态=已撤回（现 119 行）。筛「已通过」时天然出局，从不进入督办范围；周五已督办的项若周末被撤回，周一复查按已关闭处理，不进三类。
  2. **申请流程结束但未发起验收、中止变更**——申请状态=已通过而「变更状态」=变更中止/中止（现 8 行，其中 1 行名下有一张已撤回的验收单，不影响判定）。中止信息只存在于「变更状态」列（验收表无此信息），是该列参与判定的唯一地方。
- 其余申请状态为已通过的审批单，全部督办。「变更状态」为空的 3 项也算未验收，卡面标「状态未填」。

### 2.2 验收单怎么对到变更

**按变更编号对，不按审批单逐行对。两条路都认：**

1. 验收单「关联审批」开头的 12 位审批编号 → 审批表里那一行 → 它的「变更申请编号」；
2. 验收单自己的「变更编号」。

编号比较前先归一化：去掉连字符和空格，统一大写。一条已通过的审批单，变更编号落在"已通过验收单指向的编号"里，就是已验收。

两条都要用的原因：验收表「关联审批」有 33 行是空的（31 行是 2025 年批量导入的旧记录，2 行是 2026 年的），「变更编号」又只有 14 行有值，单靠一条会漏。

按编号对的原因：`FX-T6-20260724` 有两行都已通过的审批单，验收单只挂在其中一行上。按编号对，两行都算已验收；逐行对会把另一行当成未验收去催。

### 2.5 排除清单（7 项待业务确认，2026-11-24 用户拍板）

§2.4 那 7 项「状态=已验收但无已通过验收单」的，**先排除在督办之外**，待业务确认后再更新状态。

- 落法：app_config 加一个排除清单 `SAFETY_EHS_CHANGE_FOLLOWUP_EXCLUDED`（逗号分隔变更编号），预置这 7 个编号；周五筛范围时剔除，周五格子里带一句「排除待确认 7 项（状态填了已验收但无已通过的验收单）」。
- 确认后的两条自然出路，都不需要改代码：
  - 确实验收过 → 在对应验收单上补挂「关联审批」或填「变更编号」→ 定稿口径自动判关闭；
  - 确实没验收 → 业务把「变更状态」改对（如待验收/实施中）→ 从排除清单移除后自动回到督办。
- 排除只影响督办范围，不影响周一总结（它们从没进过轮次，不参与分类）。

## 3. 流程

```
周五 10:00 ──► 读审批表+验收表 ──► 判定关闭、筛出未验收 ──► 按安全员聚合 ──► 落库快照 ──► 逐人私发 ──► 投安全速递格子
                                                                                                      │
周末 ◄───────────────── 安全员反馈：提交进展（回写变更表）/ 点"进展不变" ◄────────────────────────────────┘
                                                                                                      │
周一 09:00 ──► 找到上周五那一轮 ──► 重读两表比对进展 ──► 分三类 ──► 投安全速递格子
```

**周五（默认 10:00，补发窗口到 17:00）**

1. 读审批表和验收表，按 §2 判定关闭，筛出未验收的变更。
2. 按部门 → 分管安全员聚合，**同人一卡**。
3. 落库：一轮 `round`，每人一条 `dispatch`，每项一条 `item`（记下周五当时的最新进展）。
4. 逐人私发周五卡。中途失败只补发没发成功的人；服务重启不会重发。
5. 往当日安全速递总卡投一格：未验收多少项、私发了谁、明细。

**周一（默认 09:00，补发窗口到 12:00）**

1. 找 4 天内最近的一轮周五督办；找不到就跳过并告警。
2. 重读审批表和验收表，逐项看进展变了没、有没有新关闭。
3. 分三类、落库、往当日安全速递总卡投一格；投过不再投。

- **表单始终保留**，可继续补充提交；同一变更重复提交/勾选以最后一次为准；
  同一项既填文字又勾选时**文字优先**（并清除勾选标记）。
- 单项写表失败该项不记已反馈（其余项不受影响）。
- 只有收卡人本人能操作（灰度收件人非空时跳过，供验收）。
- 全部变更放在同一个正文块里，十几项也只有一个正文元素。

## 5. 周一怎么分三类

对周五督办的每一项变更判断，顺序从上到下，命中即止：

| 先判 | 条件 | 结果 |
|---|---|---|
| 1 | 周一时已关闭：验收单新通过、变更中止、审批单被撤回或删除 | 本周已关闭，不进三类 |
| 2 | 「变更最新具体进展」和周五快照不一样，**或「变更状态」变了**（如待实施→实施中） | **③ 更新** |
| 3 | 进展没变，安全员在**该项**勾选了「进展不变，无需更新」 | **② 进展不变，无需更新** |
| 4 | 以上都不是 | **① 未更新** |

- "更新"看的是表里的内容变没变，和隐患催办同一口径。卡片提交会回写表，所以在卡里提交和在表里手工改，都算更新。
- ②类的判定源是**单项勾选**（2026-11-24 改版：`items.marked_unchanged`）——安全员逐项勾，勾了哪项哪项算②，没勾的仍算①。改版前发出的旧卡若走过全局按钮（`dispatch.response_type=unchanged`），按旧口径参与：名下未提交文字的其余变更算②。
- 三类项数之和 = 周五督办项数 − 本周已关闭项数。

## 7. 数据模型（新增 3 张表，`safety` schema）

```
safety.ehs_change_followup_rounds          一轮 = 一个周五
  id · year · week_no · fired_on
  status            sending / sent / summarized
  stats             jsonb

safety.ehs_change_followup_dispatches      一行 = 一位安全员的一张卡
  id · round_id
  officer_name · officer_open_id · departments（文本，逗号分隔）
  change_count
  send_status       pending / sent / failed / no_recipient / unresolved
  message_id · sent_at · send_error
  response_type     空 / unchanged · responded_at
  category          周一判出的分类（更新 / 进展不变 / 未更新）

safety.ehs_change_followup_items           一行 = 一轮里的一项变更
  id · round_id · dispatch_id（无人可发时为空）
  record_id · change_no · title · department
  status_shown · acceptance_note · progress_friday · expected_start · approval_url · nag_weeks
  replied_progress · replied_at · replied_by
  marked_unchanged · marked_at          ← 2026-11-24 改版：单项「进展不变」勾选
  progress_monday · outcome
  唯一约束 (round_id, record_id)
```

- `status_shown` 是「变更状态」原样留存，只用于展示。`acceptance_note` 记标注原因（§2.4 的四种：验收单审批中 / 验收单已撤回 / 疑似已由兄弟变更验收单覆盖 / 未找到验收单）。
- 落库而不是放 Redis：周一要拿周五的进展做比对，要防重发，还要能事后查"哪项变更第几周还没更新"。
- "第 N 周督办" = 历史轮次里出现过同一 `record_id` 的轮数 + 1。

## 8. 任务与开关

| 任务 | 时间 | 输出 |
|---|---|---|
| EHS变更周度督办 | 每周五 10:00，补发到 17:00 | 私发周五卡 + 投当日安全速递格子 |
| EHS变更督办总结 | 每周一 09:00，补发到 12:00 | 投当日安全速递格子 |

两个任务都走既有调度框架：状态落库、失败重试、失败告警、任务运行中心留痕。时间在前端可改。

| 开关（app_config） | 默认 | 作用 |
|---|---|---|
| `SAFETY_EHS_CHANGE_FOLLOWUP_ENABLED` | **关** | 总闸 |
| `SAFETY_EHS_CHANGE_FOLLOWUP_GRAY_RECIPIENT` | 空 | 非空时所有卡只发给这个人，内容不变。**验收必用** |
| `SAFETY_EHS_CHANGE_FOLLOWUP_EXCLUDED` | 预置 §2.5 的 7 个编号 | 排除清单（逗号分隔变更编号），周五筛范围时剔除；确认后按 §2.5 的出路移除 |

总闸默认关、另设灰度收件人，是因为**本机 dev 后端连的就是真实飞书租户**。开发期间后端热重载，调度器会把当天到点未跑的任务立刻补跑。没有这两道闸，写代码的瞬间就可能给 14 位安全员真发卡。

## 9. 降级与边界

| 情况 | 行为 |
|---|---|
| 审批表读取失败 / 连接未登记 | 抛给调度器，补发窗口内重试；未登记按既有 `no_source` 哨兵如实留痕 |
| **验收表读取失败** | **本轮不发，交调度器补发窗口重试。** 不退化成看「变更状态」，否则会把已验收的当成未验收去催 |
| 安全员姓名解析不到 open_id | 这个人不发，周五格子里列入"未发送" |
| 部门没配安全员 | 不发，周五格子里列入"未发送" |
| 卡片提交时回写变更表失败 | 提示"提交失败，请稍后重试"，不记为已反馈 |
| 回调时写库失败 | 提示重试。飞书卡片回调不重试，所以写库必须幂等，可重复点 |
| 回调 3 秒超时 | 回调里只做写表和单行写库，改卡放后台任务（与隐患催办卡同一做法） |
| 周一找不到上周五那一轮 | 跳过并告警 |
| 总闸关 | 两个任务静默跳过 |

**一个已知盲区：** 一张已通过的验收单，如果「关联审批」和「变更编号」都是空的，就对不到任何变更，它对应的变更会被当成未验收督办。今天没有这样的行（33 行空关联的已通过验收单里，31 行属于 2025 年的变更，剩下 1 行通过「变更编号」能对上）。以后若出现，靠安全员反馈发现。

系统对变更表**只写「变更最新具体进展」这一列**，而且是追加，不改写已有内容。

一期不做：判已读（已明确不需要）、私发周一总结、周一之后再催、节假日顺延、前端页面。
