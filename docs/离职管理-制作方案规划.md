# 离职管理模块 · 制作方案规划

> 依据：飞书文档《员工离职管理需求说明》（提交：AI 项目办，2026-11-25，doc token `Bd0idbn9loSrqcxlcrBcHuB7nUb`）
> 范围：HR 模块内「离职管理」子域——流程闭环（申请→审批→清退会签→证明→送达签收→办结）+ 台账筛选导出增强
> 原则：复用 HR 模块既有地基（飞书审批集成、免登签字 H5、提醒框架、邮件服务、台账同步），不跨模块改动
>
> **已拍板决策（2026-11-25 与用户确认）：**
> 1. 审批载体 = **飞书审批编排**：复用公司现行两条飞书审批定义，平台自动发起 + 轮询回写 + 节点引导
> 2. 短信通道 = **暂不接，留接口**：邮件 + H5 签署链接先上线，送达通道做抽象（mail/sms 同接口），短信服务商定了后一个适配器接上
> 3. 台账权威源 = **双轨并行**：平台流程办结自动 upsert 台账记录（工号匹配）；飞书「离职人员管理表」每日同步保留兜底（覆盖存量与线下办理），cert_sign_* 字段同步不触碰（employee_sync 已保证）
> 4. 离岗体检 = **平台登记管理**：重点岗位标记 + 体检完成登记作为流程前置门禁，未登记不允许发起审批

## 一、需求要点还原

### 1. 流程节点（需求「流程节点」9 步）

| # | 节点 | 关键规则 |
|---|---|---|
| 1 | 发起离职申请 | 试用期员工提前 3 天、转正员工提前 1 个月；按职级选流程（一般员工~M4 一套、M5+ 总监级另一套）；涉及职业健康体检的岗位须**先完成离岗体检** |
| 2 | 离职审批 | 所在部门负责人审批，**办结后方可**进入清退交接 |
| 3 | 发起清退交接 | 离职审批办结后，于**离职日前 2 天**发起 |
| 4 | 部门审批与转办 | 部门负责人审批后转办交接人与部门办事员，确认交接事项 |
| 5 | 多部门会签 | 行政后勤部（宿舍钥匙/物品/餐卡/车辆通行证等）、财务部（电脑/借款/U 盘等）、人力资源部（工号牌/社保医保/培训费等） |
| 6 | 开具解除劳动关系证明 | 会签完成后回 HR 核对开具；姓名/身份证号/入职日期/部门岗位/离职日期/离职原因从档案带出；两种模板：纸质两联版（含签收栏，当面签收）+ 电子单张版（链接线上签收） |
| 7 | 员工签字确认 | 电子版在签字确认区**手写签名**提交，签名图像随档案留存；纸质版当面签字，签收时间与方式留存 |
| 8 | 证明送达与短信通知 | 证明发员工邮箱 + 短信附签署链接（**飞书账号已注销，短信是主要送达通道**）；发送时间/号码/送达结果留存 |
| 9 | 办结收尾 | 签字确认后账号注销；用工状态更新为离职；证件档案转历史保留；台账同步更新 |

### 2. 离职人员台账（单独成册）

- 人员信息：姓名、身份证号、部门、岗位、入职日期
- 离职信息：离职日期、离职原因、用工类型、是否递交离职申请
- 证明信息：证明链接、证明附件、审批状态、HR 负责人
- 清退与结算：四部门各项清退进度与扣补金额（行政后勤/财务/人力资源/工作部门）
- 流程信息：申请编号、发起人与发起部门、发起时间、审批节点、当前处理人、完成时间

### 3. 筛选与导出（平台基本要求）

1. 可筛条件：性别、学历、部门、岗位、离职原因、用工类型、离职日期区间、审批状态、是否已开具证明、是否已领取
2. 条件任意组合、可单独使用
3. 导出 Excel，**导出字段可勾选**，不必整表带出
4. 常用条件**保存为固定视图**，一键调用
5. **导出行为留痕**：操作人、时间、筛选条件、导出条数

### 4. 现状痛点（需求「现状说明」）

- 节点先后关系靠员工自行把握，缺系统提示
- 证明发邮箱/短信靠人工，未与开具联动
- 办结后状态与台账更新部分需 HR 手动
- 台账分开存放、手工筛选另存导出

| 离职联动存量 | Employee.status=离职、departure_date/reason 字段；`_sync_roster_status` 花名册移除 | 办结联动复用其口径 |

### 缺口（本方案要新建）

1. **流程主干不存在**：无离职办结单模型与状态机，两条飞书审批与平台零联动
2. **清退会签无模型**：四部门清退清单 + 进度 + 扣补金额完全无表
3. **送达无自动链路**：证明开具后邮件需手动逐条发；无短信通道、无送达留痕
4. **签字无 API/页面**：cert_sign_* 字段空挂，无免登 H5、无手写签名
5. **办结联动不完整**：证件转历史保留、台账自动 upsert 无联动
6. **台账筛选导出弱**：仅部门/离职类型/关键词 3 条件、固定 16 列、无视图、无导出留痕

## 三、总体设计

### 3.1 数据模型（hr schema，全部软删除、沿用 BaseModel）

**`OffboardingCase` 离职办结单（hr.offboarding_cases）** —— 流程主干，一次离职一行：

| 分组 | 字段 |
|---|---|
| 关联 | employee_id（FK hr.employees）、departure_record_id（FK，台账行，发起时 upsert 建立）、case_no（申请编号，唯一，规则 `LB-20261125-XXXX`） |
| 状态 | status：`draft / approving / clearing / cert_issuing / delivering / signed / closed / canceled` |
| 员工快照 | name、employee_number、department、position、rank（办结后档案会变，列表展示用快照） |
| 离职信息 | offboarding_date（离职日期）、offboarding_type（辞职/辞退/合同到期/退休/其他）、reason、employee_category（用工类型）、application_submitted（是否递交离职申请） |
| 审批编排 | approval_track（staff/director，按 rank 路由）、resignation_instance_code + resignation_status + resignation_finished_at、clearance_instance_code + clearance_status + clearance_finished_at |
| 离岗体检 | health_check_required（重点岗位标记）、health_check_done、health_check_date、health_check_file_id（报告附件走 file_storage） |
| 证明 | cert_template（electronic/paper 两联）、cert_issued_at、cert_issued_by |
| 送达 | mail_sent_at、mail_status、sms_phone、sms_status（sms 通道预留字段）、delivery_channel（mail/sms/paper） |
| 纸质签收 | paper_signed_at、paper_signed_by（当面签收登记；电子签收走 DepartureRecord.cert_sign_*） |
| 办结 | account_deactivated（账号注销 HR 确认勾选）、closed_at、closed_by |

> 签字字段**不重复建**：沿用 `DepartureRecord.cert_sign_*`（已建好），Case 经 departure_record_id 关联读写。

**`OffboardingClearanceItem` 清退交接项（hr.offboarding_clearance_items）**：

- case_id、category（`admin`行政后勤 / `finance`财务 / `hr`人力资源 / `work`工作部门）
- item_name（宿舍钥匙、饭卡余额、电脑、工号牌、社保公积金、业务往来……）
- status（待确认/已确认/有扣补）、confirmed_by_open_id、confirmed_at
- deduction_amount（扣款）、supplement_amount（补发）、remark
- source（`feishu_form` 实例回读 / `manual` 平台登记 / `card` 卡片确认）

**`DepartureSavedView` 台账保存视图（hr.departure_saved_views）**：owner_user_id、name、filters JSON、columns JSON、is_default。

**`HrExportLog` 导出留痕（hr.export_logs，通用设计）**：module（`departure` 起步）、operator_user_id、filters JSON、columns JSON、row_count、created_at——其他台账后续可复用。

**`DepartureRecord` 加 1 列**：cert_issued_at（证明开具时间，P1 迁移一并加；「是否已开证明」筛选用；「是否已领取」= cert_sign_status=signed 或 paper_signed 登记）。

### 3.2 离职办结状态机

```
draft ──发起离职审批(飞书 create_instance，体检门禁校验)──▶ approving
approving ──轮询 APPROVED──▶ clearing            （离职审批办结，自动推进）
approving ──REJECTED/CANCELED──▶ canceled        （可复制重开）
clearing ──轮询 APPROVED / 会签回读完成──▶ cert_issuing （清退会签办结）
cert_issuing ──HR 核对生成证明(自动发邮件)──▶ delivering
delivering ──H5 手写签名 / 纸质签收登记──▶ signed
signed ──账号注销勾选 + 办结确认──▶ closed        （触发办结联动）
```

门禁：`health_check_required=True` 且未登记完成 → 不允许从 draft 发起审批（后端校验 + 前端禁用）。

### 3.3 审批编排（照 renewal_approval 模式整套照搬）

- **配置**（SystemSetting KV，`hr_offboarding.*`）：四个审批定义编码——`resignation_approval_code_staff`（一般员工~M4）、`resignation_approval_code_director`（M5+）、`clearance_approval_code_staff`、`clearance_approval_code_director`；路由按 Employee.rank 前缀判定，配置缺失自动降级**站内登记**（HR 在办理 Drawer 手动标记「审批已完成」，流程不堵死，同 renewal 降级思路）
- **发起**：case 推进时按 WIDGET_SPECS 控件名约定（姓名/工号/部门/岗位/离职日期/离职类型/离职原因/备注）自动填充 create_instance，uuid 幂等防重复发起（recovery mark 前缀 `ob:`）
- **回写**：每日定时任务扫 status∈(approving, clearing) 且有 instance_code 的 case → get_instance → APPROVED 推进下一阶段 / REJECTED→canceled / CANCELED→清实例回 draft
- **节点引导（解决痛点①）**：每阶段推进时飞书卡片通知 HR 责任人（「离职审批已办结，清退交接已自动发起」「会签已完成，请核对开具证明」），节点先后由系统编排，不再靠员工把握

### 3.4 清退会签（实例回读 + 平台清退单兜底）

- 清退交接实例办结后，从 get_instance 的 form 按控件名约定回读各部门清退明细 → 写入 ClearanceItem（source=feishu_form）；回读失败/字段缺失不堵流程，HR 在办理 Drawer 手工登记补录（source=manual）
- 扣补金额、各事项进度在平台清退单维护，台账「清退与结算」视图从 ClearanceItem 聚合

### 3.5 证明开具

- cert_issuing 阶段 HR 核对页：档案带出姓名/身份证号/入职日期/部门岗位/离职日期/离职原因（照现有 preview-certificate 的兜底逻辑），选择模板（电子单张/纸质两联）
- 电子版：现有 generator 版式保持一致；**纸质两联版**：generator 加签收栏版式的第二模板函数
- 核对确认 → 生成 PDF 存档（file_storage）→ DepartureRecord.cert_issued_at 回写 → 自动发邮件（PDF 附件 + 签署链接）→ delivering

### 3.6 送达与签字 H5

- **送达抽象**（offboarding/delivery.py）：`DeliveryChannel.send(...)` 统一接口，MailChannel（现有 send_email）+ SmsChannel（占位实现：配置缺失时抛「短信通道未配置」，状态记 pending，不阻塞主流程）；每次发送写 delivery 留痕（时间/通道/号码/结果）
- **签字 H5**：`frontend/src/app/api/departure-cert-sign/page.tsx`（静态段 + `?token=`，免登，照 contract-sign 模式）+ **手写签名 canvas 组件**（自研轻量画板，约百行，不引新依赖：pointer 事件采样 → 笔画平滑 → 导出 PNG base64）；后端公开路由挂全局 api_router（照 labor_contract sign_router 模式）：
  - `GET /departure-cert-sign/{token}`：证明预览信息（含 HTML 版式）
  - `POST /departure-cert-sign/{token}/confirm`：提交签名图 → cert_sign_status=signed、cert_signed_at、cert_sign_image、token 清空作废（一次性）→ Case→signed → 飞书通知 HR「员工已签字确认」
  - 确认成功页提供 PDF 下载（证明文件）
- **纸质两联版**：HR 在 Drawer 登记「已当面签收」（时间/签收人）→ 同样回写 cert_sign_status=signed（image 空）→ signed

### 3.7 办结联动（closed 触发，单一 service 函数收口）

1. Employee：status=离职、departure_date、departure_reason
2. 证件档案：EmployeeCertificate 当前版本转历史保留（对齐 employee_certificate_service 版本模型，实施时确认具体降级字段口径）
3. 花名册：TrainingRosterProfile 移除（复用 `_sync_roster_status` 口径）
4. 台账：DepartureRecord upsert 补全（offboarding_date/type/reason/cert_sign_*，employee_number 匹配、name+id_card 兜底）
5. 账号注销：account_deactivated 勾选登记（平台侧不自动操作飞书账号）
6. 全程写 case 时间线（各阶段 finished_at 即审计）

### 3.8 台账增强（P2）

- **筛选**：list_records/export 参数扩展 gender、education、employee_category（用工类型）、offboarding_date_from/to、approval_status（case 状态 join）、cert_issued（是否已开证明）、cert_signed（是否已领取）+ 现有 department/offboarding_type/keyword
- **导出**：新增 POST 导出（body：filters + columns[]），字段注册表 EXPORT_COLUMNS（key/label/取值函数，身份证脱敏规则保留）；GET 旧端点保留兼容
- **保存视图**：DepartureSavedView CRUD（个人维度），前端筛选栏「存为视图/我的视图」切换器
- **导出留痕**：每次导出写 HrExportLog；台账页加「导出记录」查看入口（操作人/时间/条件/条数）

### 3.9 节点提醒（P3，挂提醒框架）

- `offboarding_lead`：每日扫描档案已定离职日（departure_date 有值）但无进行中 case 的员工 → 按「试用期提前 3 天/转正提前 1 个月」规则临近违规前提醒 HR 与部门负责人
- `offboarding_clearance_due`：case 在 approving/clearing 且距离职日 ≤2 天未办结 → 催办提醒
- 发起时校验：draft→approving 提交时校验提前天数规则，不满足给出警告（可强制继续，不硬卡——业务上存在协商离职）

## 八、风险与注意事项

- **alembic heads**：开工先 `alembic heads` 检查，必要时 merge（PR #63 刚做过一次）

### 9.2 实施中对方案的调整

1. **清退会签被退回不取消整单**：§3.2 / §3.3 写的 REJECTED→canceled 只适用于「离职审批」。清退会签被退回时离职审批早已通过，改为清实例、留在 `clearing`，由 HR 处理后站内登记办结。
2. **离职审批在飞书被撤销**：按 §3.3 清实例回 `draft` 可重新发起（未采用 §3.2 的 canceled）。
3. **办结联动由四项增为五项**：增加「入职台账 `is_employed=否`」，与旧「新建离职」口径一致（否则各列表过滤不一致）。
4. **进入清退阶段自动落默认清单**：按需求列明的事项落 11 项（行政后勤 4 / 财务 3 / 人力资源 3 / 工作部门 1），HR 逐项确认；飞书回读的明细按部门替换默认行。
5. **清退表单回读的控件约定**（待人事建定义时遵循）：每部门一个多行文本控件「行政后勤清退事项 / 财务清退事项 / 人力资源清退事项 / 工作部门清退事项」，一行一条 `事项名称｜状态｜扣款｜补发｜备注`；可选数字控件「<部门>扣款金额 / 补发金额」。
6. **取消办理时撤下平台建的台账行**（无 `feishu_record_id` 的行），避免在职员工挂在离职台账里；已被飞书同步认领的行不动。
7. **签字链接一次性**：员工签字后 token 即作废，所以签字成功页的「下载证明」改为用确认接口随响应带回的 PDF，不再依赖 token。
8. **纸质两联版不签发线上签署链接**，只走当面签收登记。
9. **台账 upsert 分两种口径**：建单 / 编辑 / 开证只补空字段（飞书同步来的行以源表为准）；办结时才回写覆盖。
10. **模型补两列**（在同一迁移内）：`OffboardingCase.initiator_name`（发起人快照）、`cert_issued_by`（开具人）。
11. **台账列表按权限脱敏**：新查询接口对身份证等敏感字段按 `hr:profile:sensitive` 脱敏，与详情接口一致；签名图 base64 不进列表。
12. **未配置审批定义不算失败**：按设计内的降级路径发「阶段推进」通知，只有「配置了但发起失败」才通知 HR。

### 9.3 环境事实与待办

- **飞书原生审批本地无法实测**：本地飞书应用未开通审批定义权限（`approval:approval:readonly` / `approval:approval` / `approval:definition`），拉取审批定义直接报 `99991672 Access denied`。该路径目前只有单元测试（mock）覆盖；上线前需在飞书后台给应用开通权限，并在系统配置 →「离职管理」填写 4 个定义编码。
- **「离职原因」筛选项几乎为空**：本地 196 条台账里 `offboarding_reason` 列只有 1 条有值，真实的原因大多记在「离职类型」列（个人原因 / 部门劝退 / 调合成公司…）。这是飞书源表的数据状况，不是代码问题；是否要规范源表由人事决定。
- **学历列混有错位数据**：源表部分行的学历是日期（如 `1983/09/18`），筛选下拉已自动剔除。
- **M5+ 判定**仍按职级前缀（默认 `M5,M6,M7,M8`，可在系统配置修改），待人事确认。
- **短信**仍为适配点占位，服务商确定后实现 `delivery._send_via_provider`。
