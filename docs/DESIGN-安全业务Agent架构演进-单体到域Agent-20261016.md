# DESIGN-安全业务Agent架构演进-单体到域Agent-20261016

> 定位：与《DESIGN-安全业务Agent优化-减法优先-20261016》配对。前者回答"怎么把单体做瘦"（工程层减法），本文回答"拓扑与基础设施怎么演进"（架构层）。
> 核心判断：仓储 agent 又快又准的架构本质是**窄域单 agent**（N=1 特例）；安全 agent 的结构性问题是**一个单体服务 20 个业务域**。工具减法治标，拓扑演进治本，但每一步都要先过"减法能不能解决"这道闸。

## 一、架构诊断：五个结构性问题

### 1. 拓扑错位（根问题）
一个 Agent 实例 × 20 业务域 × 76 工具 × 27KB 全能 prompt。任何一次模型调用都要面对全部工具面和全部规则，无论用户问的是什么域。域与域之间还互相拖累：URS 的 9 个工具 schema 摊薄了隐患查询的选择准确率。

### 2. 配置绑定静态化
`agent.py` 的 `_PROVIDER/_MODEL` 是模块级单例，换模型/换绑定要重启进程——executor 注释自己承认这是"一期决策"的债。仓储的 runtime 参数（max_turns/session_rounds 等）每轮从 runtime_store 动态读，改值即时生效。

### 3. 业务知识全部内联且不可运营
27KB agent.md 把人设、20 个域的操作指引、输出格式规则全部写死在一个文件里：改一条日报输出规则要动代码仓库文件；域专家（安全工程师）无法自己维护 SOP；每轮全量注入不管相关与否。

### 4. 调度双轨
safety 自研 1296 行 30s tick 循环（scheduler.py）与平台 SchedulerEngine 并存。两套留痕/重试/告警语义各自维护，平台引擎的统一能力（warehouse 6 个任务在用）safety 享受不到。

### 5. 模块孤岛
与仓储 AI 基建平行复制（两套 ai_audit/ai_config/bitable_config/飞书 WS 长连接），且无 MCP 互操作——安全 agent 查不了仓储库存（化学品域天然相邻），反之亦然。平台已有 4 个模块 MCP 挂载先例，safety 不在其列。

## 二、目标架构与演进路径（A1-A6）

### A1 域 Agent 拓扑（核心，分阶段）

**目标态**：Orchestrator（意图分发 + 会话/确认门/权限，自身无业务工具）+ ~12 个域 Agent（每个 5-15 工具 + 域专属精简 prompt + 域专属参数）。

**现有资产即雏形**：`get_agent_for_tools`（agent.py:78）按工具名组合缓存子集 Agent——每个意图组已经有独立 Agent 实例，**缺的只是域身份（专属 instructions/model_settings）**。演进是"给子集赋予域人格"，不是从零搭建。

**委派机制**：pydantic-ai 2.8 无内建 delegation（已验证）。实现取仓储 Runner 同款模式：orchestrator 注册一个 `delegate(domain, query)` 元工具，内部程序化运行域 Agent 并回传结果。零新框架、零新依赖。

**分阶段**：
1. 前奏 = 减法文档的 P2 两段式路由（子集挂载本质上是域 Agent 去掉身份）
2. 试点：先拆 URS（9 工具重工作流）+ 办公写（低频独立）两域，验证延迟/准确率收益
3. 逐域迁移，隐患+知识核心域最后拆或不拆
4. **收手判据**（防为拆而拆）：只有当域满足"有独立多步工作流"或"有独立输出规范/人设"之一才值得独立域 Agent。若 S0+S1 减法+路由后体感已达标，A1 可以停在试点。

**orchestrator 恒定持有**：会话管理、PendingAction 确认门、ROLE_TOOL_POLICY 权限、审计 scope、记忆注入——这些是跨域能力，不随域拆分而复制。

### A2 模型/配置运行时化
- 消灭"重启生效"：模型实例按 ai_config profile 配置哈希缓存、per-turn resolve（配置变了换新实例，没变用缓存）
- temperature/max_tokens 从 agent.py 硬编码收进 ai_config 可调项（配合减法文档 P3），参数调整从"发版"变"后台改配置"
- 参照 warehouse runtime_store 模式（60s TTL + 回退链）

### A3 业务 SOP 技能化
引入仓储 skills registry 模式（三段式 markdown：frontmatter 元数据 + 步骤 + 输出格式，mtime 缓存热更新，`load_skill` 工具按需注入全文）。

**迁移对象**（从 agent.md 与 prompts 里抽出）：
- 日报/督办通报的输出格式规则（现 agent.md 中两大段"必须原样输出"硬规则）
- 监护补贴计算与确认话术 SOP
- 演练方案生成 SOP（8 节格式脚本）
- 隐患分类审核要点

**收益**：agent.md 从"全能说明书"瘦成"角色+纪律+路由说明"（目标 <8KB）；域专家可直接维护 SOP 文件零重启；触发哪个技能才注入哪个，常驻 prompt 进一步变小。

### A4 调度归一
- scheduler.py 1296 行自研循环 → 平台 SchedulerEngine 注册（接口已就绪：`app/platform/scheduler/engine.py`，warehouse 6 任务验证过）
- 迁移清单：约 15 个定时任务 + hazard_direct 的 4 个轮询协程（转为 interval 任务）
- **风险与对策**：自研循环的"时间窗 >= 触发、重启不漏发"语义需在 engine 侧确认等价（迁移前写对照测试）；分两步走——新任务直接注册 engine，存量任务按批次迁移
- 收益：净删 ~1300 行自研调度、两套留痕语义归一、告警/重试策略统一维护

### A5 MCP 互操作（跨模块能力层）
- safety 只读查询工具经 `get_module_mcp("safety")` 暴露（挂 `/mcp/safety`），完全对齐 warehouse 先例：**只读暴露、写操作绝不注册**（HITL 确认门不可绕过）
- 反向收益：安全 agent 挂载 warehouse 的 4 个 MCP 查询工具，"问安全 agent 仓库某化学品库存"成为可能（危化品安全与仓储库存天然相邻）
- 时机：A1 试点稳定之后，且先做暴露侧（被动）再做消费侧（主动）

### A6 事件与响应链路
- 事件双写异步化：append_event 改事务尾部一次提交（或后台队列），每轮 4-6 次 flush → 1 次
- Web 端 SSE + run_stream 流式（对齐仓储 accepted→stage→message→finished）
- 可选远期：regulation.updated 事件信封先例（commit d2f54a64）推广为模块内轻量事件总线，域间解耦

## 三、跨模块基建收敛（方向性拍板议题，默认不动）

两套 ai_audit/ai_config/feishu WS 的三条路：
| 选项 | 说明 | 适用条件 |
|---|---|---|
| a) 抽平台共享内核 | 审计/熔断/防注入/回退链上收平台层 | 第三模块（生产/设备）要上 agent 时 |
| b) 保持复制 + 同步约定 | 建立改一边必须同步另一边的 checklist | 现状延续，成本最低纪律最弱 |
| c) 只共享规范文档 | 把语义写成跨模块规范，实现各归各 | 中间态 |

warehouse 独立实现是既定拍板（模块自治），收敛是方向性决策不随本方案自动执行。**判断框架：等第三个模块上 agent 时，收敛收益才明确大于自治收益**，届时再立项。

## 四、演进纪律（防止架构演进变成加法）

1. 每项演进先过减法闸：A1 之前必须先做完工具减法+路由（S0/S1），实测不够再拆
2. 每步绑定度量：落地后从 ai_call_audits 取 prompt_tokens/latency P50/P95 对比，无收益即回滚
3. 零新框架：不上 LangGraph/AutoGen、不自研 orchestrator 平台——委派就是"元工具内部跑子 agent"
4. 拆出去的域复用 orchestrator 的确认门/权限/审计，不复制基础设施
