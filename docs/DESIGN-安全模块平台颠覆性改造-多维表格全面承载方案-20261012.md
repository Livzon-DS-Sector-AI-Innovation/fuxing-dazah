## 0. 一句话定位

**上一版方案回答了"平台新建什么"（监控编排核心）；本方案回答"平台拆除什么"（Web 业务面与平台自建业务流全部退役）。**

终态三句话：

1. **多维表格 = 业务系统**：录入、台账、状态流转、审批、查询、统计全在表格与表格仪表盘完成；
2. **机器人 = 唯一交互界面**：通知、催办、确认、审批、问答全部在飞书卡片与对话内闭环；
3. **平台 = 隐形后台**：只剩事件监听、判定、联动编排、督办、AI 审查、日报、Agent 问答这七个"履职动作"的执行引擎，外加一个极简监控台（驾驶舱+配置+审计）。

**这个方向不是空想——生产数据已经在投票**：
- EHS 变更平台状态机（create→commission 全套 API）**生产从未启用**，100% 业务走 Bitable（commit bce0467f 探针坐实）；
- cert 换证 renew 在直读模式下已拍板禁用（Q6=A，"改在飞书表格更新"）；
- 演练采集表→主表归集、危化品 Excel→Bitable 日更、特殊作业报备，业务执行本来就长在表格侧；
- 直读改造已把 14 域读路径切到 Bitable 单源——Web 页只是"查询转述层"，退役不影响数据链路。

## 1. 终态架构

```
┌──────────────────────────────────────────────────────────────┐
│  飞书（业务系统）                                             │
│  多维表格：录入/台账/状态列/仪表盘     机器人：通知卡/催办卡/    │
│  审批流：重审批（红线动作）            确认卡/问答/命令          │
├──────────────────────────────────────────────────────────────┤
│  平台（隐形后台，无业务界面）                                   │
│  事件总线 → 联动规则引擎 → 督办状态机 → 日报/报告生成            │
│  AI 审查插件 · vision · 知识 RAG · 法规爬虫 · 业务 Agent        │
│  留痕：ai_call_audits / linkage_rule_runs / scheduler_job_runs │
├──────────────────────────────────────────────────────────────┤
│  极简监控台（Web，~5 页）                                      │
│  驾驶舱（联动运行流/督办大盘/链路时间线）· 配置台 · AI 审计      │
└──────────────────────────────────────────────────────────────┘
```

**量化终态**：前端 41 个业务页 → **保留约 5 页**（驾驶舱 + 4 配置/审计页，agent-chat 可选）；API 45 个路由组 → **保留约 10 组**（监控/配置/审计/Agent/文件）；平台 DB 业务表 → **冻结归档不删除**（审计可回溯），活表只剩配置、留痕、派生三类。

## 3. 业务交互的 Bitable 承载设计

### 3.1 四类交互的新家

| 原平台交互 | Bitable 化承载 |
|---|---|
| 表单录入（登记/报备） | 表格直填（桌面）、多维表格**表单视图**（手机/现场）、机器人引导卡（URS/MSDS 采集模式已有先例） |
| 状态流转（提交/审批/驳回） | **状态单选列**为唯一事实：人改列、或确认卡一键回写；联动规则监听列变更推进下游 |
| 审批（部门内确认，轻） | 机器人**确认卡**（card.action 通过/驳回 → 平台回写状态列，防回环标记） |
| 审批（跨级/红线，重） | **飞书审批流**：联动规则创建审批实例 → 通过后回调回写状态列（联动方案二期接入） |
| 查询/统计 | 表格视图（筛选/分组/看板）、**表格仪表盘**（官方图表能力）、bot 问答（Agent query 工具直读） |
| 台账导出 | 表格自带导出；复杂报表=平台生成 Excel 发飞书（监护补贴同款） |

### 3.2 状态列设计规约（B 类域通用）

每域状态列枚举与原状态机对齐（如 B2 安全检查：待审核/已确认/已退回），并遵守：

1. 状态列只允许「人手改」或「平台带防回环标记回写」，两条路径互不打架（sync_ignore 既有手法）；
2. 联动规则以状态列变更为触发器（字段级过滤），驱动下一环节通知/督办——**平台状态机代码退役，规则引擎接管编排**；
3. 逾期逻辑不在表格算：督办状态机按截止列扫描，逾期催办卡直达责任人（"没有任何一张单据不了了之"）；
4. 每域保留「数据来源/更新时间/操作人」系统列，审计回溯用。

### 3.3 权限模型迁移

- 原 platform 账号权限（permissions.py 的模块级权限）→ **飞书表权限**（谁可见/可编辑哪张表）+ **Agent 用户角色**（agent_user_roles 保留，写操作确认门继续生效）；
- 平台侧不再有业务操作入口，权限面大幅收缩；监控台/配置台保留平台账号权限。

## 4. 与联动编排方案的关系（新建 + 拆除 = 完整颠覆性改造）

| 联动编排方案（新建核心） | 本方案（拆除迁移） |
|---|---|
| 事件总线：Bitable drive 事件 + 平台域事件 | B 类域 Bitable 化后，其状态变更天然走 Bitable 事件（平台域事件源减少） |
| 联动规则引擎（R1 报警→隐患等 12 条） | B2 检查问题→隐患、B9 事故→CAPA 督办 等新规则随迁移新增 |
| 督办状态机 | **承接 B 类域退役的审批/闭环职责**（B9 CAPA、B5 verify、B2 confirm） |
| 监控驾驶舱 | Web 终态唯一业务保留面（D 类） |
| 机器人卡片工作台 | A/B 类页面的交互承接面（确认卡/验收卡/催办卡） |

实施顺序上：**联动方案一期（事件总线+引擎+督办+R1）先行**——它是 B 类域退役的前提（状态机退役后靠它编排）；B 类域逐域迁移时直接用"表格+规则+督办"三件套承接。

## 6. 迁移五步法（B 类每域标准流程）

| 步 | 内容 | 验收 |
|---|---|---|
| 1 建表契约 | contract.py 幂等建列（dry-run→人工确认→apply），状态列枚举与原状态机对齐 | 重复执行跳过；字段与 §3.2 规约一致 |
| 2 存量迁移 | 平台 DB 导出→Excel→Bitable（复用危化品 Excel 写入通道），串行+间隔 | 行数一致、抽样 20 行逐字段一致 |
| 3 双跑核对 | 新写入同时落两边（或切换期只写表格、平台侧只读核对）；直读 vs 平台 DB 全量比对脚本 | record 集合一致、逐字段差异 0 |
| 4 消费方切换 | 日报/规则/Agent 工具/预警引擎改读直读（bitable_direct 底座）；交互切确认卡/验收卡 | 双路径输出逐字相同 ≥3 天 |
| 5 退役归档 | Web 页+路由删除；平台表停止写入、打归档标记（不删数据）；菜单清理 | 回归全绿；归档说明落档 |

**开关与回滚**：每域 `SAFETY_<DOMAIN>_BIZ_MIGRATED` 开关；切换后发现问题的回滚=开关回退+表格停写指引（数据双跑期内两边都在，回滚不丢数据）；退役 git revert 可单独回滚页面。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 现场习惯迁移（一线从 Web 改用表格/卡片） | 每域退役前发操作指引卡（bot）；A 类先退无状态页降风险；关键角色（安管/班组长）逐人过一遍 |
| 表格视图统计能力不及原页面 | 高频统计用表格仪表盘配置；复杂统计由平台日报/速递卡/Excel 承载（本就更强） |
| 并发写/限流（状态列回写+联动生成叠加） | 串行+0.5s 既有铁律；B 类域写入频率低（检查/培训/事故均为日级十行内），量级安全 |
| 状态列被人误改 | 状态列变更走联动规则校验（非法跳转告警）；操作人系统列留痕；关键状态（事故关闭）挂审批门 |
| 平台表冻结后历史查询 | 表不删只冻结；驾驶舱时间线可回放；如需长期查询可导出归档 Excel 到云文档 |
| 双飞书依赖（业务=表格，交互=机器人） | 同一飞书生态，本就同源；保留 bot 降级话术与失败告警（failure_notifier 模式） |
| 与联动方案开发的并行冲突 | 联动一期先行；B 类迁移按域开票互不重叠；B8 冻结域零开发 |
