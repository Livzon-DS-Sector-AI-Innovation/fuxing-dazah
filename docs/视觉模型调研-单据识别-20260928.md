# 视觉模型能力调研——单据识别场景（2026-09-28）

> 目的：为仓储拍照识别入库的「C 项（评测换模型）」提供选型依据。现用视觉模型
> `deepseek-flash`（网关内名）识别中文单据（印刷表格为主、夹杂手写）成功率低，
> 本文档梳理候选模型的能力证据、成本与接入约束，并给出评测方案与推荐短名单。
> 价格与榜单分数为检索时的公开口径，**用前以官方定价页/实测为准**。

---

## 一、结论速览（TL;DR）

1. **通用 VLM 做 OCR 有天花板**：OCRBench v2 上最强的模型完成率也只有 ~66-67%，
   没有模型过 70%——靠换通用视觉大模型不能指望"接近全对"，但从中下游
   （deepseek-flash 一档）换到第一梯队（GLM-4.6V / Qwen3-VL 一档）仍有明显提升空间。
2. **印刷文档/表格的专用解析模型是另一个世界**：OmniDocBench v1.6 上
   PaddleOCR-VL-1.6（96.33）、MinerU2.5-Pro（95.69）、GLM-OCR（95.22）等
   0.9B 级专用模型做到 95%+，远超通用 VLM——**印刷体表格单据的终极答案是
   专用解析模型或云表格 OCR**，不是更大的通用 VLM。
3. **手写单据没有可信基准**：手写中文识别没有饱和的公开基准，任何"98% 准确率"
   的宣传数字都不能直接采信，**必须用自己的真值集实测**。
4. **推荐路径**：先在网关可用模型里实测 **GLM-4.6V（首选）与 Qwen3-VL（对照）**
   的字段命中率（复用 eval_recognition.py 口径），再用 **GLM-OCR / PaddleOCR-VL**
   （本地 GPU 允许时）或云表格 OCR 兜底印刷表格场景。

---

## 二、现状与问题

现用模型与链路（warehouse 模块）：

- 视觉识别走 OpenAI 兼容网关，场景位 `receipt_recognition` / 
  `finished_receipt_recognition` **可按场景独立换模型 + 备用通道**（ai_config 
  scenario 级配置，改配置即生效，不用改代码）；
- 现模型 `deepseek-flash` 为 reasoning 型 vision 模型（temperature 0.1，
  max_tokens 16384，reasoning tokens 实测 3k-8k+）；
- 实测缺陷（代码注释与验收记录）：旋转单据大量幻觉（已加方向预判矫正）、
  小数点误读（1.10 → 1110）、必提字段偶发整批置空、多行明细漏行/合并。
- 单张识别成本敏感度低（仓库单据量级每天几十张），**瓶颈是准确率不是钱**。

## 三、三条技术路线

### 路线一：换更强的通用视觉大模型（API 接入，改动最小）

| 模型 | 能力证据 | 接入/价格 | 备注 |
|---|---|---|---|
| **GLM-4.6V**（智谱，2025-12 开源） | OCRBench 等 30+ 基准较 4.5V 显著提升；图文混排中文字/表格/图形识别强；128K 上下文 | bigmodel 平台 OpenAI 兼容 API；约 1 元/百万输入 token、3 元/百万输出（较 4.5V 降 50%）；**GLM-4.6V-Flash（9B）免费** | 与现网关同生态可能性大；Flash 免费版可先当零成本试金石，也可用来替换分类/旋转预判这类轻调用省钱 |
| **Qwen3-VL**（阿里，plus/max + 开源 8B/235B） | 32 种语言混合识别强；OCRBench v2 中文子集开源系领先（Qwen2.5-VL-72B 63.7）；图文推理强 | 阿里云百炼 token 计费（VL 档位与 plus 接近，需开通）；开源版可私有化 | 中文 OCR 榜单最强的开源系；手写先验口碑较好（无权威中文手写单据基准佐证） |
| 豆包 vision（火山方舟） | 256K 上下文；单据 OCR 公开案例少 | 火山方舟 API | 业界常见组合是"豆包做理解 + 专业 OCR 做识别"，说明其 OCR 非卖点 |
| Gemini 3 Pro / GPT / Claude | OCRBench v2 榜首（Gemini 3 Pro ~63.4） | 需境外 API | **制药厂数据合规基本排除**，仅作榜单参照 |

### 路线二：文档专用解析模型（印刷表格最强，需本地 GPU 或确认 API 可用）

2026-09 开源第一梯队（OmniDocBench v1.6 口径）：

| 模型 | 分数 | 规格/部署 | 对本场景的意义 |
|---|---|---|---|
| **PaddleOCR-VL-1.6**（百度） | 96.33 | **0.9B**，GPU 显存 ≥8GB（推荐 4090D 级）；Apache 生态、工业级管线 | 印刷表格+版面的专用答案；支持倾斜/弯折/屏摄异形框 |
| **MinerU2.5-Pro**（上海AI Lab） | 95.69 | 1.2B 级 | 文本识别与通用 VLM 相当、**表格/公式更强** |
| **GLM-OCR**（智谱，2026-02 开源） | 95.22 | **0.9B**，低资源部署灵活 | 与 GLM 生态同源，若网关/私有化路径顺可持续跟踪 |
| DeepSeek-OCR | 官方称 ~97%（含压缩） | 3B 级 MoE，本地部署 | "光学压缩"路线，印刷文档强，社区支持为主 |
| HunyuanOCR（腾讯） | — | 1B 级轻量 | 轻量专用 OCR 备选 |

**约束**：本地部署需要 GPU（≥8GB 显存）——**现服务器若无 GPU 则此路线走不通**，
只能等云上 GPU 或确认网关是否已路由这些模型；专用模型**不做字段语义归一**
（输出是全文/结构化 markdown），接进来仍需 LLM 做字段映射，管线要加一跳。

### 路线三：云 OCR 表格识别服务（结构化稳、按量计费、纯识别）

| 服务 | 价格口径（检索口径，以官网为准） | 特点 |
|---|---|---|
| 腾讯云智能结构化 | 约 0.4 元/次（400 元/千次档） | 单据/表格结构化，输出行列 |
| 百度智能云表格识别 | 通用 ~1.8 元/千次；表格 ~3.6 元/千行（**注意计费单位不同**） | 有免费额度（企业认证 1000 次/月） |
| 阿里云读光 | 按次计费（见官网） | 表格/文档/资质证明系列全 |

按当前量级（几十张/天）月成本约几十到几百元——**不贵但也不白给**；且云 OCR
只解决"印刷表格"识别，手写与字段语义仍要在仓内解决。定位：方向 D 的兜底，
当前优先级低于路线一实测。

## 四、基准数据怎么读

- **OCRBench v2**（通用 VLM 的 OCR 综合卷，含中文子集、手写数学表达式等
  8 项能力）：2026-09 榜单领先者 Gemini 3 Pro ~63.4 分，中文子集首位
  Qwen2.5-VL-72B 63.7 分，**没有模型达到 70%**——这就是"通用 VLM 识别成功率
  低"的行业共性注脚，不是 deepseek-flash 独有的问题。
- **OmniDocBench v1.6**（文档解析卷，含表格 TEDS）：专用模型 95%+ vs 通用
  VLM 整体明显更低——**印刷体表格选专用路线的理由**。
- 两个基准都**不代表中文手写单据**：OCRBench v2 只含少量手写子项，OmniDocBench
  以印刷 PDF 为主。手写能力只能靠真值集实测。

## 五、评测方案（C 票落地步骤）

1. **确认网关可用模型清单**：对网关发 `GET /models`（OpenAI 兼容），列出可路由
   的视觉模型；若网关即 bigmodel，GLM-4.6V / GLM-4.6V-Flash 应可直接试。
2. **建真值集**：原辅料已有 60 张（S2 期）；**成品入库新建 30-50 张**（含多行
   明细、返工/退货单、手写样张），人工 Base 录入做 truth.jsonl。
3. **跑分**：复用 `scripts/eval_recognition.py` 口径（必提字段字段级命中率
   ≥90% 门禁 + 对齐命中率 ≥95%），候选模型各跑全量，对比：字段命中率、
   每张耗时、每张成本、rows 完整率（成品多行场景关键指标）。
4. **切换**：场景位 `finished_receipt_recognition` / `receipt_recognition`
   改模型配置即生效；先灰度成品场景，备用通道留原模型。
5. **可选增强**：双模型交叉验证（两模型各识别一次，diff 不一致字段标 ⚠）；
   轻调用（分类/方向预判）换 GLM-4.6V-Flash 免费档降成本。

## 六、推荐短名单

| 优先级 | 候选 | 角色 |
|---|---|---|
| 1 | **GLM-4.6V** | 首选实测：中文文档强、bigmodel API 直供、价格低；Flash 免费档做轻调用 |
| 2 | **Qwen3-VL（plus/max）** | 对照实测：开源系中文 OCR 榜首，多语言/手写先验好 |
| 3 | **GLM-OCR / PaddleOCR-VL** | 印刷表格兜底：需 GPU 本地部署或网关路由，管线加字段映射一跳 |
| 4 | 云表格 OCR（腾讯/百度/阿里） | 方向 D 兜底：结构化稳、按量计费，量大才划算 |
