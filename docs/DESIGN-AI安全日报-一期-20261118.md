## 0. 目的与裁剪口径

**功能目的只有一个：规范化日报内容**——员工写清楚「做了什么 / 到什么程度 / 有什么问题 / 怎么解决」。

需求原文按管控思维设计（两次解锁链 + 确认状态机 + 名单硬拦截 + 双份内容存储），一期按「只解决核心问题」裁剪：

| # | 拍板 | 决定 | 理由 |
|---|------|------|------|
| P1 | 五段 or 四段 | **四段**：协调并入「问题与协调」 | 员工最大分流困难=协调/风险二选一；问题的解法常是协调某人，一段写全闭环 |
| P2 | 生成按钮硬拦截 or 软警示 | **软警示**：按钮常可点，卡片列未完成名单 | 名单按天维护是持续负担；部门人少，人判比机器拦截灵活 |
| P3 | 载体 | **多维表格唯一数据源**（4 张表）+ 机器人卡片交互 | 状态机/查重/聚合/筛选是本需求灵魂，云文档全部打不通（详见会话评审） |
| P4 | 员工写入路径 | **卡片表单回调→机器人写表**，员工无表格编辑权 | Bitable 表单只能新建不能改原记录（违反验收②）；直授编辑权会互改行 |
| P5 | 初稿留痕 | Bitable 追加「提交历史表」（不用 PG 迁移） | 全部数据一处可见；避免与并行 WIP 迁移链纠缠 |
| P6 | 员工详情解锁 | 删除。已提交者随时可看自己记录 | 员工看自己的日报不需要锁 |

两次提交（初稿→AI一轮→修改完成）**保留**——这是「AI 建议被真正消化」的唯一保证。强制性的全部实现 = 「待补充」状态在群卡片上可见。

## 2. 数据模型（Bitable，1 Base 4 表）

**员工日报表** `reports`（一人一天一条，查重键=日期键+员工OpenID，客户端过滤）：

| 字段 | 类型 | 说明 |
|------|------|------|
| 日报日期 | 日期 | 展示/排序 |
| 日期键 | 文本 | `YYYY-MM-DD`，查重与拉取键 |
| 员工姓名 | 文本 | 冗余展示字段 |
| 员工OpenID | 文本 | 身份键（safety 应用作用域） |
| 今日重点工作 | 多行文本 | 做了什么（对象/区域/类型） |
| 完成情况 | 多行文本 | 到什么程度（数量/结论/进度/未完成） |
| 问题与协调 | 多行文本 | 问题+已采取措施+需谁支持 |
| 明日计划 | 多行文本 | 可空 |
| AI评价与建议 | 多行文本 | 一轮评价 ≥3 条 |
| 日报状态 | 单选 | 待补充 / 已完成 / 评价异常 |
| 首次提交时间 | 日期 | 含时间 |
| 完成提交时间 | 日期 | 含时间，可为空 |

四段字段始终存**最新内容**（初稿→最终版就地更新），初稿快照进历史表。

**汇总表** `summary`：汇总日期 / 日期键 / 负责人日报（markdown 多行）/ 发布时间。应提交人数等派生值不落库。

**名单表** `roster`：成员（人员字段→open_id）/ 角色（单选：员工、负责人）。成员姓名经本地 users 表 open_id 反查，查不到显示 open_id 尾段。

**提交历史表** `history`（append-only）：日期键 / 员工OpenID / 员工姓名 / 阶段（单选：首次提交、最终提交、AI评价）/ 内容（多行文本 json）。每次提交与每轮 AI 评价各追加一行。

## 3. 交互流程

**每日入口卡**（群，一日一张）：
- 顶部：日期 + `已完成 x / 应交 y`；中部：`待补充：@张三` / `未提交：李四、王五`（待补充用 @ 提及催办）
- 按钮：`📝 填写今日日报`（open_form，所有人）｜`📊 生成负责人日报`（gen_leader）｜已生成后：`🚀 发布`（publish）
- 状态变化（提交/完成/生成/发布）→ 重算 → PATCH 原卡

**表单卡**（DM 发起，四段表单）：
- form 容器 + 4 个 `input`（`input_type: multiline_text`，max_length 1000，required 前三段）+ submit 按钮（name=`dr_submit` 携带路由，value 双写 JSON）
- 「修改并完成」路径：`default_value` 预填当前四段内容
- 提交回调：form_value 取四段 → `service.submit(stage=first|final)` → toast

**AI 评价**（首次提交后，后台任务）：
1. `evaluation.evaluate(sections)` → LLM 契约 `{"suggestions": [≥3条], "overall": "一句话"}`，temperature 0.2
2. 校验失败/调用异常 → 状态 `评价异常`，DM 失败卡带`🔄 重试AI评价`按钮；成功 → 写建议字段 + 状态 `待补充` + 历史表追加
3. DM 员工建议卡（四段原文+建议列表+`✏️ 修改并完成`按钮=预填表单卡）+ PATCH 群卡
4. 每人每天每记录只评一轮；重试按钮是唯一重评入口（次数不限但同记录串行）

**最终提交**：回调 `submit(stage=final)` → 校验该记录处于待补充/评价异常 → 就地更新四段 + 完成提交时间 + 状态 `已完成` → PATCH 群卡。

**负责人汇总**：
- `gen_leader`：操作者须为名单角色=负责人 或 `permission:role:manage`（fail-closed，r3_card `_operator_is_admin` 同款）→ 后台 LLM 聚合全部 `已完成` 记录 → 校验 → upsert 汇总表 → 群卡追加草稿预览 + `🚀 发布`按钮
- 有未完成时：卡片明示「⚠️ 未完成：张三、李四，汇总将不含其内容」，仍可生成（软警示）
- `publish`：写发布时间 → 全文日报卡发群 → 群卡状态更新为已发布

**负责人日报格式**（AI 聚合输出）：四段式——`一、今日重点工作`（按【专项分类】）/ `二、数据项目`（有来源数据，多人提及同一事项去重不重复累计）/ `三、协调事项` / `四、风险报备`；来源不足或口径不一标 `（待核实）`；无风险不凭空补；可选明日计划。

## 4. AI 契约与降级

- 模型：`create_ai_service("text")`（ai_config 注册表 text profile → deepseek-flash，带审计+备用降级），`ai_audit_scope(scenario="daily_report_eval"|"daily_report_agg", channel="system")`
- 评价 prompt 骨架：四问检查维度（具体性/成果进度/风险闭环/一致性）+ 建议 3–5 条按重要性排序 + **事实边界：只提问、评价、适度整理，禁止编造数量/结论/整改结果/措施/时限** + 需求文档示例（初稿"作业票办理；现场巡查；变更验收"→ 三条补充建议）作为 few-shot
- 校验（代码层，不信任 LLM）：`suggestions` 为 list[str]，去空去重后 3≤n≤6；`overall` str 非空；任一不合法 → 整体判失败（AIOutputError → 评价异常），不降级到部分写入
- 聚合校验：`report_markdown` 非空且含 `一、二、三、` 三个段头；失败 → 不写汇总表，操作者收失败提示
- 评价/聚合均为**后台任务**执行，绝不占 2.9s ACK 窗口

## 5. 权限与幂等

- 卡片回调：payload 不可信（铁律同 r3_card），身份只认 `event_data.operator.open_id`
- 写记录：只允许写 `员工OpenID == operator` 的记录（不能替他人提交）
- gen_leader/publish：负责人名单 ∪ admin，fail-closed
- 幂等：一人一天一条（提交前查重，命中则 update）；eval 任务对同一 record 串行（submit 回调先置状态防重入）；群卡 PATCH 失败重建（daily_digest 护栏：早于昨天拒绝重建）
- REST 与卡片回调共用 service 核心，operator 分别来自鉴权用户 / event_data

## 8. 测试方案

**单测**（零真机）：卡片 JSON 结构（四 input/按钮 name/value 双写）、查重 upsert（命中 update 不 create）、评价契约校验（<3条/非str/异常→失败）、状态机（first→eval→final；eval失败→评价异常→重试）、名单差集（未提交/待补充）、回调路由（action name/scope 分发）、汇总校验。推送层由 conftest autouse 隔离。

**E2E（机器人测试群，REST 驱动真链）**：
1. lark-cli 建 Base「AI+安全日报（测试）」→ seed 脚本建 4 表+登记连接+播种名单（许康福=负责人）
2. DB 开闸（ENABLED=true）→ 触发入口卡 → 群内可见
3. 铸 token（许康福）REST：首次提交 → 真 LLM 评价 → 建议 DM 卡 + 群卡更新（待补充@）
4. 最终提交 → 已完成 → 群卡更新
5. 生成（负责人）→ 草稿 → 发布 → 全文日报卡进群
6. 人工补测：许康福真机点击 填写/表单提交（UI 面，唯一 REST 覆盖不到的环节）
