## 一、需求要点还原

### 1. 在职劳动合同管理（需求第一章）

| 需求点 | 内容 |
|---|---|
| 目标 | 签订 → 到期预警 → 续签审批 → 员工续签 → 盖章领取 → 归档 全流程线上化，建成合同电子档案库，一人一事一档 |
| 期限规则 | 第 1 次 3 年、第 2 次 6 年（累计满 9 年）、第 3 次无固定期限；**自每份合同起始日起算**（不按入职日）；系统按签订次数自动计算到期日；无固定期限不再进续签流程 |
| 到期预警 | 提前约 50 天进入公告期，通知**用人部门负责人**，台账同步标注到期状态 |
| 部门审批 | 用人部门在续签审批台账核对信息后勾选「同意续签 / 不同意续签」，系统记录审批时间；不同意 → 转终止劳动合同流程 |
| 通知链路 | 部门同意后：续签通知（提示员工到 HR 办理）→ 现场签字盖章（次数/期限/起止日期系统带出）→ 盖章完成推送领取通知 → 领取后推送签字提醒（链接线上签字，结果回传台账作为领取凭证） |
| 电子归档 | 9 条规则：范围（先本科以上、逐步全覆盖；离职单独归档）/ 时点（领取签字后）/ 扫描（逐页合并一份）/ 命名（工号+姓名+签订次数+起止日期）/ 存放（个人档案，与证件资料、离职材料同档）/ 缺失标识（未归档标注+按部门导出补扫清单）/ 版本保留（原合同不覆盖）/ 调阅权限（HR 全部、部门负责人本部门在职基本信息、员工本人；调阅下载留痕）/ 保管期限（离职后不删除） |
| 现状待补 | ①一般员工合同未电子化 ②档案未与证件/离职材料合并 ③离职合同未单独建台账 ④各环节状态分散、缺一处可查的完整进度 |

### 2. 离职人员劳动合同台账（需求第二章）

| 需求点 | 内容 |
|---|---|
| 目标 | 离职人员的合同终止记录、原件与材料单独管理，与在职台账分开，避免混同与误发提醒 |
| 台账内容 | 人员信息 + 合同信息（历次起止、签订次数、最后一份期限类型）+ 离职信息（终止/解除方式、终止日期、审批依据）+ 手续状态（离职流程单号、离职证明开具与送达状态、原件回收与归档状态） |
| 流程衔接 | 部门不同意续签或到期未续签 → 合同标记终止转离职流程 → 离职办结写入离职台账、不再参与预警 → 原件回收扫描归档 → 可按部门/离职时间/终止方式查询并出具合同情况说明 |
| 台账隔离 | 在职台账只留有效期内合同与待续签记录；两本台账不交叉 |

## 二、现状盘点（能复用什么、缺什么）

### 已有地基（直接复用）

| 现有能力 | 位置 | 与本需求的关系 |
|---|---|---|
| 合同到期定时提醒 | `hr/reminder/contract_scheduled.py`：每天 09:10 扫描，飞书提醒 **HR**，默认提前 30 天，数据源 = Employee.contract_end_date + OnboardingRecord 四组合同起止宽表 | 改造为需求口径（提前 50 天、**通知部门负责人**），数据源切换到新合同表 |
| 人事提醒框架 | `hr/reminder/`（config + routes + scheduled 注册模式，system_settings 可配 enabled/open_ids/days_ahead） | 预警/通知的调度与配置底座 |
| 证件资料库 | `EmployeeCertificate`：对象存储（`app/core/file_storage`）、版本保留、调阅经后端代理并记审计 | 合同扫描件归档**整套照搬**此模式；「与证件统一存放」天然满足 |
| 离职台账 | `DepartureRecord`（departure_records，飞书离职表同步，含离职日期/部门/岗位） | 离职合同台账的人员与离职信息来源，补充合同/手续状态字段 |
| 部门负责人口径 | `Employee.department_manager_name`（转正审批第二级同款） | 续签审批通知的收件人 |
| 台账 Excel 导入 | `ledger_import.py` 两步预检式 | 存量合同数据从多维表格迁移的通道 |
| 飞书通知 | HR 模块既有飞书推送（培训/审批/提醒均在用） | 四类通知（部门审批、续签、领取、签字提醒） |
| 员工档案 | Employee 主档 | 合同台账的关联主体 |

### 缺口（本方案要新建）

1. **无独立合同表**：合同数据散在 Employee（第 1 份）+ OnboardingRecord（1~4 份宽表），无法表达「一份合同一行 + 签订次数 + 状态流转 + 归档」
2. **无部门维度续签审批**（现有提醒只发 HR；平台飞书审批适配器只有读取能力，无创建实例）
3. **无面向员工的通知链路与线上签字确认**
4. **无合同扫描件归档**（上传、命名、未归档标识、补扫清单、调阅留痕）
5. **无离职合同台账**（DepartureRecord 无合同/手续状态字段）
6. **无完整进度视图**（合同详情一处可查全流程状态，对应「待补四」）

## 三、总体设计

### 3.1 数据模型（hr schema，全部软删除、无外键约束）

```text
hr_labor_contracts            劳动合同表（一份合同一行，核心表）
├─ 员工：employee_number / name / department / position（冗余快照，入账时固化）
├─ 合同：seq_no(1|2|3) / term_type(fixed_3y|fixed_6y|open) / start_date
│        / end_date(按 term_type+start_date 自动算，open 为 NULL)
│        / sign_date / 首签标记
├─ 状态：status（见 3.2 状态机）
├─ 部门审批：dept_decision(agree|disagree) / dept_decision_by / dept_decision_at
├─ 签收：employee_sign_confirmed_at / sign_token_hash（线上签字凭证）
├─ 归档：archive_status(unarchived|archived) / archive_file_key / archive_file_name
│        / archive_uploaded_by / archive_uploaded_at
└─ 终止：terminated_reason / terminated_at / departure_record_id（关离职台账，逻辑关联）

hr_contract_access_logs       调阅/下载留痕（照搬证件库审计模式）
├─ contract_id / viewer_id / viewer_name / action(view|download) / created_at

（离职合同台账 = 视图层概念：DepartureRecord 增量补字段 + hr_labor_contracts 按员工
  employment_status 关联；不另建平行人员表，避免两处维护）
DepartureRecord 新增列：contract_term_type_last / contract_termination_type
  / contract_termination_date / contract_approval_ref（审批依据）
  / separation_process_no（离职流程单号）/ certificate_issuance_status（离职证明开具/送达）
  / original_recovery_status（原件回收状态）
```

设计要点：

- **期限自动计算**：`seq_no=1 → fixed_3y`、`seq_no=2 → fixed_6y`、`seq_no=3 → open`；`end_date = start_date + N 年`（服务端计算并落库，前端只读展示），杜绝人工推算偏差（需求原话）。
- **软删除防重**：`hr_labor_contracts` 建 `(employee_number, seq_no)` 部分唯一索引 `WHERE is_deleted=false AND status != 'terminated_superseded'`——同一员工同一签订次数只允许一份有效记录，删除后可重新录入（遵循「重复添加→删除→添加不触发隐形 bug」约束）。
- **原合同保留**：续签生成新行（seq_no+1），旧行状态置 `superseded`（已被新合同取代），不物理覆盖——对应归档规则「续签按新合同归档，原合同保留」。
- **扫描件一份合同一份文件**（需求：逐页合并为一份、不拆分），换传新版本时旧行保留可查（沿用证件库版本化思路）。

### 3.2 合同状态机

```text
                    ┌──────────────────────────────────────┐
                    │                                      │
 active ──(进入50天公告期)──▶ pending_renewal（公告期，已自动发起飞书原生审批）
    │                              │
    │                    ┌─────────┴──────────┐
    │              审批通过（回写）          审批拒绝（回写）
    │                    │                    │
    │             renewing（办理中）        terminated（终止）
    │                    │                    └─▶ 写入离职台账、停止一切提醒
    │          员工签订（生成新合同行 active）
    │          旧行 → superseded
    ▼
 superseded / expired_unrenewed（到期未续签 → terminated 同路径）

 归档维度（与状态正交）：archive_status: unarchived → archived
```

- 台账列表按状态打标：`生效中 / 公告期 / 续签办理中 / 已归档 / 未归档 / 已终止 / 已取代`。
- **待补四的解法**：合同详情页用 Steps 组件呈现六节点进度（预警→部门审批→通知续签→签订盖章→领取签字→归档），一处可查完整进度。

### 3.3 到期预警与通知（改造现有 + 新增三类）

复用 `hr/reminder/` 框架，`contract_scheduled.py` 改造 + 新增任务：

| 通知 | 触发 | 收件人 | 渠道与内容 |
|---|---|---|---|
| ① 到期预警+发起审批 | 每日扫描，`today + 50d` 窗口（可配）：进入公告期即**自动发起飞书原生审批实例**（见 3.4），台账同步标注公告期 | **用人部门负责人**（Employee.department_manager_name，作为审批人）；HR 抄送可配 | 部门负责人收到飞书**原生审批待办**（自带消息提醒与移动端审批入口）；另发 HR 提示卡片备查 |
| ② 续签通知 | 审批通过（同意续签）回写时触发 | 员工本人 | 飞书卡片：到 HR 办理续签、联系人、携带材料（可配文案） |
| ③ 领取通知 | HR 在台账标记「已盖章」即时触发 | 员工本人 | 飞书卡片：到 HR 领取合同原件、联系人 |
| ④ 签字提醒 | HR 在台账标记「已领取」即时触发，附一次性签字链接 | 员工本人 | 飞书卡片「点击签字」→ 站内确认页 → 回写 sign_confirmed_at（作为已领取凭证） |
| ⑤ 归档缺失提醒（P2） | 每周汇总未归档清单 | HR | 按部门分组，附补扫清单导出 |

- 预警排除口径：仅 `status=active` 且 `term_type != open` 的在职合同；已离职/已终止/无固定期限一律不出窗（需求「两本台账不交叉」）。
- 50 天、3 年、6 年、通知文案均入 `hr.system_settings`（沿用「人事提醒配置」卡片扩展），服务器部署无需改环境变量。

### 3.4 部门续签审批（飞书原生审批，站内勾选降级）

**主通道：系统自动发起飞书原生审批实例**——部门负责人在飞书内完成原生审批（消息待办 + 移动端一键同意/不同意 + 审批中心留档可查），审批结果自动回写合同状态。需求原文的「台账勾选」是现行多维表格做法，文档已授权「具体实现方式由项目办结合平台能力确定」，原生审批是升级实现。

```text
扫描进入公告期 ──▶ 系统创建审批实例（POST /approval/v4/instances）
                   表单自动填充：姓名/工号/部门/岗位/原合同到期日/
                   本次签订类型与次数/合同期限/起止日期
                   审批人 = 部门负责人（open_id，定义设「指定成员」由 API 传入）
                        │
 部门负责人在飞书审批（通过/拒绝）
                        │
 定时轮询实例状态（沿用职称评审已验证模式）──▶ 回写合同表：
                   通过 → dept_decision=agree + renewing + 触发续签通知②
                   拒绝 → dept_decision=disagree + terminated + 转离职流程
                   同时存 instance_code + 审批链接（= 离职台账「审批依据」字段来源）
```

设计要点：

- **平台层最小扩展**：`app/platform/integrations/feishu/approval.py` 现只有读取能力（`list_instance_codes`/`get_instance`，职称评审在用），需新增 `create_instance`（创建审批实例）一个方法；沿用其「凭证可传独立应用、缺省回落全局 FEISHU_* 应用」的约定，先复用全局应用凭证，不加新环境变量。
- **结果回写走轮询，不新增事件订阅基础设施**：定时任务（复用职称评审拉取模式，时间分段/分页已趟平）拉取时间窗口内实例 → `get_instance` 判定状态变更 → 幂等回写。轮询间隔约 10~30 分钟，审批延迟可接受；事件订阅后置可选优化。
- **降级兜底（双模式）**：`hr.system_settings` 配置了审批定义编码（`hr_contract.renewal_approval_code`）即走原生审批；未配置（如本地开发环境、定义未建）降级为站内台账勾选审批（原方案保留为 fallback：部门负责人视图 + 行内同意/不同意 + 确认弹窗 + 记录 decision/by/at），两条路径回写同一组合同字段，前端无感知差异。
- **权限**：站内降级路径下部门负责人仅能操作本部门记录（复用 `user_department_access_routes` 部门数据权限）；原生路径的审批人由发起时显式指定。
- **审批留档**：合同详情进度 Steps 的「部门审批」节点直接挂审批实例链接，点击跳飞书审批详情；离职台账「审批依据」字段引用同一链接。

### 3.5 电子档案库（照搬证件库模式）

- 上传：MinIO（`app/core/file_storage` 的 store_object/proxy 模式），PDF/图片，一份合同一份合并文件；文件名按「工号+姓名+签订次数+起止日期」由服务端生成落库。
- 未归档标识 + 补扫清单：台账 `archive_status` 列 + 「按部门导出未归档清单」按钮（Excel，复用 xlsx_utils）。
- 调阅权限（需求第 8 条）：
  - HR：全部合同原件；
  - 部门负责人：本部门**在职**人员合同基本信息（不含原件下载）；
  - 员工本人：本人合同（站内「我的劳动合同」轻页或经 dazah-agent 查询，见 §6 待确认）；
  - 全部调阅/下载写 `hr_contract_access_logs` + 平台审计。
- 保管期限：离职不删除，随离职台账保留（软删除策略天然满足，永不物理删除）。

### 3.6 一人一事一档（聚合视图）

- 员工档案详情新增「合同」页签（与既有「证件」页签并列）：历次合同列表 + 各份扫描件 + 归档状态。
- 数据同源（hr_labor_contracts + employee_certificates + DepartureRecord），满足「与证件资料、离职材料同一档案下存放」。

### 3.7 离职合同台账

- 入口：`hr/departure` 既有页面扩展「合同台账」页签（不新建平行页面，DepartureRecord 已是离职人员唯一数据源）。
- 展示：需求四块内容（人员/合同/离职信息/手续状态）；合同列从 hr_labor_contracts 按 employee_number 聚合（历次起止、次数、最后期限类型、终止方式、终止日期）。
- 衔接：合同 `terminated` 时回写 DepartureRecord 补充列；离职办结后该员工全部合同退出预警扫描（扫描 SQL 已按 status 过滤，天然满足）。
- 导出：按部门/离职时间/终止方式筛选导出「离职人员合同情况说明」（Excel）。

## 八、风险与注意事项

1. **飞书审批前置依赖**：审批定义需人事在审批后台手工创建（API 不支持建定义），应用需开通审批实例创建 scope；这两项未就绪时系统自动降级站内勾选，不阻塞上线，但要避免长期双轨。
2. **审批结果回写走轮询**：存在 10~30 分钟级延迟；回写必须幂等（以 instance_code + 状态为准，重复拉取不重复触发通知）。审批定义后续若改表单控件名，轮询解析按 custom_id 兜底。
3. **宽表→新表迁移**：OnboardingRecord 四组合同起止是现有唯一数据源，迁移脚本须处理「不足 4 份、跨工号重名、日期缺失」等脏数据；本地开发库允许破坏性重迁，生产迁移只读不写回宽表。
4. **不要动既有 `contract_scheduled.py` 的提醒口径**直到新表数据迁移完成，避免迁移窗口期双源重复提醒（加 `system_settings` 开关切换）。
5. **归档文件命名含中文与日期**：MinIO key 用英文安全字符，展示名按需求规则。
6. **敏感信息**：合同扫描件属于敏感个人资料，代理下载必须鉴权 + 审计（证件库已趟过的路，直接照搬）。
7. 部署：通知/扫描任务依赖服务器侧调度器与飞书凭证，本地验证用本地开发 token；env 无新增变量（审批定义编码等配置全走 system_settings，凭证复用全局 FEISHU_* 应用）。
