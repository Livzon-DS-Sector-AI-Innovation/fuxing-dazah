> 依据：本次对 197 条占位判定依据记录的实测重跑（140 成功 / 57 未写回）+ 全表 2464 条字段冲突量化 + 30 天 AI 调用审计 + 代码走读

## 0. 执行摘要

**三条主线、六个判断：**

1. **字段冲突（专题一）**：AI 识别产出 6 个 AI 列（描述/级别/分类/类别/判定依据/整改建议）+ 2 个系统派生列（督办等级、隐患编号兜底）与人工列「双轨并行」；当前写路径不存在 AI 覆盖人工字段的问题（140 次写回字段固定为 AI 7 列，隐患编号 0 变动），**冲突发生在"读口径"**：
   - 台账「隐患等级」列按人工优先展示，但**筛选/统计走 AI 值**（`page_query.py:158`）；「隐患类别/类型」列直接展示 AI 值（`HazardLedgerPage.tsx:427-455`）——同一页面三套口径；
   - ③督办已正确「只取人工等级」（`hazard_supervision.py:100-104`），但⑤评分与页面筛选把 AI 等级当权威值用；通报则是 `manual or AI` 混合回退；
   - 人工优先的**正确样板已存在**（③督办、②-c「人工关闭优先，AI 结论单向跟随」），应把该原则固化为全模块统一契约。
   - 结论：**确立"人工列唯一权威、AI 列仅候选证据、系统规则列单一写者"三层规则**，P0 先统一读口径，P1 清理遗留字段与差异展示。

2. **识别链路（专题二）**：链路本身可用（RAG 恢复后单条 p50 AI 耗时 5.4s、P90 7.3s，30 天 496 次调用 0 失败），但**质量瓶颈不在"有没有 RAG"**：
   - 本次 57 条失败中，**26 条检索 top-1 相关性 <0.3（未召回相关条文）**、13 条检索里有「第X条」可引用分块但模型拒引；知识库实测缺 GB 30871；长噪声描述直接当检索 query 导致召回漂移；
   - 视觉输出 JSON 合法率 89.2%，**31 条非法样本中 22 条只是尾逗号**（本地修复可到 96.9%，零额外调用）；规则校验 error 触发率 83.5% 但非严格模式全放过；
   - 判定依据规则自相矛盾：prompt 允许「知识库无对应条文→填占位」（`prompts.py:93-94`），规则引擎非严格模式只告警不拦截（`ai_analysis.py:111`、`rules.py:212-238`）；
   - **生产链路没有「知识层降级不写回」闸门**：RAG 失败时链路继续跑并把占位依据 + 分类一起写回，分类非空后永不再重试——这正是 197 条占位产生的机制（本次靠脚本才修复）；
   - 失败语义「不写字段→下轮重试」缺少退避/限次/死信，永久失败记录会每 5 分钟无限烧 AI；
   - 成本结构：单条约 8.75k input tokens（30 天 4.34M / 496 次），其中知识库上下文占约 47%；图片每条重下载、RAG 结果 1h 缓存无写入失效联动。
   - 结论：按「输出可靠性 → 判定依据质量 → 检索质量 → 失败治理 → 评估体系」分 P0/P1/P2 优化。

3. **SuperAgent（专题三）**：平台底座 `app/platform/superagent/`（Source→Trigger→Task→Effect→Watchdog）代码已上线但 `SUPERAGENT_ENABLED=false`、5 个 Source 全停用、0 Task/0 Effect；`business_agent` 是面向对话的 pydantic-ai Agent（86 会话/124 消息/18 待确认），与 ① 是两种形态。
   - **① 不应 Agent 化主链**（每条 1 次 LLM 是成本/确定性前提；多轮会 3~6× 成本并破坏 5min/200 条吞吐）；**应复用平台底座**：Source 化消除自管轮询与重启重放、Effect 化写回获得幂等/退避/对账、Watchdog 获得健康与死信告警；
   - **例外才交给 Agent**（RAG 空/JSON 失败/引用缺失→安全助手多步补检 + 人工确认），先 `observe` 后 `auto`；
   - `orchestrator + script1~8`（危险源辨识）不是"上一代 super-agent"，是确定性 workflow；正确合并点是 superagent 的 **Executor 协议**，而非改成 tool-calling Agent。
   - 结论：**A（确定性主链底座化，P0）+ B（例外 Agent，P1/P2），不做 C（全 Agent 化）**；②③⑤逐步挂到同一「记录级 Thread」编排。

### 2.3 设计原则（以人工为准）

1. **单一权威**：每个业务语义只认一个人工权威列；AI 列是"候选/证据/参考"，不进入任何权威口径（列表筛选、统计、督办、评分、通报）。
2. **单向写入**：AI 只能写 `*（AI）` 列；人工列只由人工（飞书）或经人工确认的动作写入；系统规则列（督办等级/评分）只由各自规则引擎写，禁止多写者。
3. **读口径统一**：统一 `effective_*` 取值函数——`manual 有值取 manual，否则 fallback AI 且显式标注来源`；所有下游（页面筛选/统计/看板/评分/通报/Agent 查询）只走该函数。
4. **AI 候选不落权威**：AI 结果高差异（如级别不一致）时，页面展示"AI 建议：较大（与人工不一致）"提示，提供"采纳 AI"人工动作（写人工列并审计），而不是自动同步。
5. **重跑不覆盖人工**：①重跑只刷新 AI 列；人工若编辑过 AI 列或已人工确认，需 stale 标记与二次确认（P2）。
6. **类型契约对齐**：人工/类型列与 AI 列一一镜像（单选对单选），多选历史值给兼容归一（P1）。
7. **字段生命周期**：存量遗留字段（AI审核结论等）迁移/下线；新增字段必须登记归属与读口径（P1）。

### 2.4 落地改造清单

**P0（先把口径统一 + 止血，1~2 天）**
1. 新增 `hazard_direct/field_authority.py`：字段归属注册表（owner∈{HUMAN,AI,SYSTEM,DERIVED,FORMULA}），写函数必须声明 owner，越权写告警；单一事实源。
2. `HazardView` 增加 `effective_level/effective_type/effective_category`（manual 优先、AI fallback + `level_source` 标记）；`page_query._matches`、统计、⑤评分输入、`bulletin`、Agent 查询/导出统一改用 `effective_*`。
3. 前端台账：等级/类别/类型三列统一"人工优先"，不一致时悬浮提示 AI 值；AI 为空时 fallback 并标注"AI 建议"。
4. 明确督办等级单一写者：①不再写督办（③独立写），或反向收编 ③ 到 ① 的写回（二选一，需拍板；推荐 ③ 唯一写者，① 只算不写）。
5. 统一写锁：①②③⑤ 共用 `repo.WRITE_LOCK`（Bitable 单表写不支持并发）。
6. 止血 C8：旧事件通道相关代码标记 deprecated 并加运行期断言（开关开启即告警），防止误开整行覆盖人工列。

**P1（1 周内）**
7. 迁移/下线遗留字段：AI审核* 5 字段（36 条）归档说明；重复标签（AI）查清写入方后决定保留/废弃；C5 的 8 个无消费人工列确认停用或接入。
8. 字段类型对齐：人工级别多选→单选（1 条双值人工裁决）；`hazard_supervision` 入口先经 `HAZARD_LEVEL_MAP` 归一；统一中英文枚举映射。
9. 差异可视化：详情页/接口返回 `ai_vs_manual` diff（等级/分类/类别），附"以人工为准"标注；②-b/②-c 规则补录与 AI 结论分选项/分列。
10. ⑤评分输入改为 `effective_level`，并在评分说明标注"基于人工等级"；通报统一 `effective_level`。
11. 写回护栏 CAS：写前回读，仅当目标列仍等于计算快照才写（防 ①/③ 竞态写旧值）。

**P2（2~4 周）**
12. 「采纳 AI」动作：人工一键把 AI 候选写入人工列（写人工列需显式动作 + 审计留痕：who/when/from_ai/record_id）。
13. stale 标记：写 AI 列时记录输入指纹（描述+级别+类别 hash）到新列，读取时比对；人工改输入后 AI 列标 stale，重跑需二次确认。
14. 字段治理测试：单测锁死"AI 写路径不得包含人工列"、"页面筛选用 effective 口径"、"旧通道开关不得为 true"。

### 2.5 验收指标

- 页面/统计/评分/通报使用 AI 值作为权威口径的代码路径 = 0；
- 人工列被 AI 覆盖次数 = 0（写回字段白名单单测）；
- 人工级别与 AI 级别差异记录占比（现状 10.7%）≤ 基线且可视化 100% 覆盖；
- 「采纳 AI」动作审计完整率 100%。

### 3.1 链路耗时/成本构成（单条，实测估算）

> 口径：round1 109 条、并发 2，worker 秒 = 719s × 2 = 1438s。**真实单条服务 ≈13.2s**（吞吐 ≈4.5~5 条/分钟/2 并发）。

### 3.3 优化方案

**P0 快速止血（1 天内可验证，按性价比排序）**
- **① JSON 局部修复**：解析前清理尾逗号/围栏/截取首尾大括号，修复后过 schema 校验并在审计标 `json_repaired` → 合法率 89.2%→96.9%，省 22/288 次重试调用，p90 -5~8s；
- **② 视觉调用加 `response_format=json_object`**（先验证 deepseek 视觉端点支持，不支持则回落）→ 预计非法率进一步降；
- **③ 只下载缺陷图 + Feishu tenant token 缓存** → 附件下载 -44%、每条 -0.8~1.3s；
- **④ AI 客户端单例**（配置指纹变更重建）→ -0.5~1s/条；
- **⑤ 占位/低质不写回门禁**（见 A-1/A-2）→ 阻断"占位污染→永久离队"。

**A. 输出可靠性（P0，1~2 天）**
1. **补「降级/低质不写回」闸门**：识别前若 RAG `degradation != ragplus` 或 chunks==0 → 本条按失败处理（不写任何字段，保持「分类（AI）空」以便恢复后自动重试），并记录降级事件；
2. 写回前质量门槛：判定依据为空/含占位文案/引用无法在本次 chunks 命中 → 视为失败不写（或只写分类等低风险字段并标记待补）；
3. 视觉解析失败改为"带错误反馈的 JSON 修复重试"（第二次 prompt 附上次非法输出 + 校验错误），而非整段盲重发；文本路径同样加一次修复重试；
4. `strict_mode=True` + 字段级容错：缺字段只补跑缺失字段（同一输出 schema），避免整条重跑；
5. 输出校验器扩展：JSON 截断检测（`finish_reason=length`）、字段类型/枚举/长度/引用格式校验，失败进入重试或人工队列。

**B. 判定依据质量（P0~P1，2~4 天）**
6. 拆分字段语义：`major_hazard_basis` 只承载"重大隐患判定依据"；整改依据并入 `整改建议（AI）`，避免"无重大隐患条文→占位"污染判定依据；
7. prompt 改造：明确"知识库无对应条文"时的合法输出（宁缺毋滥 + 转人工标记，而非写占位进表）；引用格式统一 `《法规》第X条：'原文'`；增加"引用必须来自本次注入的知识库片段"的强约束；
8. 规则强校验：basis 引用的法规名/条号必须能在本次 RAG chunks 中匹配（doc_name/article 级），不匹配→标记 `citation_unverified` 并不写回；
9. few-shot 增加"无匹配→应输出什么"负例，减少占位触发。

**C. 检索质量（P1，1~2 周）**
10. query 改写：从长噪声描述抽取「设备/物质/行为/场所/标准关键词」后再检索（规则词表 + 轻量 LLM 二选一）；视觉分析结果回喂检索（Q2）；
11. 检索参数：top-k 12 → rerank → 8；对短描述/多主体描述做多路查询合并；评测 recall@8；
12. KB 补录闭环：以失败样本聚类为输入（如受限空间、消防水、防台风、PPE 表格式分块），补录/重切片缺失法规；表格型分块增加"条文上下文"元数据；
13. RAG 缓存：KB 变更（ragplus_sync/ingest）时自动 `invalidate_knowledge_cache()`（现仅 API 手动）。

**D. 失败治理与人工兜底（P0，2~3 天）**
14. 失败分桶 + attempts/backoff/上限：失败原因落 `ai_call_audits` 维度 + 记录的 attempts；超过 N 次进死信，不再每轮重试；
15. 死信→人工队列：生成结构化提示（record_id、失败原因、检索证据、AI 输出），推送安全管理员（可复用 business_agent 确认卡/Attention）；
16. 告警只报"新增失败/死信"，避免每轮重复告警。

**E. 效率与成本（P1~P2）**
17. 附件内容缓存（file_token/hash → 已降采样文件），重复分析零下载；
18. AI 客户端复用（进程级单例，替代每条 `create_ai_service`）；
19. 知识库上下文裁剪（rerank 后摘要/压缩，token 预期 -30%）；
20. 模型分级：视觉描述用 VLM、判定/引用用更强文本模型；ai_config 场景注册表绑定 `hazard_identification`（①消费场景配置）；
21. 批量写回合并 + 写间隔，仅 Bitable 并发约束内；
22. few-shot 从 4175 字压到 2~3 例（静/动态 prompt 合计 token 9k→6.5k，-28%）；图片编码/落盘改 `asyncio.to_thread`，并发 3→4~6（写回仍单并发）；
23. 两阶段链路：分类+级别（轻量 2k token）→ 按类别定向检索 2~3 chunk 再产出依据/建议（单条 token -40~50%）；
24. 事件驱动（Bitable `bitable_record_changed_v1` 已有 handler）替代 5min 全表轮询，轮询降为 15~30min 兜底。

**F. 可观测与评估（P1）**
22. `ai_call_audits.extra` 扩展：`json_ok / retry_count / retrieval_docs / degradation / citation_verified / missing_fields / exit_reason`；新增识别质量看板；
23. 离线评测集：以 2464 条中人工已填级别/分类/类别为弱标签（可用 800+ 条），另建 200~500 条人工标注意见；每次 prompt/模型/RAG 变更跑回归；
24. 指标体系见 3.4。

## 4. 专题三：SuperAgent 架构的应用提升空间

### 4.1 三层实体与差异画像

| 维度 | ① AI 识别（batch 管线） | business_agent（对话 Agent） | superagent 底座（平台） |
|---|---|---|---|
| 触发 | 5min interval + Bitable 判据 | 人发消息 | Source（Bitable/cron/消息） |
| 决策 | 单次 LLM + 固定 JSON | 多轮 tool-calling | 一期无 LLM（程序判定） |
| 输入 | 记录+图片+RAG 预注入 | 对话+工具结果 | Trigger 事件 |
| 输出 | 强类型 7 列写表 | 自然语言+确认卡 | Task/Effect/Report |
| 失败语义 | 不写→下轮重试 | 澄清/确认/报错 | 幂等+退避+死信 |
| 成本敏感 | 极高（每条 1 次调用） | 中 | 低（程序） |
| 人工为准 | 字段隔离 | 写前确认 | Attention/订阅 |

**① 要不要 Agent 化？否。** Agent 三要素（多步规划/动态选工具/对话消歧）在主链是负资产：会把每条 1 次调用变 3~6 次，在 5min/200 条/并发 3 约束下不可行，并破坏温度 0.05 的可复现性（`plugin.py:63-67`）。但 ① 有三个只有多步才能补的真实缺陷：图文割裂、字段级失败无补救、引用依据无强约束——这正是"例外 Agent"的价值来源。

### 4.2 可复用能力映射

| 能力 | 结论 | 复用方式 | 成本 |
|---|---|---|---|
| superagent Source/Trigger（bitable_poll） | **最该复用** | ①改 Source 化：指纹幂等 + 读位持久化，重启不重放/不漏单 | ~2d |
| superagent Effect/Executor | **最该复用** | 写回做 `hazard_ai_writeback` effect（先存后做/退避/对账）；识别注册程序 executor | ~2d |
| Watchdog/HealthBoard | 直接复用 | 连续失败、死信、健康度进看板 + DM 告警 | ~1d |
| core/pipeline（超时/审计/截断） | 可借鉴 | 图片/检索/校验/写回各包一层，统一单点审计 | ~0.5d |
| ai_config 场景绑定 | 已注册未消费 | ① 从 text/vision profile 改为场景×模态二维解析 | ~1d |
| skills/SOP 软配置 | 借鉴 | prompt 拆分为 md + 版本号，安全管理人员可改软性内容，硬护栏留代码 | ~1.5d |
| 权限/写确认（PendingAction） | 主链不适用，例外可用 | 重大隐患/低置信写回前人工确认 | ~2d（可选） |
| 会话/记忆/压缩/路由 | 不适用 | ① 无会话；仅借鉴 turn_gate 的多 worker 锁教训 | 0 |

### 4.3 三方案对比

- **方案 A（确定性主链 + 底座化）**：①保持现有 plugin/规则/写回不变，调度从自管 interval 迁到 superagent Source→Effect，写回进 effects 队列。
  优点：成本/时延/确定性不变，幂等对账、退避、死信、重启不重放、可观测全部白拿；与 ③ 督办已采用的形态一致（`superagent_bridge.py` 冒烟②），回滚=关开关。
  缺点：不解决 Q1/Q2/Q3 的质量问题。工作量 5~6 人日。
- **方案 B（确定性主链 + 例外 Agent）**：主链全量照跑；例外（RAG 空/降级、JSON 失败、枚举非法、basis 空、引用不可验证）交 Agent 多步补检（看图→二次检索→法规核对→产出同一 `HazardIdentificationOutput`）。
  优点：成本≈1× + 例外率×3~5；可先 `observe`（只记录不写回，复用 Policy 语义），再 `auto`；人工为准更强（例外默认不写）。
  缺点：例外判据要运营；时延不可控；审计需聚合。增量 6~8 人日。
- **方案 C（全 Agent 化）**：每条 4~6 次调用，吞吐/确定性/成本/回滚全部劣化。**不立项**。

**推荐：A（P0）+ B（P1，先 observe，后 auto）**。判断依据：① 的痛点与 superagent 一期立项理由逐条重合；底座是"运行时"，Agent 是"例外处理器"，二者层次不同，不冲突。

### 4.4 推荐目标架构

```
                    ┌────────── app/platform/superagent/ ──────────┐
 Bitable 变更/轮询 ─▶ Source(bitable_poll: hazard.ledger)          │
                    │   ▼ Trigger(指纹幂等, relevant_fields 排除 AI 列)│
                    │   ▼ Task: hazard_ai_identify                 │
                    │       Executor=程序(确定性主链: 图→RAG→LLM→规则)│
                    │   ▼ Effect: hazard_ai_writeback (串行/退避/对账)│
                    │   ▼ Watchdog/HealthBoard + 死信告警            │
                    └───────────────┬──────────────────────────────┘
                                    │ 例外(占位/JSON失败/低置信/引用不可验证)
                                    ▼
                    business_agent「AI 识别复核员」
                      tools: view_images / search_regulations /
                             get_record_context / cross_check /
                             propose_writeback
                      → 结构化 Attention 卡片 → 安全管理员确认
                      → 以人工为准写回；失败样本沉淀为知识库补录候选
```

关键红线：**`relevant_fields` 必须排除全部 AI 写回列**，否则写回改 `last_modified` 会触发自激循环（bitable_poll 指纹只挡"相关字段未变"，挡不住"相关字段就是 AI 列"）。

### 4.5 与 ②③⑤ 的协同：记录级 Thread，而非域 Agent

①→②→⑤ 是**数据依赖**（②依赖①识别结果、⑤依赖①分类），不是意图分发——用 Agent 编数据依赖是用错工具。建议统一 `thread_key = bitable:hazard:<record_id>`，①②③⑤每次写回同一 Thread 的 Trigger/Effect，天然串行、可回溯、可订阅；③ 已具备该形态（`superagent_bridge.py` 冒烟②），① 跟随即可。

### 4.6 `orchestrator + script1~8`（危险源辨识）的定位

不是"上一代 super-agent"，而是**确定性 workflow 状态机**：有节点/状态/每步人工 gate，无分支、无工具选择、下一步由代码决定（`orchestrator.py:61-128`）。它已是该业务最优形态；与 superagent 的唯一正确合并点是 **Executor 协议**（一条辨识记录=一个 Task，每步=program executor，人工 gate=Report(waiting)），用于统一留痕/重试/观测面，**不改 Plugin、不改成 tool-calling**。

### 4.7 路线图

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0（1~2 周）** | A：①收编 superagent Source/Effect；审计扩展；失败分桶+退避+死信；prompt 拆分与修复重试；统一读口径（与专题一 P0 同步） | kill -9 对账零重放零漏单；占位率≤3%；JSON 合法率≥95%；单轮 P95<12min |
| **P1（2~3 周）** | B-observe：例外 Agent（4 工具+同一输出 schema），只记录不写回；评估集+质量看板；RAG query 改写；KB 补录 | 例外率<8%；rescued≥60%（observe 口径）；引用可验证率≥95% |
| **P2（3~4 周）** | B-auto：例外 auto + 重大隐患写前人工确认；②③⑤挂 Thread；skills 化 prompt；orchestrator 收编 Executor | 人工复核率<10%；重大误判 0；①②⑤字段完整率≥99%；Token -30% |
