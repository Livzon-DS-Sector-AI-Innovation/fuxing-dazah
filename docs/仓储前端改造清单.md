## 二、改造项

### P0-1 补前端工程脚本与测试设施（≈半天）

- **问题**：全前端零测试、无 typecheck 脚本，任何回归都靠人肉点页面。宁夏侧正是靠行为化测试（权限显隐、写流、失败分支 11 个用例）兜住 2356 行巨石组件的质量。
- **步骤**：
  1. 安装 devDependencies：`vitest`、`@vitest/coverage-v8`、`@testing-library/react`、`@testing-library/user-event`、`@testing-library/jest-dom`、`happy-dom`、`@vitejs/plugin-react`。
  2. 新增 `vitest.config.ts`：environment happy-dom、setup 文件引入 jest-dom matchers + antd `App` 上下文所需 polyfill；suite timeout 15s（antd portal 渲染慢，宁夏踩坑同款）。
  3. `package.json` scripts 补齐：`"test": "vitest run"`、`"test:watch": "vitest"`、`"typecheck": "tsc --noEmit"`、`"lint"` 保持。
- **验收**：`pnpm test`、`pnpm typecheck` 可执行且通过；首个测试文件落地（见 P0-2 / P1-1 配套）。

### P0-2 失败态与空态区分（≈半天）

- **问题**：列表失败时 `catch { message.error(...) }` 后表格回落为空数据——用户无法区分"没数据"和"加载失败"。宁夏 DESIGN.md 的规则值得直接采用：**空态必须区分 无结果 / 无数据 / 出错**，出错时展示 Alert + 重试入口，而不是伪装成空表。
- **步骤**：
  1. 排查 19 个组件的 catch 分支（重点：`StockTable`、`MaterialTable`、`MovementTable`、`StocktakeBoard`、system 各 Tab）。
  2. 统一模式：失败 → 表格上方 `<Alert type="error" action={重试}>`，保留上次成功数据；空数据 → `<Empty>`；两者互斥。React Query 迁移（P1-1）后此模式由 `isError/error` 天然获得，可合并实施。
- **验收**：断开后端请求 warehouse 页面，看到错误 Alert 而非空表；恢复后重试可自愈。

### P1-1 warehouse 组件接入 React Query（≈1 天）

- **问题**：`@tanstack/react-query` 已装、Provider 已全局挂载，但 warehouse 19 个组件仍是手写 loading/fetchData/setTimeout 轮询式加载（如 `MaterialTable.tsx:38-60` 的 `useCallback + useEffect + setTimeout(fetchData, 0)` hack、手写 8 个 state）。
- **步骤**：
  1. 先迁 4 个核心表格：`MaterialTable`、`StockTable`、`MovementTable`、`StocktakeBoard`——`useQuery({ queryKey: ['warehouse','materials',{page,pageSize,keyword,category}], queryFn })` 替换 fetchData/useState 三件套；写操作用 `useMutation` + `onSuccess: invalidateQueries` 替换手写"提交成功后 fetchData()"。
  2. queryKey 规范写入组件目录：`['warehouse', <资源>, <过滤参数对象>]`，invalidate 用 `['warehouse']` 前缀兜底。
  3. 再迁 `system/` 各 Tab（纯读列表，机械替换）。
- **验收**：组件内不再有手写 loading state；翻页/筛选有缓存（30s 内返回不重新请求）；写操作后列表自动刷新。

### P1-2 读操作切 lib/api 直连，Server Actions 只留写（≈半天，依赖 P1-1）

- **问题**：客户端组件读数据走 `getMaterials` → Server Action（一次额外 HTTP POST 到自身）→ 后端；而 `lib/api/warehouse.ts` 里的 `fetchMaterialsClient/fetchStocksClient/fetchMovementsClient/fetchLocationsClient/fetchStocktakeClient` 五个浏览器端读函数全部无人调用。actions/warehouse.ts 291 行中 14 个是读包装。
- **步骤**：
  1. P1-1 迁移 useQuery 时，queryFn 直接调 `*Client` 变体（`lib/api/equipment-client.ts`、`production-client.ts` 已是同模式先例；迁移时验证浏览器 cookie 凭证链路在 `http-client.ts` 对客户端请求生效）。
  2. `actions/warehouse.ts` 删除全部读包装（保留页面 Server Component 初始取数所需的 server 端 fetch），只留 17 个写 action。
- **验收**：浏览器 Network 面板中 warehouse 读请求为 `GET /api/v1/warehouse/*`，不再出现 Server Action POST；`actions/warehouse.ts` 只含写操作。

### P1-3 OpenAPI → generated 类型契约（≈1 天）

- **问题**：`types/warehouse.ts` 512 行手写类型 + 手工字段映射，后端改契约前端无感知（宁夏同类问题被判为"类型契约半失控"）。`frontend/openapi.json` 已提交但只是死文件。
- **步骤**：
  1. 安装 `openapi-typescript`，新增 `scripts/generate-api.mjs`：优先读 `../backend/openapi.json`（后端启动时导出），否则 fetch `/openapi.json`；生成 `src/types/generated/schema.ts`。
  2. `package.json` 加 `"generate:api": "node scripts/generate-api.mjs"`。
  3. 收敛策略（不搞一次性重写）：新代码/新接口一律从 `@/types/generated/schema` 取类型；`types/warehouse.ts` 按模块逐步替换为 `Omit<generated[...]>` 派生（宁夏 `types/warehouse.ts:340` 已示范该模式）。
  4. 可选后续：CI 里重新生成后 `git diff --exit-code` 做契约漂移门禁（属 CI 改造清单，此处只留接口）。
- **验收**：`pnpm generate:api` 一键生成；至少 warehouse 一个资源的类型改为 generated 派生并通过 typecheck。

### P2-1 移除浏览器直连路径，统一相对路径走代理（≈半天）

- **问题**：`lib/api/warehouse.ts:56` 的 `CLIENT_API` 优先取 `NEXT_PUBLIC_API_BASE_URL`——配置后浏览器绕过 Next 代理直连后端（CORS、后端地址暴露、与宁夏"禁止 NEXT_PUBLIC_API_* 直连"的规范相悖）；本地 CI（`.github/workflows/ci.yml:30`）恰好注入了该变量，说明构建产物实际在直连。
- **步骤**：
  1. `lib/api/warehouse.ts`（及其他模块 client 文件同步检查）删掉 `NEXT_PUBLIC_API_BASE_URL` 读取，CLIENT 恒为 `''` 相对路径；server 端保留 `API_BASE_URL`。
  2. 删除 CI 中 `NEXT_PUBLIC_API_BASE_URL` 环境变量（ci.yml:30）；`.env.example` 同步注释说明浏览器一律走代理。
  3. 确认 `next.config.ts` rewrites/proxy 覆盖 `/api/v1/*` 与 `/uploads/*`。
- **验收**：构建产物 grep 无 `NEXT_PUBLIC_API_BASE_URL`；浏览器 warehouse 请求全部为同源相对路径。

### P2-2 危险操作确认文案规范核查（≈2 小时）

- **现状**：Confirm 已覆盖关键写操作（Location/Material/Movement/Stocktake/BitableTab），此项只做文案校准：确认框需含**对象 + 影响 + 不可恢复提示**（宁夏侧 `FeishuTablePage` 删除/同步的文案是现成范例）。
- **验收**：5 个删除/确认操作的 Popconfirm 文案逐个过一遍，达到"对象+影响"标准。

## 三、明确不做 / 暂缓项

| 项 | 理由 |
|---|---|
| `warehouseScope` 页面权限纯函数映射 | 宁夏该组件服务于其页面级权限体系（X-Dazah-Page-Key + page_permission_matrix），本地无此体系；本地 5 页规模 + `usePermission` 已够用。待本地落地页面权限（后端议题）时再评估 |
| AI 面板流式输出 | 宁夏侧自己也是一次性返回（Server Action），无流式可借鉴 |
| force-dynamic 清理 | 本地 warehouse 仅 1 处使用，宁夏"机械铺满"的问题在本地不存在 |
| 表格虚拟化 | 本地表均为服务端分页（page/page_size），数据量场景与宁夏 47 页大表不同，暂无必要 |
| 巨石组件重构 | 本地最大 411 行（`StocktakeBoard`），暂无风险；仅立约定：**组件超 400 行即拆**（对齐宁夏 300 行约定但考虑本地规模放宽） |

## 五、通俗版说明（给非前端同学）

先记住一个画面：**用户看到的网页是"前台"，存数据的服务器是"后账房"，中间还有个"中转站"（我们自己的网页服务器）**。

1. **装个"自动质检员"（P0-1 测试设施）**：现在改完代码只能靠人把页面点一遍检查。装上自动测试，就是请了个机器人质检员，每次改完代码它自动把"点删除、填表单、翻页"全过一遍，坏了当场喊停。
2. **加载失败要"说实话"（P0-2 失败态区分）**：现在拿数据失败时表格显示空白，管理员分不清"库里真没货"还是"网断了没加载出来"。改成：失败显示"出错了，点这里重试"，真没数据才显示"暂无数据"。就像超市货架：卖完了和"理货员还没补上"要标清楚。
3. **请个"数据管家"（P1-1 React Query）**：现在每个页面都手写一遍"去账房拿数据→显示加载中→存起来→翻页再拿"，抄来抄去容易错。React Query 把这些杂活全包了：代码变短、翻回看过的页面秒开、增删改完列表自己刷新。
4. **少绕一道手续（P1-2 读切直连）**：现在前台看数据要先报给中转站，中转站跑去账房问再带回来。直连的路早就修好了没用上。改完直接问，中转站只管"改数据"这种要登记签字的事。
5. **说明书从手抄换自动同步（P1-3 类型契约）**：前端的"数据长什么样"说明书是手工照着后端抄的，后端一改前端不知道，用户点出 bug 才发现。改成工具自动生成：后端一改，前端立刻报警。
6. **收好账房门牌号（P2-1 移除直连）**：现在有个配置会让浏览器绕开中转站直接连账房，账房地址谁都能看到。而发布脚本恰好配了它。改掉后所有人只走正门，账房地址不外泄。
7. **把话说全（P2-2 确认文案）**：删除弹窗从干巴巴的"确认删除？"改成"删除物料【XX】？名下还有 3 条库存记录，删了不能恢复"，防手滑。

一句话：**1 装质检员，2 失败说实话，3 请数据管家，4 少绕手续，5 说明书自动同步，6 收好门牌号，7 把话说全**。做了第 3 件，第 2 件基本顺带解决。
