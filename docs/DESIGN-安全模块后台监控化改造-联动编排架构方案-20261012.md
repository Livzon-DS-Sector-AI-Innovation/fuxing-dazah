## 0. 一句话定位

把安全模块从「**报告驱动的工具集合**」改造为「**事件驱动的后台监控编排系统**」：

- **飞书多维表格 = 唯一业务数据源**（单源权威，直读改造已把 14 域全部切到这条路上）；
- **机器人 = 工作流与业务交互的统一界面**（卡片即表单：通知、催办、审批、验收、问答全部在飞书内完成，不跳 Web）；
- **平台安全模块 = 后台监控者**（监听数据变化 → 判定 → 跨域串联生成单据 → 督办到闭环 → 全程留痕）。

一句话业务语义：**表格里发生任何事，平台立刻知道、判断要不要管、要管就生成单据并盯到闭环**。
样板链路（用户指定）：报警记录产生 → 自动生成隐患记录进行跟踪。

### 1.1 分层结构

```

│ 交互层  飞书机器人（卡片即表单）          Web 驾驶舱（监控+配置）    │
│         通知卡·催办卡·审批卡·验收卡·问答    规则运行流·督办大盘·时间线 │
├─────────────────────────────────────────────────────────────────┤

├─────────────────────────────────────────────────────────────────┤
│ 事件层  业务事件总线（双源：Bitable drive 事件 + 平台域事件）        │
│         幂等去重 · 回环防护 · 字段级过滤 · 兜底对账                  │
├─────────────────────────────────────────────────────────────────┤
│ 判定层  规则引擎（静态）· AI 审查插件（8 类，复用）· vision（复用）   │
├─────────────────────────────────────────────────────────────────┤
│ 数据层  Bitable 权威数据源（14 域直读底座 bitable_direct）          │
```

### 1.2 样板数据流：报警 → 隐患 → 闭环

```
值班人员在 Bitable 报警表补录"报警性质=真实报警"
  │ drive 事件（record_changed, 字段级）
  ▼
业务事件总线（去重/回环检查）→ emit alarm.confirmed
  ▼
联动规则引擎 R1「报警转隐患」
  ├─ 条件：报警性质∈{真实报警} 且 未标记"已转隐患"（幂等键）
  ├─ 动作1：隐患 Bitable 表创建记录（预填来源/描述/位置/部门/期限）
  ├─ 动作2：报警表回写"已转隐患"标记列（防重复，串行写）
  ├─ 动作3：督办状态机建档（责任人/期限/验收条件）
  └─ 动作4：通知卡发责任人 + 抄送安管（gate=notify_after 事后通报）
  ▼
隐患域既有链路自动接管：AI 定级 → 整改单直达 → 周三催办卡 → 复核销号
  ▼
全程 linkage_rule_runs 留痕（Web 驾驶舱可见整条链路时间线）
```

## 2. 六条架构原则

1. **Bitable 单源权威**：业务单据（含联动生成的单据）一律落 Bitable；平台 DB 只存三类表——配置、留痕审计、派生缓存（快照/TTL）。与仓储 V3.0「Base 权威 + 本地派生镜像」同构。
2. **事件与查询分离**：drive 订阅的职责从「镜像消费者」（直读改造已废）**翻转**为「业务触发器」——事件只读不写镜像；数据消费（列表/统计/Agent 问答）继续走直读。两类角色互不干扰。
3. **机器人优先（card-as-form）**：凡面向责任人的动作（整改、进展、验收、确认）做成可交互卡片，卡内闭环；Web 不做一线操作台。
4. **平台是编排者不是数据主**：平台的状态（督办进度、规则运行）是 Bitable 数据的派生视图；跨域单据关联靠「源 record_id 幂等键 + 回写标记列」在 Bitable 侧可追溯。
5. **红线代码化（gate 机制）**：每条联动规则强制声明动作门——`notify_after`（自动执行+事后通报）/ `approval_before`（先飞书审批后执行）。处罚、停工、通报类动作一律 `approval_before`，对应文档"Agent 不拥有结论性权力"。
6. **沿用工程铁律**：开关闸门（每条规则独立开关默认关）、串行写+0.5s、批量读禁逐条、AI 调用全审计（ai_call_audits）、双路径验收、幂等键全覆盖。

## 3. 核心组件设计

### 3.1 业务事件总线 `service/event_bus/`（新建）

**职责**：把两类源头归一为标准业务事件，供规则引擎订阅。

| 件 | 设计 |
|---|---|
| 接入 A：Bitable drive 事件 | 复用 `feishu/event_client.py` WS 长连接与 `@on_event` 注册表；既有 17 个 `bitable_record_changed_v1` handler **保留原职责**（RAG 入库/hazard_id 流程/ehs_change 镜像等不退订域），在处理末尾追加 `emit()` 钩子；直读后退订的域（hazard/special_op/fire_alarm/central_alarm/cert/chemical/key_risk_op/contractor_admission/emergency_drill）**以新角色恢复订阅**——新 handler 是纯发射器（只解析变更、emit 事件，零镜像写入），镜像闸门保持关闭 |
| 接入 B：平台域事件 | 平台侧状态机与任务（作业票审核结果、事故 CAPA 状态、EHS 变更 commission、爬虫 update、外部审计导入）在关键节点调用 `event_bus.publish()`；不依赖 Bitable 的业务同样能进联动 |
| 事件信封 | `{event_id, source: bitable\|platform, domain, table_id, record_id, op: created\|updated, changed_fields[], actor: human\|platform, occurred_at, trace_id}`；`actor=platform`（平台自身回写）默认不进规则引擎——即回环防护的第一道闸 |
| 幂等 | `event_id` 去重窗口（Redis/DB）+ 规则执行幂等键（见 3.2）；事件重放安全 |
| 兜底对账 | **定时巡查器**兼事件补偿：小时级直读扫描各域近 2h 窗口，与已处理 event_id/标记列比对，漏掉的变化补 emit。顺带把 S12 报警从"日级拉取"升级为"小时级监控" |
| 开关 | `SAFETY_EVENT_BUS_ENABLED` 总闸 + 每域 `SAFETY_<DOMAIN>_EVENT_EMIT_ENABLED`（与既有镜像闸门命名同族但独立） |

**验收口径**：事件不写任何镜像表（零写入探针）；人为断开 WS 30 分钟，巡查器补齐漏发事件（对账脚本）。

### 3.2 联动规则引擎 `service/linkage/`（新建，后台监控的心脏)

**规则模型**（一期代码声明式注册，形如 bitable_config/REGISTRY）：

```python
LinkageRule(
    id="alarm_to_hazard",
    domains=["fire_alarm", "central_alarm"],          # 业务域标签（S 模块映射见拼图文档附录）
    trigger=EventTrigger(domain="fire_alarm", op="updated",
                         field_filter=["报警性质"]),    # 字段级触发：等关键字段就绪再判
    condition=RuleCondition(
        static=alarm_is_real,                          # 静态规则
        ai=ai_config 场景引用,                           # 可选 AI 判定（走 ai_audit）
        confidence_gate=0.8),                          # 低于阈值转人工确认卡
    actions=[
        CreateRecord(target="hazard_bitable", field_map=..., dedup="alarm_to_hazard:{record_id}"),
        Writeback(source_marker="已转隐患"),
        CreateSupervision(deadline_days=7, verify="rectification_review"),
        SendCard(template="hazard_created", to="责任人+安管"),
    ],
    gate="notify_after",          # 或 approval_before（红线动作）
    enabled=False,                # 默认关
)
```

| 件 | 设计 |
|---|---|
| 执行器 | 规则匹配 → 异步执行队列（复用 scheduler 基建）；写 Bitable 串行 + 条目 0.5s；动作失败重试 1 次后告警（复用 failure_notifier 模式） |
| 判定 | 静态规则优先；AI 判定走既有插件管线 + `ai_config` 场景管理 + `ai_audit` 全审计；置信度不足自动降级为人工确认卡（不静默放弃） |
| 幂等 | 每条动作声明 `dedup` 键（通常=源 record_id）；已存在则跳过并记录 |
| 留痕 | 新表 `linkage_rule_runs`（rule_id / 触发事件快照 / 判定输入输出 / 各动作结果 / trace_id）——**这是后台监控的运行日志，也是 S16 调查时间线还原的数据源** |
| 配置 | 一期代码声明（可测试可审计）；三期视需要评估 Web 配置化 |

### 3.3 通用督办状态机 `service/supervision/`（从 hazard 抽取泛化）

**现状**：仅隐患域有真闭环（周三催办卡可卡内提交进展 + 周四督办通报 + 三级复核），S7 随访/S10 作业票各有一套简化版——三处复制已经出现，是抽通用件的时机（同 bitable_direct 教训）。

**对象模型**：

```
SupervisionCase {
  domain, source_record_id(Bitable), source_marker_column,
  responsible(责任人), supervisor(复查人),
  deadline, state,
  state 机: notified → in_progress → submitted → verified → closed
            逾期: overdue → escalated(呈报厂领导/飞书审批)
  reminders: T-3d 提醒 / T-0 当天 / T+1 催办 / T+3 升级（策略可配）
  verify: 字段回填核验(静态) | 人工验收卡 | AI 复核(rectification_review)
}
```

| 件 | 设计 |
|---|---|
| 数据落位 | 平台 DB 权威（留痕类）；Bitable 侧只回写业务要求的可见列（如「催办状态」「逾期次数」），回写走既有串行+防回环手法 |
| 卡片 | 催办卡（复用 `progress_card.py` 一卡一单可提交模式模板化）、验收卡、升级呈报卡 |
| 升级 | 呈报卡直达厂领导；二期接飞书审批流后，升级动作可挂审批 |
| 接入面 | 规则引擎动作之一（CreateSupervision）；既有 hazard 催办/督办**暂不回改**，新域先用通用件，稳定后单票收敛（同 hazard_direct 不回改先例） |

**产品语义**：文档要求"没有任何一张 Agent 发出的单据会不了了之"——督办状态机就是这句话的代码化。

### 3.4 机器人卡片工作台（feishu/ 强化，不新建）

| 卡片类型 | 语义 | 现状基础 |
|---|---|---|
| 通知卡 | 单向告知（日报、生成单据通报） | notification.py 群卡/私卡已有 |

## 5. 样板链路详设：R1 报警转隐患（用户指定场景）

**前置事实**：报警表由值班人员补录（报警性质/处置情况为人填字段）；AI 原因分析在 17:00 日报任务批量做——所以事件触发时用**人填字段做静态条件**，不等 AI；AI 结论出来后可二次规则增强。

| 步骤 | 设计 |
|---|---|
| 1 订阅 | fire_alarm/central_alarm 以"业务触发器"角色恢复 drive 订阅（新 handler 纯 emit；镜像闸门保持关闭，事件零写镜像） |
| 2 触发 | record_changed + changed_fields 含「报警性质」→ emit `alarm.updated`；巡查器每小时直读近 2h 窗口对账补漏 |
| 3 条件 | 静态：报警性质 ∈ 真实报警清单（可配枚举）且「已转隐患」标记列非真；模糊值（误报/测试/待确认）不触发 |
| 4 动作 | ① 隐患表建行：来源=报警联动、描述=报警位置+类型+时间、责任部门=表→部门映射（bitable_mapper 既有）、整改期限=7d（可配）；幂等键 `alarm_to_hazard:{record_id}`，建行前查重 ② 报警表回写「已转隐患」=是（防人工重复转）+隐患 record_id ③ 督办建档（验收=AI 整改初审+人工复核）④ 通知卡：责任人 + 安管抄送，附报警原文与依据条款（RAG 取） |
| 5 接管 | 隐患域既有链路零改动接管（AI 定级→整改单→催办卡→督办通报→三级复核） |
| 6 兜底 | 建行失败重试 1 次→告警安管+人工兜底单；处置中报警（性质后续修正）允许幂等重入 |
| 7 验收 | 双路径：人工在表格手转一条 vs 规则自动转一条，字段逐项一致；零误转（误报枚举抽测）；断 WS 30min 巡查器补齐；回写探针证明事件路径除标记列外零写入 |

## 6. 数据落位原则

| 数据 | 落位 | 说明 |
|---|---|---|
| 业务单据（隐患/整改/督办可见列/联动生成单据） | **Bitable 权威** | 联动生成的单据也写 Bitable（数据源单一，现场可在表格看到全貌） |
| 配置（规则/开关/督办策略/点位） | 平台 DB | 并入 app_config 体系 |

## 8. 非功能铁律（沿用既有手法，逐条可验收）

1. **幂等**：事件去重窗口 + 每动作 dedup 键；任意事件重放 N 次结果一致（单测断言）。
2. **回环**：actor=platform 事件不进规则引擎；平台回写打 sync_ignore；回写只写声明列（零写入探针）。
3. **写约束**：Bitable 同表串行 + 条目 0.5s；批量读禁逐条 get_record。
4. **审计**：判定与动作全量落 linkage_rule_runs；AI 调用全走 ai_call_audits。
5. **红线**：处罚/停工/通报类动作 engine 强制 approval_before；审批结果回写留痕。
6. **兜底**：巡查器小时级对账补漏；WS 断连自愈（既有）+ 断连告警。
7. **开关**：总线总闸 + 每域 emit 开关 + 每规则开关，全默认关；关=行为与今天完全一致。
8. **质量**：ruff 改动行 clean；mypy 对照基线零新增；双路径/对账脚本归档 scripts/tmp。
