# DESIGN — 安全设备设施管理：三台账校验闭环 + 特种设备监控（2026-10-19）

## 0. 一句话

在 facilities 占位域（registry/domain_pages/前端骨架已预留）上接入**三张既有台账**（安全附件/消防器材/特种设备的多维表格均已存在——2026-10-19 用户确认，登记连接+字段映射即接入，**不新建表**），新建通用**「校验任务」实体**实现「到期前派任务给责任部门 → 责任人**在多维表格里更新校验时间** → 平台检测锚点前移**自动闭环**」（同类型任务**合并为滚动批次卡**通知与追踪——同批安全阀校验/灭火器换药一卡盯到底，不逐条发送）；特种设备另建**锅炉数据监控链**（数据来源唯一=飞书群人工发送消息，采集解析统计整理成时序快照 + 阈值规则引擎 + 即时报警 + 趋势）。

## 2. 总体架构

```
飞书 Bitable 既有三张台账（人维护，唯一事实源，不新建表，连接位留空待登记）
  ├─ 安全附件台账   ─┐
  ├─ 消防器材台账    ├─ 列映射适配层（实际列名→标准字段，缺列降级）
  └─ 特种设备台账   ─┘   → 直读 Reader（TTL 300s）→ 到期引擎（纯函数）
        └─ record 变更事件 + 每日对账 → 闭环检测（校验时间前移 → 自动关任务）
                              │
      ┌───────────────────────┼────────────────────────┐
      ▼                       ▼                        ▼
 校验任务编排+闭环检测   监控规则引擎                 展示层
 （派发/幂等/盯表）    （阈值/去抖/静默）     facilities 页三 Tab

 （DB 状态机+事件流）    （DB 报警记录+处置闭环）    + 监控/趋势 Tab
      │                       ▲                        │
      │              锅炉群消息采集 worker               │
      │     （拉群消息→模板/AI 解析→统计整理落快照）      │
      │     telemetry_snapshots（时序快照+原消息留痕）    │
```

三台账共用一套任务机制（`biz_type` 区分），状态机、派发编排、卡片交互零分叉；锅炉监控独立成链但复用通知与趋势底座。

## 3. 数据模型

### 3.1 Bitable 既有台账接入（三表已存在，不新建，连接位留空）

用户确认（2026-10-19）：安全附件/特种设备/消防器材的台账多维表格均已存在。设计从「建表」改为「**接入适配**」：

1. **registry 登记**：`facilities` 域 kinds 扩为 `accessory_ledger` / `fire_equipment_ledger` / `special_equipment_ledger`（原 `equipment_ledger`/`inspection_record` 保留）；**default_connection 一律留空**，拿到实际 app_token/table_id 后经 bitable 配置页（或 registry 默认值）登记，页面统计即活
2. **列映射适配层（关键设计）**：不要求既有表改结构。每台账一份映射配置——先精确匹配常见列名（「下次检验/校验/检查日期」「责任部门」「设备/附件/器材编号」「状态」等），未命中再表头关键词模糊匹配（抄危化品表头驱动思路），映射到下述标准字段；**实施第一步=直读三张表实际结构，生成映射初稿与用户核对**
3. **锚点必备校验与降级**：到期督办锚点优先取「下次日期」列；缺则用「上次日期+周期」运行时推算（只读不回写）；两者都缺的行进「信息不全清单」（速递格子 ⚪ 口径倒逼补录，抄外来人员保险做法）。责任部门列缺失→派发解析失败即告警，不静默丢任务
4. **闭环不回写**（2026-10-20 用户拍板）：校验时间由责任人直接在多维表格里更新，平台只读检测（见 §4.3），**不做任何写回**；「检验记录」表若存在则仅作直读展示，同样不写
5. **未接入态运行语义（2026-10-20 用户拍板：本次开发所有数据源连接一律留空，待确认后接入，其余功能全量交付）**：连接未登记时——页面走既有三态信封 not_connected（不报错不假数据）；每日派发/升级任务检测到无连接则以 `no_source` 跳过并如实留痕进任务运行中心（**严禁假 success**，吸取四期调度空跑假留痕事故教训）；锅炉群 chat_id 未配置时采集任务同样 no_source 跳过。连接登记后零改码即插即用

标准字段口径（列映射的目标端，实际列名以三张表真实结构为准）：

- 通用：编号（唯一）/名称/类别/位置/责任部门/责任人/上次日期/周期（月）/**下次日期（督办锚点）**/状态
- 消防器材特有：换药/维修到期、报废到期（辅助预警，可空）
- 特种设备特有：注册代码、检验类别、检验机构、**接入监控（是/否——是=进入锅炉监控链）**
- 缺列降级：锚点列缺→「上次+周期」推算，再缺进不全清单；编号缺→该行不可派任务；状态列缺→视为全部在用；责任部门缺→退化为部门负责人解析，失败告警

## 4. 校验任务闭环（需求①②的核心；2026-10-20 用户拍板口径）

**闭环口径：任务派发以多维表格数据为准；责任人直接在多维表格里更新校验时间（上次/下次校验日期），平台检测到锚点前移即自动关闭任务。平台不回写台账、卡片不收表单——多维表格既是唯一事实源，也是唯一的闭环入口。**

### 4.1 状态机（无中间态，闭环完全锚定表格数据）

```
issued ──表格锚点前移（事件/对账检测到）──▶ closed（终态）
  │
  ├─ 台账行删除/设备停用 → cancelled（对账自动）
  └─ 今日 > due_date 且仍 issued → 逾期（派生口径，不改状态）→ 升级通知
误关可 reopen（管理员，留痕）；closed_trigger 区分 event/poll/manual
```

**闭环铁律**：closed 的前置条件是**台账行锚点已前移**——下次校验日期 > 任务 due_date，或上次校验日期出现/更新为派发之后的新值。责任人不更新表格里的校验时间，任务永远关不掉；管理员 manual 关闭仅作极端兜底，必填原因并单独留痕。

### 4.2 派发编排（SCHEDULED_JOBS 新增「设施校验任务派发」，每日 08:30（2026-10-20 拍板），补发窗口 12:00）——以多维表格为准

1. strict 直读三台账（绕过 TTL 强刷）
2. 筛选：状态=在用 且 锚点日期 ≤ 今日 + lead_days（默认 30，按 biz_type 可配；特种设备定期检验建议 45）
3. 幂等：已有 (biz_type, ledger_key, due_date) 且 status=issued 的跳过
4. 建任务（冗余快照落库，含**锚点原值 anchor_at_dispatch** 作闭环判定基准）→ 责任人解析：台账 owner person 字段优先 → `IdentityResolver.resolve_responsible_person` + `responsible_mapping` 归口兜底
5. 通知（**合并发送，绝不逐条轰炸**，机制详见 §4.5）：按部门合并为**滚动批次卡**，@mention 相关责任人，卡内按任务分组分区列明细，附多维表格跳转指引；同时当日速递格子新 key `facility_check`（全厂口径：逾期 X / 30 天内到期 Y / 待闭环任务 Z）
6. 对账 reconcile：台账行已删/停用 → 对应 open 任务自动 cancelled + 事件留痕

### 4.3 闭环检测（核心逻辑：盯表格变化，双通道保最终一致）

- **实时通道=bitable record 事件**：facilities 域 registry `subscribe="record"` 已有，复用 `bitable_config/event_hooks` 订阅框架与 at-least-once 去重；handler 收到台账行变更 → 定位该行 open 任务 → 跑锚点前移判定 → 命中即自动 closed（closed_trigger=event）+ 批次卡对应条目刷新为绿
- **兜底通道=每日派发任务顺带对账**：事件丢失/断线期间的变化，由次日扫描全部 open 任务比对「当前行锚点 vs anchor_at_dispatch」补闭环（closed_trigger=poll）——事件只做加速，对账保证最终一致
- **判定规则**（纯函数，today 可注入）：下次日期 > 任务 due_date（已滚动到新周期），或 上次校验日期出现/更新为 ≥ 派发日期 的新值 → 判定校验已完成 → 自动 closed；责任人只改了无关列（名称/备注等）→ 任务保持 issued
- 行删除/状态改停用 → cancelled；误闭环 → 管理员 reopen（事件留痕，任务回到 issued）
- 两种通道闭环后统一动作：任务置 closed + 事件留痕 + **刷新所属批次卡**（条目变绿、分组进度行更新、全闭环时卡片置绿归档，见 §4.5）

### 4.4 逾期升级（SCHEDULED_JOBS 新增「校验任务逾期升级」，每日 17:10）

issued 且今日>due_date → remind_count+1，**同样按部门合并一卡** @部门负责人 + 安管（`ALERT_NOTIFY_OPEN_ID` 口径），汇总本部门全部逾期项，不逐条私发；逾期>7 天进速递格子红档督办口径。

### 4.5 合并通知与批次追踪（2026-10-20 用户拍板：同类型任务合并发送，不逐条轰炸）

**分组键** = 部门 × 任务分组（类别标签 × 工作性质）。类别标签映射自台账类别列（安全阀/压力表/灭火器/消火栓/锅炉/压力容器…，未识别归「其他」桶，不因未知类别拆卡）；工作性质（task_subtype）由触发锚点决定：校验/检查/**换药到期/报废更换**（消防特有锚点）/定期检验。同一批安全阀校验、同一批灭火器换药各自成为一个分组，永远不按单件发消息。

**滚动批次卡**（一张卡盯到底，学督办通报 upsert_daily_digest 的原地 PATCH 模式）：

- 每部门至多一张**进行中**批次卡（`facility_notice_batches` 部门唯一 open）：当日派发时该部门无进行中卡 → 新发建批次；有 → 新任务**并入原卡原地 PATCH** 追加分组分区，不另发新卡（避免同部门卡片随天数堆积）
- 卡内结构：头部进度行（本部门待闭环合计 X 件 · 已闭环 Y）→ 按分组分区（「安全阀·校验 6 件：已闭环 2」+ 可折叠明细：设备/位置/到期日/剩余天数/状态）→ 尾部 @责任人 + 多维表格跳转指引（「校验完成后请在表中更新校验时间，任务将自动闭环」）
- 闭环检测命中 → 对应条目变绿 + 分组进度行原地刷新（不发新消息）；该部门全部闭环 → 卡片头部置绿「✅ 全部完成」，批次归档停更；此后该部门再有新临期任务 → 新开一张批次卡
- 逾期升级催办同样按部门合并（§4.4），并引用/刷新批次卡而非另起炉灶
- 全厂跨部门口径由速递格子 `facility_check` 承担（分桶计数 + 逾期 Top 清单），不重复发部门级明细
- 通知侧防刷屏兜底：批次卡 PATCH 频率限流（如 5 分钟窗口内合并刷新），避免事件风暴下连环更新卡片

## 5. 特种设备监控（锅炉，需求③）

### 5.1 数据接入：飞书群人工消息（用户拍板，目前唯一来源）

现状：无 DCS/PLC/modbus/数采通道。用户确认（2026-10-19）：设备监控数据目前只有一种来源——**飞书群里人工发送的信息**，采集后统计整理。

```
指定锅炉群（chat_id 可配）
  └─ 采集 worker「锅炉群消息采集」（interval，默认 5 分钟）
       ├─ im 消息 API 增量拉取（since 上条 message_id，分页，重启安全）
       ├─ 范围：文本消息 + 图片/文件（抄表截图、报表）
       ├─ 解析分层：
       │    ① 模板解析（可配正则/关键词模板，如「汽压 0.8 / 水位 -30」多行抄表文本）——确定性优先
       │    ② 未命中模板 → AI 解析（文本结构化 / 图片 OCR+视觉抽数——meter 报告匹配与视觉单据识别链路已有先例）
       ├─ 统计整理 → 幂等落 telemetry_snapshots（raw_message_id 留痕，可追溯回原消息）
       └─ 解析失败 → 标记 pending_review 不丢弃，人工补录页面兜底 + 失败计数告警
```

- **权限前提**：机器人已在目标群 + `im.message` 读取权限（开放平台操作，流程同当初 sheets 直读授权）；不走事件订阅——轮询 5 分钟已满足「发现异常立即报警」（≤5 分钟），且不增加事件通道运维
- **消息→设备归属**：模板里带设备编号优先；未带时按发送人/班次映射默认设备（映射配置，P5 小项拍板）
- **无关消息**：模板与 AI 都未抽出数值的闲聊消息自然跳过（不计为解析失败）
- **抽象保留**：采集层收敛为 `TelemetrySourceAdapter` 接口（群消息实现为一期唯一实现）；将来锅炉上了数采出口，加 HTTP/网关实现，快照表与判定报警链全不变

### 5.2 监控编排（interval 任务「锅炉群消息采集与判定」，默认 5 分钟，参照 HAZARD_AI_POLL_TASK 模式）

1. 采集 worker 拉新消息 → 解析 → 幂等落 `telemetry_snapshots`
2. 对**新增快照**跑规则引擎纯函数 `TelemetryRuleEngine.evaluate(history, rules, now)`：超上限/低于下限/**变化率超标**/**连续 N 点异常**（默认连续 2 点，防单点毛刺）
3. 命中 → **立即报警**（当轮即发，不等整点）：
   - 飞书群卡 @安管 + 责任部门负责人（目标群 app_config 可配）
   - `telemetry_alarm_records` 落 firing（dedupe_key + 静默窗口默认 30 分钟，同源异常不刷屏）
   - 当日速递格子（并入 `facility_check` 或独立 `telemetry_alarm` key）
4. 报警处置闭环：firing → acked（值班确认）→ resolved（处置说明），Web API + 卡片按钮，处置结论留痕——与校验任务同款「不处理完不关闭」语义
5. 前端特种设备 Tab「监控」：实时读数卡（每设备每指标最新值+状态色）/ 报警列表（处置操作）/ 趋势图（复用危化品趋势链：snapshots 按日/按小时序列 + ui-kit charts）/ 解析失败待补录列表

### 5.3 阈值规则（一期代码默认 + DB 覆写）

默认按设备类别给典型规则（锅炉：汽压上下限/水位上下限/炉膛温度上限…），`app_config` 键 JSON 覆写（设备级>类别级>代码默认）。页面化管理二期再议（拍板点 P6 附带）。
