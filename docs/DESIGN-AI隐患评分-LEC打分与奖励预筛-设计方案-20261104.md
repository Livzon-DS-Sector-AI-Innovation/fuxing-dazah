## 一、背景与制度依据

制度 §10「事故隐患上报奖励机制」现状：打分完全由评选小组**每两个月人工逐条**进行，预选靠健康安全部门人工筛选（§10.1「根据隐患整改难易程度、隐患事故风险等级筛选出优质隐患」），无系统支撑。员工每人每月 ≥2 条上报（§4.6），两月窗口存量约千条级，人工预筛负担重且标准漂移。

制度给出的可数字化标尺：

| 标尺 | 制度出处 | 内容 |
|---|---|---|
| **LEC 打分** | §10.3 | D = L×E×C×X（四维档位乘积，区间 [14.7, 100]） |
| **奖励门槛** | §10.4 | 特等 ≥55 分（1名/800元）、一等 ≥45 分（2名/600元）、二等 5名、三等 10名 |
| **优质四标准** | §10.2 | 符合重大隐患判定（含安全零容忍）/ 重大合规风险 / 普遍性未辨识风险 / 改正后明显提升安全效益 |
| **排除规则** | §10.5 | 安全管理人员查出的不参评；同一隐患未闭环期间重复提出不参评；打分须匿名（隐藏提出人姓名及部门） |
| **H/M/L 风险分级** | §4.5 + 附件四/五 | 按分类条目对照定 高/中/低风险（与法定「一般/重大」分级并存，两套体系） |
| **重大隐患判定** | 附件一（试行20条）/ 附件二（AQ 3067）/ 附件三（甘肃省办法） | 命中即属重大隐患，同时是优质评选第一条标准 |

**打分档位表（制度原文，评分模型唯一权威）：**

| 维度 | 档位→分值 |
|---|---|
| L 造成事故的可能性 | 非常可能 2 / 可能 1.5 / 可能性小 1 |
| E 工作人员接触隐患频率 | 连续接触 2 / 每天几次 1.8 / 每周 1.6 / 每月 1.4 / 每年 1.2 / 很少接触 1 |
| C 可能造成事故的后果 | 灾难 25 / 非常严重 22 / 严重 20 / 一般 18 / 轻微 15 |
| X 排查难度 | 难 1 / 较难 0.99 / 一般 0.98 |

## 二、系统现状（摸底结论）

- **运营核心 = `service/hazard_direct/` 四轮直读架构**（Bitable 直读直写、不落库）：
  - ① `ai_analysis.py`：判据 `隐患分类（AI）isEmpty` → 下缺陷图 → 多模态识别+RAG → 写回 7 字段+督办等级；失败语义=不写任何 AI 字段，下轮自动重试；
  - ② `review.py`（AI 整改初审）、③ `supervision.py`（督办）、④ `bulletin_watch.py`（通报值守）；
  - 字段常量/判据/写回全在 `bitable_repo.py`（`write_ai_analysis` @584，7字段+F_SUPERVISION）。
- **AI 插件四件套模式**（标杆 `ai_urs_review/`：*「评分/等级/结论由代码计算，AI 辅助摘要」*，低温度 0.05 + 强类型输出 + 规则兜底）；现役识别插件 `ai_hazard_identification/`（`AIHazardIdentifier`，被①轮调用）。
- **AI 通道**：`create_ai_service("vision"/"text")` + `ai_audit_scope(scenario=…)` 自动落审计表；`thinking_policy.py` 中 `hazard_identification` 属 FORCE_OFF（thinking 会吃满 max_tokens 截断，URS 实测教训）。
- **前端**：`HazardLedgerPage.tsx`（/safety/hazard-ledger）事故隐患台账，直读透传 Bitable 字段。
- 本地 `hazard_reports` 镜像表为旧路径遗留，直读化后不再承载数据；R1 报警联动的隐患也写 Bitable，天然进入同一评分链。

## 三、目标与不做

**做：**
1. 每条新上报隐患由 AI 自动**预打分**：L/E/C/X 四维档位+理由、总分 D、H/M/L 风险等级、重大隐患判定命中条目、优质四标准勾选——一次调用全出。
2. **公式/门槛/排除全部代码化**（对标 URS 模式）：AI 只选档位，D 值、奖项门槛、参评资格由代码判定，杜绝算术漂移。
3. 奖励预筛：按评选窗口（两月）聚合的**预筛清单**（排序+排除过滤+匿名化脱敏）。
4. 台账展示：风险分列 + 评分详情。

**不做（一期）：**
- AI 分数**不直接决定奖励**——制度要求评选小组人工打分，AI 分仅为预筛排序与参考；
- 不改写人工「隐患级别」字段、不动督办等级计算链；
- 不做评分历史落库（直读直写，重评=清空表内分值列触发重跑）；
- 评选工作台（打分录入/RD08 记录表导出）留二期。

## 四、评分模型（制度数字化）

### 4.1 计算与判定（全部在 `rules.py`，代码权威）

```
D = round(L × E × C × X, 1)          # 档位分值唯一来源为枚举表，AI 无权给裸数字
奖项门槛：D ≥ 55 → 特等奖候选；D ≥ 45 → 一等奖候选；其余按 D 降序入二/三等池
优质标记：四标准任一勾选 且 D ≥ 45 → 「优质候选」（预筛默认过滤条件，可放宽）
```

### 4.2 排除规则（代码，参评资格）

| 规则 | 判定 | 输出标记 |
|---|---|---|
| **非员工自查上报** | 检查类别/来源非员工日常上报——R1 报警联动生成、外审通报源、专业/综合检查记录均不属「一线操作人员自查」（§10.5），按检查类别字段过滤（具体选项值实施时核对台账） | 不参评-非员工上报 |
| 安全管理人员查出 | 检查人员部门 ∈ 安全序列清单（健康安全环保部/EHS部/安全序列，**清单可配**，P5 拍板初值） | 不参评-安全管理人员 |
| 重复上报 | 同描述规范化 hash 且台账内存在未闭环同 hash 记录 | 不参评-重复上报 |
| 信息不足 | AI 判 uncertain（复用 defect_substance 语义） | 待定-人工复核 |

误报兜底：排除标记只作预筛默认过滤，清单上保留「显示被排除项」开关，最终资格由健康安全部门人工确认（制度 §10.1 预选权在其手上）。标记**不写入 Bitable**（无奖励预筛列，P2 已拍板），仅在预筛清单端点响应中输出。

### 4.3 H/M/L 与一致性软校验

H/M/L 由 AI 按**附件四/五分类对照表**直接判定并引用条目（制度无 D→H/M/L 映射，不做硬换算）。代码做软校验：`D ≥ 45 而 band=L` 或 `D < 25 而 band=H` → 评分说明追加「⚠档位与分值不一致，建议人工复核」，不强制改写。

### 4.4 重大隐患判定命中

AI 对照附件一/二/三输出 `{hit: bool, clauses: ["附件一·五", …]}`。命中后：评分说明醒目标注 + 前端标红 + 预筛清单置顶；**不改**「隐患级别」人工字段、**不动**督办链（P4）。

## 五、架构与代码落点

### 5.1 新模块 `backend/app/modules/safety/ai_hazard_scoring/`（四件套）

| 文件 | 职责 |
|---|---|
| `schemas.py` | `LikelihoodEnum`(3档)/`ExposureEnum`(6档)/`ConsequenceEnum`(5档)/`DifficultyEnum`(3档)——枚举值=制度分值；`HazardScoringInput`（description/hazard_type/hazard_category/hazard_level/major_hazard_basis/department——**全部来自①轮已写回的识别结果**）；`HazardScoringOutput`（四维档位+各一处理由、band_HML+对照条目引用、major_hazard{hit,clauses}、quality_criteria 四布尔+理由、summary≤120字；**不含 total_score——总分代码算**） |
| `rules.py` | `compute_total()`、`award_threshold()`、`eligibility()`（三条排除）、`band_consistency_check()`、枚举校验（非法档位丢弃，对标①轮 `_validate`） |
| `prompts.py` | 制度档位表全文 + 附件四/五按 **13 类别裁剪的 H/M/L 对照精简表**（附件全文太长，按 `hazard_category` 13 枚举各挂相关条目）+ 附件一/二条目号索引 + 匿名要求（输入不含提出人姓名/部门字段）+ JSON 输出契约 |
| `plugin.py` | `AIHazardScorer(ai_service).score(input)`；温度 0.05；`ai_audit_scope(scenario="hazard_scoring", resource_type="hazard", channel="system")` |

### 5.2 接入 hazard_direct —— 独立⑤轮（P1 推荐）

新增 `service/hazard_direct/hazard_scoring.py`，注册为引擎 interval 任务（对齐①~④的四轮模式，`scheduled.py` 加一个 `_run_hazard_scoring_round`）：

```
判据：隐患分类（AI）isNotEmpty AND 评分结果 isEmpty
  （=①轮识别已完成、评分尚未做过；重评运营语义=清空「综合得分」列，与「清空分类重跑识别」习惯一致）
链路：search → per-record 锁 → 纯文本 AI 调用（无图，输入即①已写回的识别结果）
  → rules 校验/计算 → 写回 4 列 → 释放锁
失败语义：不写分值列 → 下轮重试（复用①的模式）
```

**依赖方向**：评分消费①的识别结论（分类/级别/判定依据）去对照附件四五——识别结论正是对照表的索引键，这是质量最优的依赖方向；且文本调用成本低、失败隔离、不动①的稳定性。

### 5.3 Bitable 新列（用户建列，2 列，P2 已拍板 2026-11-04）

| 列名 | 类型 | 写入方 |
|---|---|---|
| 评分结果 | 数字（1 位小数，D 值，可排序/可筛选） | ⑤轮 |
| 评分说明 | 文本（H/M/L + 四维档位与理由摘句 + 重大判定命中 + ⚠不一致提示） | ⑤轮 |

风险等级 H/M/L 不单列，并入评分说明首部；**奖励预筛/参评资格不落表**——预筛清单端点实时计算（§4.2 排除规则），仅在响应中输出标记。
`bitable_repo.py` 增 `F_SCORE/F_SCORING_NOTE` 常量、COND_SCORING_PENDING 判据（评分结果 isEmpty）、`write_scoring()` 写回函数（复用 `write_serial` + 进程写锁）。

### 5.4 前端与 API

- `HazardLedgerPage.tsx`：加「风险分」列（D 值 + H/M/L 色点：H红/M橙/L蓝）；行展开/Drawer 加「AI 评分」块（四维档位条+理由+判定依据引用+奖励预筛标记；重大命中标红）。
- `api/hazards.py` + `page_query.py`：直读透传 2 个新字段（评分结果/评分说明）。
- 预筛清单端点（一期核心交付）：`GET /hazards/award-shortlist?from=&to=` —— 两月窗口聚合，按 D 降序、默认滤除不参评、**响应脱敏**（去 discovered_by_name/检查人员，对齐制度匿名打分要求），返回门槛分档统计。
- 速递格/驾驶舱消费：二期可选（高分新隐患提示）。

### 5.5 不需要 DB 迁移

直读直写模式，无新表无新列；`thinking_policy.py` 注册 `hazard_scoring` → FORCE_OFF（结构化抽取，同 hazard_identification）。

## 六、测试与验收

1. **单测**（新 `tests/test_ai_hazard_scoring*.py`）：档位→分值映射、D 计算（边界 14.7/100）、门槛判定、三排除规则（含部门清单匹配/hash 去重）、band 一致性软校验、非法档位丢弃、写回 payload 组装、⑤轮判据与失败重试语义（mock Bitable）。
2. **prompt 线质量抽检**：取台账近两月已人工定级隐患 ≥30 条回放打分，四维档位与人工 H/M/L 对照，一致率目标 ≥70%（LEC 人工无基线，首检建立基线）。
3. **真机冒烟**：新建一条上报 → ①轮识别写回 → ⑤轮打分写回 2 列 → 台账页展示 → 清空「评分结果」→ ⑤轮重评。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 附件四五对照表塞满 prompt 撑爆上下文 | 按 13 类别裁剪精简表（每类 ≤8 条典型），条目号引用可追溯 |
| AI 档位漂移（同类隐患给不同档） | 低温度 + 对照表锚定 + 每维强制一句理由；抽检基线持续校准 |
| 排除规则误伤（如安全员以个人身份上报） | 标记可被人工推翻（清空奖励预筛列重算/清单上手动恢复）；默认过滤带开关 |
| X 维（排查难度）语义最虚，AI 易恒选「一般」 | prompt 中明确 X=「该隐患被日常排查发现的难易」并给正反例；抽检盯该维分布 |
