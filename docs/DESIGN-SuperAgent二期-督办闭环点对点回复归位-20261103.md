## 0. 一句话定位

责任人在群里催办话题下回一句「已安排明天施工」，系统**自动知道这话属于哪条隐患**：归位到对应督办任务、把回执原文追加进 Bitable「目前进展」、话题内回一句确认——不再靠下一轮全量重查撞运气。

## 2. 现状事实（2026-11-03 基线）

- ③督办等级：5 分钟轮询直读直写 Bitable（纯函数规则；冒烟②开关可旁挂 bitable_poll Source，默认关）。
- ④值守通报：周四 13-18 点每分钟比对变化即刷新速递格。
- 批量催办 job（未更新进展）：名单/节奏成熟，消息形态为通报内 @ 责任人——**没有话题锚点**，回复无法结构化归属。
- 底座已就位：订阅直通（§4.3：人的消息在已订阅 Thread=执行器自己消化，**天然 explicit，不受 accept_mode 管辖**——A 期不需要 observe/auto）；Trigger DB 幂等；outbox 保序；「需要人」格。
- R1 已把「报警→生成隐患」接入底座，生成的隐患自动进既有督办链——本设计是该链的末段补全。

## 3. A 期架构

### 3.1 feishu_message Source（前置新增）

- **kind**：`feishu_message`（safety bridge 注册，对齐 cron_scan 模式，底座内部零改动）。
- **挂点**：`event_client` 的 `im.message.receive_v1` 分发处（现有进程内去重**之后**、业务 handler 之前），`try/except` 包裹同步 `await ingest`——转发失败只记 warning，绝不影响原消息链路（红线）。
- **Trigger**：`external_id = feishu message_id`（天然幂等；与 event_client 现有进程内 TTL 去重是两层叠加，互不替代——进程内那层的收编是后续独立项，本期不碰）。
- **Thread 映射**：话题 root message_id = thread_key；非话题消息（无 parent/root）→ filtered（原因 `not_thread_reply`）。
- **scope（Fast Path，配置驱动）**：①群 ∈ 白名单（首期治理群一个）②仅话题回复 ③机器人自身消息丢弃（防环）。三者外全部 filtered，落 disposition 可查——量级可控（治理群话题回复日均个位数）。
- **channel**：话题内回复（回执卡用）。

### 3.2 督办任务（影子）

- **来源**：催办话题卡发送成功时 ensure 任务（幂等键：隐患 record_id + 未关闭状态至多一个活任务）。
- **字段**：executor=`supervision_followup`；mandate.scope=该隐患 record_id；订阅=催办话题 thread。
- **阶段（派生，不落库）**：从 Bitable 整改状态派生 等整改/待复查/已关闭；已关闭 → 任务结束（outcome=completed）。

### 3.3 催办卡话题化（批量 job 形态微调，口径说明）

拍板 4 的「不动批量」= 节奏/名单/收件人逻辑零改动。发送形态从「通报内 @」升级为：**每条被催办隐患在治理群发一张话题催办卡**（root=卡片消息；内容=隐患编号/等级/责任人/期限 + 一句「在此话题下回复进展即可，自动同步督办台账」）。发送走 outbox（chat_id 行内权威），成功后注册任务订阅。周四通报照旧不动。

### 3.4 supervision_followup 程序执行器（零 LLM）

收到话题内新回复 Input 后：

1. **写台账（唯一写点）**：把回复原文以固定格式追加写 Bitable「目前进展」——`【群内回执·YYYY-MM-DD HH:mm·发送者】原文`。**只写这一个字段**；整改状态/督办等级等强字段永不自动写（③轮询自会按新进展重算）。
2. **话题内回执卡**（经 outbox）：一句确认「已记录到该隐患目前进展」+隐患编号。
3. **超范围回交**：回复明显与该隐患无关（话题内但内容指向别的事务，如「收到」「好的」之外的指令性内容）→ 不写台账，回执改为「已收到，如需办理其他事务请单独联系」，任务保持 waiting。判断用保守关键词规则（零 LLM）：明确进展陈述才写台账，寒暄/疑问/跑题一律只回执不写。
4. **闭环检测**：写完台账后读整改状态，已关闭 → 任务结束。

### 3.5 与既有链路的关系（红线）

| 组件 | 动作 |
|---|---|
| event_client / business_agent handler | 仅加分发处转发 hook（try/except），去重与业务链路零改动 |
| 批量催办 job | 节奏/名单不动，发送形态话题化+走 outbox |
| ③等级计算 / ④值守 / 周四通报 | 零改动 |
| Bitable 隐患表 | 唯一数据源不变；程序只 append「目前进展」一个字段 |
| 底座一期代码 | 内部零改动（新 Source kind + 执行器全部注册制扩展） |
| 开关 | `SAFETY_SUPERVISION_FOLLOWUP_ENABLED` 默认关 + feishu_message Source 实例默认停用 + 白名单群进 config |

## 4. 验收冒烟（全过才算 A 期成立）

1. **冒烟 A1（全链）**：测试隐患（2099 隔离口径）→ 手动触发催办 → 治理群出话题卡 → 测试身份在话题下回复「明天施工」→ 断言：任务收到 Input / Bitable 目前进展新增回执行 / 话题内回执卡 / 寒暄回复不写台账。
2. **冒烟 A2（可靠性）**：回复后立刻 kill -9 后端再启动 → 无重复写台账（Trigger 幂等）、无丢回执（outbox）。
3. **冒烟 A3（旁路安全）**：开关全关状态下，催办 job 行为与今逐字节一致（原路径直发）；非白名单群消息零 Trigger 入库（filtered 计数可查）。

## 5. B 期方向（不设计，只留锚）

任务全量生命周期（每条未闭环隐患都开任务而非仅被催办的）/ watchdog 实质进展巡检（催办 N 天无回复升级）/ per-task 到期催办替换批量的数据评估 / 话题外平铺消息的 LLM 归属研判。

## 6. 风险

| # | 风险 | 对策 |
|---|---|---|
| S1 | 回执写入「目前进展」污染台账 | 只 append 带前缀标记的原文，人工可删可纠；保守关键词规则+寒暄不写；冒烟 A1 断言寒暄路径 |
| S2 | 话题催办卡数量=催办名单条数，刷屏 | 每轮催办每群上限（默认 10 条/轮，超出合并为通报 @ 形态走原路径）——上限进 config |
| S3 | feishu_message Source 挂点拖慢消息主链 | ingest 同步但轻（单行 insert + scope 判定）；try/except 兜底；冒烟 A3 计时对比 |
| S4 | 责任人在话题里回无关内容被写进台账 | 同 S1 保守规则；写台账失败=Task blocked 可重试，不静默 |
