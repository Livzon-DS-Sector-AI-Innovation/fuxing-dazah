## 0. 一句话定位

报警数据（消防/中控）里暴露的真实问题，不再只停留在日报里，而是**自动筛出候选 → 飞书卡片一键确认 → 在隐患登记闭环主表生成隐患记录 → 既有督办链路自动接管盯到闭环**，全程可追溯。

**按原因判断的两个坑**：
1. **设施故障漏网**：故障报警 91 条分布在 设备误报61/施工17/测试12/氧气1——纯原因白名单会漏掉 61+17=78 条真设施失效（消防设施故障本身是法定整改项）。对策：白名单 ∪ (性质=故障报警 且 原因∉{测试,演练})。
2. **原因与性质矛盾率约 17-29%**：氨水引发 43/246、甲烷 28/97 被人工标「误报」——标注习惯不稳。对策：主判原因，只排除性质∈{测试报警,测试性质,演练引发}，不动「误报」标记（留给确认门人工判断）。

量级核算：推荐白名单 349 条 + 故障子规则 78 条 ≈ 427/292 天 ≈ **日均 1.5 条**（加边缘类 30 条到 1.6），确认卡可承受。

| 类 | 条数 | 占比 | 语义 | 性质/原因构成 | 近 90 天 |
|---|---|---|---|---|---|
| E 已恢复/已闭环 | 1492 | 89.1% | 含「恢复/复位/正常/已更换/无异常」 | — | — |

| **A 处理情况为空** | 7 | 0.4% | — | 测试 3/误报 2/泄漏 1（09-23 妥布 1-54 氨水取样）/故障 1 | 4 |

**未闭环合计 ≈ 131（A+B+C+D）+ F 中约 10 条 ≈ 140 条（8.4%），日均约 0.5 条。** 三个强信号：
1. **反复同点位报修不修**：妥布车间罐区 1-4 探头故障「已通知仪表」7/19·7/23·7/24·7/25·10/09 五次，另 7/23·7/26·7/27「不间断报警」三连；提炼一部洁净区 4-1 自 5 月起 8 次——消防设施长期失效，是最该立隐患的一类，也是聚合口径的直接证据；
2. **屏蔽→恢复无记录链**：80 条屏蔽没有任何一条记录恢复，表结构上缺「屏蔽台账」；屏蔽超 N 天无恢复 = 探测保护空白；
3. **真实泄漏处置无结果**约 8 条（氨水管道漏/滴漏/取样挥发）。

**中控表（14 张，34,165 条，2026-03-31~10-20，日均约 160 条）**：仅 4 字段，但**处置情况写在「报警情况说明」正文里**，形态规整：「时间 + 设备 + 报警类型 + 处置」（如「19:42 1#纯化收集罐高压，压料已恢复」）。按处置语义分类：

| 类 | 条数 | 占比 | 语义 | 闭环判定 |
|---|---|---|---|---|
| E1 已恢复/误报 | 11,306 | 33.1% | 「压料已恢复」「控温后恢复」「误报」 | 闭环 |
| E2 已处置动作 | 17,380 | 50.9% | 「低压，抽料」「高液位已停液」「已转走」「开冰水」——动作即处置，未写恢复 | 闭环 |
| B1 原因解释 | 1,665 | 4.9% | 「空罐」「搅拌」「用量较大」「赶醇/顶水」——操作员判为工艺正常现象 | 闭环（已判定） |
| **C 已通知岗位** | 2,223 | 6.5% | 「已通知停液/降温/岗位处理」——中控本职收尾，岗位执行结果未记录 | 单条不算未闭环；**反复通知同设备**才是信号 |
| **B2 仅报警无说明** | 678 | 2.0% | 混有故障陈述（「压力表坏了」「气动阀漏气」「氮气补给不足」） | 其中故障陈述是候选 |
| **D 明示待修** | 11 | 0.03% | 「待仪表校准/待白班仪表维修/降温失效待处理」 | 未闭环 |
| Z 占位/空 | 902 | 2.6% | 「07:00 无」「停产」 | 非报警 |

结论：**中控闭环率约 89%（E1+E2+B1），「没闭环就确认」在中控同样不能逐条用**；真正的信号是下面两类，均可用规则直接提取、零 AI 成本：

1. **设备/仪表故障陈述**（关键词：坏了/故障/待维修/检修/校准/拆除/漏气/氮封不补气/氮气补给不足/断线/损坏）：全周期 **125 条**（月均 18，近 30 天 23）。构成：氮气补给不足 36、故障 35、检修 22、坏了 10、拆除 8、断线 6。**最重的一族是「储罐氮封压力低—氮气补给不足」36 条**（合格酒精罐 A/C/D、20% 酒精罐 R0405B、新罐区 18#/20# 反复出现）——可燃液体储罐氮封失效 = 防爆隔离缺失，属系统性隐患；其次「温度表/压力表拆除后报警照常」8 条属仪表管理缺陷；「氮封坏了/不补气」「液位计/压力表坏了」「罐盖密封圈损坏」为单体设备缺陷。
2. **同设备同类型反复报警**（规则：同表 · 设备 · 报警类型，30 天 ≥N 次）：近 30 天 ≥20 次的有 23 组（2#配液罐高温 45、米尔贝 1#/3#洗脱剂储罐低压 45/42、达巴氮气主管低压 35…）；全周期 top：莫西 1#热水罐高温 289、米尔贝洗脱剂储罐低压 234/216、达巴氮气主管低压 205。「已通知岗位」类里反复最多的是车间二（达巴、非达）1#/2#/9# 配液罐低液位，30 天合计 43 次通知。频发 = 报警阈值设定不合理 / 设备缺陷 / 操作习惯问题，聚合为一条隐患候选而非逐条。

另一硬事实：**日均 160 条 vs 日报 AI 分析上限 50 条/日**——现有 17:00 日报 AI 只覆盖约 1/3，ai_pattern 单独做候选会漏 2/3。

**对候选口径的推论（2026-10-20 修订）**：**用户拍板：屏蔽（含未记录恢复）按闭环处理，不计未闭环；中控「故障已修复」同理**。消防 = 原因白名单（抓真实事件）∪ 闭环规则（移交无回执 / 明示待办 / 处理情况空）∪ 故障子规则，并集日均约 1.5 条。中控 = **故障陈述关键词规则（日均 ~0.7 条）∪ 频次聚合（同设备同类型 30 天 ≥N 次，聚合为一条）**，ai_pattern 退为可选增强；中控不走逐条闭环口径。两域都额外产出「同点位/同设备反复」信号，是二期聚合口径的直接依据。

**修订版复盘数字（2026-10-20 晚口径，docs/盘点-报警未闭环记录-修订版-20261020.md）**：消防未闭环 147→**19 条**（F1 空 7→0、F3 移交无回执 36→3、F4 待办 8→0、F5 模糊收尾 16）；其中约 48 条是**在线补录**消化——盘点文档发给许康福后 1 小时内值班侧已按清单批量补填「XX:XX 恢复系统」处理结果（抽查原「空」记录均已回填）。中控 77 条（Z1 2 + Z2a 待修 9 + Z2c 故障陈述未写 66）+ Z3 频发聚合组 133 组。三点启示：①清单驱动整改即时见效，验证了「候选→人工确认」的产品形态；②一次性快照迅速过时，联动扫描必须按日滚动才能维持清单有效性；③残留 F3 中 2 条是「烣复系统」错别字/「11:15 的系统」截断导致的分类假阳性，实现分类器时需做文本规范化（形近字、截断句式）。

### 1.3 隐患链路（联动目标侧）

- **隐患登记闭环主表（bitable）= 唯一数据源**，平台不落库；`SAFETY_HAZARD_EVENT_SYNC_ENABLED` 默认关。
- 四常驻轮询已跑通（300s 级）：① AI 识别（条件：`隐患分类（AI）` isEmpty；同时给空/占位编号的行分配 `HZ-YYYYMMDD-NNN`，**已有正式编号不覆盖**）→ ② AI 整改初审 → ③ 督办等级计算 → ④ 周四督办通报值守。
- 整改闭环字段齐全：责任人/部门/期限/三级复核/整改状态/目前进展/督办等级；**督办判定以人工隐患级别为准**。
- **隐患域没有「创建记录」写路径**——`SafetyBitableClient.create_record()` 封装存在且在 emergency_drill / regulation_ingest / msds / oh_health_exam / chemical_inventory 等域实际在用，hazard 域只做过 update 回写。写权限已通。
- 隐患表**无来源字段**，来源区分现仅靠 `检查类别`（multi_select，无固定选项集，registry 无 value_map）。

### 1.4 与 10-12 总体联动方案的关系

总体方案的事件总线、通用规则引擎、驾驶舱维持推迟。本设计把其中的 R1 规则**单独纵切**：

- 复用其原则：bitable 单源权威、平台只存「配置/留痕审计/派生缓存」三类表、幂等键、串行写+0.5s、gate 机制、AI 全审计；
- 不复用其基础设施：不建 event_bus、不建 LinkageRule 通用引擎、不做事件驱动（一期定时批量+人工触发）。将来联动平台复活时，本服务可整体吸收为 R1 规则的实现体。

## 2. 目标 / 非目标

### 目标
1. 消防/中控报警按各自口径筛出「值得立隐患」的候选，幂等不重不漏；
2. 飞书确认卡一键确认/忽略（gate=人工确认），确认后在隐患主表 create_record，字段预填可直查；
3. 生成的隐患被既有 ①②③④ 链路自动接管（AI 识别→初审→督办→通报），**不新建督办机制**；
4. 双向可追溯：平台联动台账（报警 record_id ↔ 隐患 record_id/编号/状态）+ bitable 侧「关联报警」标记；
5. Web 报警页可见联动状态、可单条手动转隐患；Agent 对话内可查可办（写走确认门）。

### 非目标（一期不做）
- 通用事件总线 / 规则引擎 / 联动驾驶舱（维持推迟）；
- 事件驱动实时联动（「性质=真实」即触发）——一期定时批量 + 手动；
- 同族报警聚合（中控 repeated 多条合并为一条隐患）；
- 全自动直写隐患表（gate 一律人工确认；自动模式留开关位二期验证）；

## 5. 详细设计

### 5.1 平台侧两张新表（属架构允许的「派生缓存+留痕审计」类）

```sql
-- ① AI 分析快照（派生缓存；仅中控一期使用，domain 字段为消防/后续域预留）
CREATE TABLE safety.alarm_ai_snapshots (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    domain              VARCHAR(16)  NOT NULL,          -- 'central_alarm'
    alarm_record_id     VARCHAR(64)  NOT NULL,
    alarm_date          DATE,
    ai_alarm_type       VARCHAR(64),
    ai_equipment        VARCHAR(255),
    ai_pattern          VARCHAR(32),                    -- anomalous/repeated/false_alarm/normal_transient
    ai_dimension        VARCHAR(32),
    ai_reason_analysis  TEXT,
    ai_rectification_direction TEXT,
    analyzed_at         TIMESTAMPTZ,
    created_at          TIMESTAMPTZ DEFAULT now(),
    updated_at          TIMESTAMPTZ DEFAULT now(),
    CONSTRAINT uq_alarm_ai_snapshots UNIQUE (domain, alarm_record_id)
);
-- 量级 ~50 行/日，不做 TTL。ON CONFLICT (domain, alarm_record_id) DO UPDATE（每日重跑覆盖）。

-- ② 报警→隐患联动台账（留痕审计 + 幂等键）
CREATE TABLE safety.alarm_hazard_links (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    alarm_domain        VARCHAR(16)  NOT NULL,          -- 'fire_alarm' / 'central_alarm'
    alarm_record_id     VARCHAR(64)  NOT NULL,          -- 报警 bitable record_id（幂等键）
    alarm_snapshot      JSONB        NOT NULL,          -- 触发时刻报警关键字段+AI判定快照
    candidate_reason    TEXT         NOT NULL,          -- '报警性质=真实报警' / 'AI pattern=anomalous'
    status              VARCHAR(24)  NOT NULL,          -- candidate/linked/ignored/failed
    hazard_record_id    VARCHAR(64),                    -- create_record 返回值
    hazard_no           VARCHAR(64),                    -- ①轮询分配后回读回填（展示用，可空）
    card_message_id     VARCHAR(64),                    -- 确认卡消息 id（原地更新用）
    decided_by_open_id  VARCHAR(64),                    -- 点确认的人
    decided_at          TIMESTAMPTZ,
    error_message       TEXT,                           -- failed 时记录
    created_at          TIMESTAMPTZ DEFAULT now(),
    updated_at          TIMESTAMPTZ DEFAULT now(),
    is_deleted          BOOLEAN DEFAULT false
);
CREATE UNIQUE INDEX uq_alarm_hazard_links ON safety.alarm_hazard_links
    (alarm_domain, alarm_record_id) WHERE is_deleted = false;
```

**状态机**：`candidate → linked`（确认+创建成功）/ `candidate → ignored`（忽略，终态）/ `→ failed`（创建异常，保留候选快照可重试）。允许 `ignored / failed → linked`（人工二次确认重建，含报警页手动按钮与 Agent 工具路径）；`linked` 为终态——报警侧后续被人工改性质/删除**不自动撤回**隐患（人工在隐患表按正常流程关闭），联动表保留原快照可查。

### 5.2 中控 AI 快照落库（既有日报任务的增量改造）

`generate_daily_report()` / `build_dept_daily_reports()` 中 `analyze_per_records()` 完成后（对象内存里已带 ai_* 字段），尾部新增 `persist_ai_snapshots(db, views)`：逐条 upsert 至 `alarm_ai_snapshots`。

- **不写 bitable**，中控「AI 不落盘」口径不变——本表是平台派生缓存，属 10-12 架构原则第 1 条明确允许的平台三类表；
- 顺带收益：alarms 页中控 Tab 的 pattern 筛选/展示不再只活在 17:00 那一瞬间；
- 日报某日失败 → 当日无快照 → 次日扫描窗口（滚动 7 天）自动覆盖，联动扫描器发现「近 7 天报警存在但快照缺失」时记 warning 日志（不自行重跑 AI，避免双倍成本）。

### 5.3 联动扫描器 scanner

```
输入：window_days=7（配置）
消防：直读 fire_alarm 表近 7 天记录 →
      (原因分类 ∈ SAFETY_ALARM_HAZARD_FIRE_CAUSES（推荐默认 '现场着火,硫化氢引发,氨水引发,甲烷引发'，值集待拍板圈定）
       或 (性质 = 故障报警 且 原因分类 ∉ 排除集))
      且 性质 ∉ SAFETY_ALARM_HAZARD_FIRE_EXCLUDE_NATURES（默认 '测试报警,测试性质,演练引发'）
中控：查 alarm_ai_snapshots 近 7 天 → ai_pattern ∈ {'anomalous','repeated'}
过滤：LEFT JOIN links（UNIQUE 键）→ 已有任何状态的 link 行即跳过
输出：新增 candidate 行（含 alarm_snapshot、candidate_reason）+ 汇总确认卡
上限：单轮候选 ≤ 10 条入卡，超出部分仅落库不进卡（台账页可见），防刷屏
```

- 去重完全靠 UNIQUE 索引 + `ON CONFLICT DO NOTHING`，任务重放安全；
- 扫描不写任何报警 bitable 表。

### 5.4 确认与生成 confirmer（卡片按钮 / Web 按钮 / Agent 工具三入口共用）

`ensure_and_confirm(domain, record_id, actor_open_id)`：
1. 查/建 links 行（candidate 缺失则即时建，如手动路径）；
2. `record_lock`（复用 `hazard_direct` 的 per-record Redis 锁模式，防卡片重复点击/双入口并发）；
3. 字段映射（下表）→ `SafetyBitableClient.create_record()`（hazard 域连接，`store.get_connection("hazard","hazard")`；经 `bd_writer.write_serial` 串行写）；
4. 成功：回填 `hazard_record_id`，status=linked，更新卡片该条为「✅ 已生成 HZ-xxx」（HZ 号由 ① 轮询分配后回读回填）；失败：status=failed + error_message，卡片标红可重点。

**报警 → 隐患字段映射**（P3/P5 拍板口径）：

| 隐患表字段 | 取值 | 说明 |
|---|---|---|
| 隐患描述 | `【消防报警联动】{部门}·{楼栋}{部位}·{报警类型}·性质:{性质}：{原因}` / `【中控报警联动】{车间}·{产线}·{岗位}：{报警情况说明}（特殊说明）[AI分析: {原因分析摘要}]` | 人可读完整上下文 |
| 检查日期 | 报警时间 | |
| 检查类别 | `报警联动` | multi_select 写新值自动建选项 |
| 关联报警（新列，P3） | `fire_alarm:recXXX` / `central_alarm:recXXX` | 双向追溯键 |
| 整改责任人.部门 | 消防：记录自带部门；中控：车间→部门映射（复用 `central_alarm/daily_dm.group_records_by_dept`） | 多选文本可写；**person 字段（检查人员/整改责任人）一律留空**，由业务方在表里指派 |
| 整改期限 | 报警日期 + `SAFETY_ALARM_HAZARD_DEADLINE_DAYS`（默认 7） | P5 |
| 整改状态 | **显式写 `未关闭`** | 关键：空值不匹配 ③ 督办/通报的 `COND_OPEN`（is [未关闭,整改中]）会被漏筛 |
| 隐患编号 / 隐患分类（AI）/级别（AI）/类别（AI）/描述（AI）/判定依据（AI）/整改建议（AI）/督办等级 | **一律不写** | 编号由 ① 轮询的 `HazardNoAllocator` 分配（单一分配点，已有正式编号不会被覆盖）；AI 列由 ① 生产；督办等级由 ③ 计算 |
| 缺陷图片/整改后图片/复核三列/目前进展 | 不写 | |

### 5.5 飞书确认卡

- 17:15 扫描有候选 → 发目标群（P4）一张汇总卡：「今日报警联动候选 N 条」，逐条列 时间/域/车间(部门)/描述/AI 判定（中控）/建议动作（来自 ai_rectification_direction），按钮：每条「生成隐患 / 忽略」+ 底部「全部生成」；
- 卡片回调注册进 `business_agent_bot_handler.py` 既有 `card.action.trigger` 路由（action 前缀 `alarm_link_confirm_` / `alarm_link_ignore_` / `alarm_link_confirm_all_`，模式同 `progress_submit_rec_`）；按钮可点人按 open_id 白名单（复用督办通报人员口径），非白名单点了回 toast 无权限；
- 决策后原地 `update_card`（`card_message_id` 已存 links 行），不重复发新卡。

### 5.10 既有链路兼容性核查结论（已按代码确认）

1. ① 轮询分配编号仅针对空/占位编号（`ai_analysis.py:226 is_placeholder_no`），联动创建不写编号 → 不冲突；
2. ① 轮询触发条件是 `隐患分类（AI）` isEmpty，联动不写 AI 列 → 新行 ≤300s 内被 ① 正常接管；
3. `write_ai_analysis` 写 7 个 AI 字段不会碰「检查类别/关联报警/整改期限/整改状态」→ 预填字段安全；
4. 创建显式写「整改状态=未关闭」后，③ 督办与周四通报的 `COND_OPEN` 能覆盖联动行；
5. 隐患 bitable 写凭证与其他域共用（tenant token），`update_record` 在 hazard 表已有先例（progress_card / write_ai_analysis），`create_record` 为首次使用但封装现成。

## 7. 测试与验收口径

**单测/集成（pytest，沿用现基线）**
- 扫描：两域筛选口径、窗口滚动、幂等（重复扫描零新增）、快照缺失降级（warning 不抛错）；
- 确认：字段映射全量断言（含显式「未关闭」）、并发双点击只建一条（锁）、create 失败落 failed 可重试、ignored/failed → linked 迁移、linked 终态不可重复；
- 快照：upsert 覆盖、日报失败路径不写脏数据。

**真机验收（T8）**
- 手动扫描接口触发 → 测试报警记录（bitable 造一条性质=真实）→ 卡片出现在目标群 → 点「生成」→ 隐患主表出现新行且字段逐项符合映射表 → ≤300s 后 ① 轮询补齐编号与 AI 列 → ③ 督办等级出现 → links 行 hazard_no 回读回填；
- Web 报警页联动列状态流转正确、直转按钮幂等；
- Agent 对话「把昨天的中控异常报警转成隐患」走确认门全链可办。
