# DESIGN — 事故事件管理（S16 incidents）：业务全景与三期能力设计（2026-10-22）

## 0. 一句话

S16 从「三态骨架占位」升级为**「登记台账为事实源（人维护）＋ Agent 感知/调查/盯办为增量（人拍板）」**的事故事件管理域：一线与安管负责快报登记、调查定性、措施验收；Agent 负责事发感知候选、时间线还原与调查初稿拼装、CAPA 到期盯办、案例警示推送。**调查的定性权/定责权/验收权全部在人**——Agent 产出的调查初稿里「原因/性质/责任」三栏强制留空。

> 依据：飞书《安环AI-Agent体系业务层设计》修订 59 §13.1（S16 管什么/怎么管/管理所依）；《生产安全事故报告和调查处理条例》（国务院令 493 号）；GB/T 33000-2016 §5.7；GB 6441-86 事故类别。
> 上游文档：四期蓝本 §5（incidents 2 表字段与 6 卡口径，20261014）；拼图分析 §3 S16（现状≈40%）；R1 报警→隐患联动设计（确认卡模式，20261019）；S1 核查引擎设计（D7-03 人工项，20261021）。
> 代码基线：feature/warehouse-module（incidents 三态骨架已交付：页面/端点/健康度墙/registry kind 均在）。

## 1. 实际业务全景（S16 涉及哪些业务）

体系原文口径六项 + 法定要求 + 福兴实际，归并为五条业务线：

### 1.1 报告登记线（事发后第一小时）

| # | 业务 | 要点与法定依据 |
|---|---|---|
| 1 | 事发即时报告 | 现场人员→安管快报（内部流程，分钟级）；一般事故以上 1 小时内报属地监管部门（493 号令 §9）——**对监管的上报由人执行，系统只留痕登记时间线，Agent 不越权** |
| 2 | 登记建档 | 事件编号/时间地点部门/**事件类别（事故/未遂事件/异常事件）**/**等级**/简述/伤亡/直接损失；事故类别按 GB 6441（触电/高处坠落/机械伤害/中毒窒息/火灾爆炸等 20 类） |
| 3 | 补报 | 伤亡情况变化 30 日内补报、新情况及时补报（493 号令 §13）——台账要能挂补报链 |
| 4 | 相关方事故纳入 | 承包商/相关方/访客**在本企业内**的事故同样登记（体系原文明确），并作为 S14 承包商季度评价的扣分素材 |

### 1.2 调查处理线（四不放过）

| # | 业务 | 要点 |
|---|---|---|
| 5 | 内部调查 | 查明经过与原因（直接+根本）、认定性质（责任/意外）、认定责任、提出整改防范建议（体系原文）；调查组组建、方法（5-Why/FTA 等） |
| 6 | 四不放过核查 | 原因未查清不放过/责任人未处理不放过/整改措施未落实不放过/有关人员未受到教育不放过——**结案的前置条件**，逐项可勾核 |
| 7 | 调查报告归档 | 报告文件挂台账行，迎检/自评时档案完备（S1 核查引擎 D7-03 对应项） |
| 8 | 责任处理与考核 | 责任追究/考核落档——纸档+人工为主，绩效联动数据进 S1 |

### 1.3 纠正预防线（CAPA 闭环）

| # | 业务 | 要点 |
|---|---|---|
| 9 | 措施制定 | 纠正（治标）与预防（治本）双轨，一事件多措施 |
| 10 | 责任分派与落实跟踪 | 部门/责任人/期限；进度与完成登记 |
| 11 | 验证关闭 | 验证人+有效性判定；**无效重开**（不得带病销号）——平台遗产 Accident 模型已验证过 start/verify/close 全周期形态 |

### 1.4 案例警示线（事后教育）

| # | 业务 | 要点 |
|---|---|---|
| 12 | 案例沉淀 | 结案事件即案例源（含原因/教训的结构化行），**不另建案例库表** |
| 13 | 警示推送 | 案例卡推送涉事部门+同类作业部门（班前会素材），不全员轰炸 |
| 14 | 举一反三 | 事故后重新辨识是法定情形（GB/T 33000 §7.1 四种重新辨识之一）——结案后向安管发「同类风险再辨识提醒」，链接 S3/S4 |

### 1.5 统计分析线（管理闭环）

| # | 业务 | 要点 |
|---|---|---|
| 15 | 事故统计 | 年度事件总数/其中事故/未遂事件/直接损失；千人负伤率口径 |
| 16 | 趋势规律 | 月度趋势、类型分布、部门分布（未遂事件堆积=前兆信号，海因里希金字塔底层是本域主要数据形态） |
| 17 | 目标绩效联动 | 「重伤及以上事故为零」是 S1 上限型指标；S16 接入后 S1 的 incident 系取数器自动出数、无数据态消除 |
| 18 | 档案完备核查 | 四不放过+调查四要素齐备性，S1 D7-03 从人工项升级自动判定 |

**福兴实际特点**（决定设计的形态）：化工制药企业，事故属小概率（年度目标为零），**台账的日常主体是未遂事件/异常事件**；相关方作业频繁；报警高频但真后果稀少（R1 盘点：全表 1666 条里真火警 2 条）——所以本域价值不在「事故 CRUD 频率」，而在**登记文化培育（未遂事件进账）+ 稀发事故的调查辅助与档案完备**。

## 3. 总体架构

```
感知（多源候选，确认门兜底）            事实源（人维护，Bitable）           循环（复用既有形态）
─────────────────────────            ──────────────────────           ─────────────────────
① 群@机器人快报 ─┐                   incident 登记表（主台账 v2）        capa deadline 日扫描
② 报警联动升级 ──┼→ 安管确认卡 ─→ 草稿行 → 调查 → CAPA 跟踪 → 结案   → 到期提醒卡/逾期速递红条
③ 页面人工登记 ──┘                       │        │          │              │
      （候选≠登记，确认才算）             │        │          └─ 结案 ─→ 案例警示卡（定向）
                                         │        │                      └─ 再辨识提醒→S3/S4
                                    「生成调查初稿」按钮                     （举一反三）
                                         │
                              留痕库时间线 + 本域同类案例 + ragplus 法规依据
                                         │
                              初稿卡（经过✓时间线✓ | 原因/性质/责任=留空人工填 | 措施建议）
                                         │
                              终稿附件回填 report_file → 四不放过逐项勾核 → 结案
```

三层解耦：感知只产候选（草稿行+确认卡），登记/调查/验收是人的动作；Agent 的四个增量（感知候选/初稿拼装/到期盯办/警示推送）全部挂在既有循环形态上，不建新链路。

## 4. 数据模型

### 4.1 Bitable「事故事件登记表」（kind=`incident`，蓝本 v1 → v2 修订）

v1 14 列保留，新增 9 列：

| Bitable 列名 | 目标字段 | 类型 | 说明 |
|---|---|---|---|
| 事故类别 | accident_category | single_select | GB 6441 二十类（物体打击/触电/高处坠落/机械伤害/中毒窒息/火灾/其他爆炸…）；仅类别=事故时填 |
| 涉事方类型 | party_type | enum | 本厂员工 / 承包商相关方 / 访客 / 其他（相关方事故纳入口径，S14 评价联动锚点） |
| 涉事单位 | party_name | text | 相关方名称（party_type≠本厂时填） |
| 伤害详情 | injury_detail | combined_text | 伤者/部位/程度/救治医院（自由文本结构化习惯即可，不做子表） |
| 补报标记 | is_supplement | enum | 首报 / 补报（补报行在「备注」注明补报对象编号，不建自关联列） |
| 直接原因 | direct_cause | combined_text | 调查四要素①（人工填，初稿留空） |
| 根本原因 | root_cause | combined_text | 调查四要素②（同上） |
| 事件性质与责任 | nature_accountability | combined_text | 调查四要素③④（性质：责任/意外；责任认定） |
| 四不放过自查 | four_checks | four 个 enum 列：原因查清 / 责任处理 / 措施落实 / 人员教育（已完成/未完成） | 结案前置：四列全「已完成」且 CAPA 全闭环 |

v1 修订一处：**状态枚举扩为 已报告 / 调查中 / 整改中 / 已结案**（v1 三态漏了调查完成到结案之间的 CAPA 落实段——四不放过第三条要求措施落实后才结案）；「调查报告」列（report_file）保留，终稿附件回填。

### 4.2 Bitable「CAPA 措施跟踪表」（kind=`capa`，蓝本 v1 基本保留）

v1 11 列保留，仅修一处：**验证结果=无效 → 状态强制回「进行中」**（无效重开口径写进列说明，不建 reopen 计数）。

### 4.3 红线：AI 不定性、不定责

调查初稿与一切 AI 产出**只填「经过/时间线/同类案例/法规依据/措施建议」五类内容**；直接原因/根本原因/事件性质/责任认定四栏一律留空由调查组填写；对监管的上报动作系统不代发。这是 §1 调查处理线的定性权边界，也是调查报告作为法定文件的严肃性要求。

### 4.4 平台遗产 `Accident` 表处置

models/safety_ops.py 的 Accident + repository CRUD 为旧 dazah Web 遗产（无 API/前端消费方，历史迁移曾在 dazah 后端 drop 过同款表）。**建议 drop 并移除模型**（避免与 Bitable 双事实源困惑，遵「Bitable 唯一数据源」全局口径）——列为拍板点 P2。

## 5. 业务功能（按期）

### 5.1 一期：台账接入（转 live）

1. 用户按 §4.1/4.2 建两张 Bitable 表（v2 字段）→ bitable 配置页登记 app_token/table_id → 页面零改码转 live（三态机制已在）。
2. 统计卡 6→8：v1 六卡 + **相关方事故数**（party_type≠本厂，当年）+ **未结案事件**（status∈{已报告,调查中,整改中}）。健康度卡 warn 口径沿用（capa_overdue>0 或 调查中超 30 天）。
3. Agent 只读工具 `query_incidents(category?, level?, status?, year?, party_type?, keyword?)` / `query_capas(status?, overdue_only?)` 注册 read_tools——「今年几起未遂」「上起事故整改闭环了吗」Agent 可答。
4. Accident 遗产表处置（P2 拍板后执行）。

### 5.2 二期：事发感知 + 调查初稿

**感知（三源一确认）**：
- 群@机器人快报：安全群 @机器人 一段话（时间/地点/简述/伤亡初判）→ 解析成草稿行（status=已报告，备注标「快报待核实」）+ 安管确认卡；确认后即为正式登记行。**先做，零依赖**。
- 报警联动升级：R1 确认卡上加「升级为事件登记」动作，仅当报警性质∈{火警,泄漏}且已造成实际后果时人工触发——与 R1 排期并轨（R1 未实施则本期只留接口）。
- 页面人工登记：台账页「登记事件」按钮（表单按 v2 字段）。
- 候选≠登记：一切候选先进草稿行，安管确认门兜底防噪音（与 R1 同一原则）。

**调查初稿生成**（事件详情 Drawer 内按钮 / Agent 对话触发）：
1. 输入锚点：事发时间±窗口、部门、地点关键词。
2. 时间线还原：scheduler_job_runs（该时段该域 Agent 跑了什么任务）+ ai_call_audits/agent_sessions（审核/催办/问答留痕）+ hazard/alarm 域记录（事发前后相关隐患与报警）→ 按时间排序的事件流水，**每条带留痕链接可溯源**。
3. 同类案例：本域台账历史行（类别/部位相似）+ ragplus 法规库（事故报告调查条款、涉事作业操规条款）双源检索。
4. 产出：飞书卡片初稿（四不放过清单框架：经过✓/时间线✓/同类案例✓/法规依据✓/**原因·性质·责任=留空**/措施建议）→ 调查组编辑 → 终稿附件回填 report_file。

### 5.3 三期：CAPA 盯办 + 案例警示 + S1 联动

1. **CAPA 盯办**：每日扫描 capa 表（进行中）→ deadline 前 3 天提醒卡到责任人；逾期 → 速递格红条（incidents 域格）+ 催办卡（复用 hazard 催办卡形态）。结案门：四不放过四列全完成且名下 CAPA 全「有效」才允许结案（页面校验+Agent 工具同口径）。
2. **案例警示**：结案（类别=事故，或 near_miss 高价值）→ 案例卡定向推送涉事部门+同类作业部门（按作业/装置关键词匹配，不做全员推送）；卡片含经过/原因/教训/防范要点，链接台账行。
3. **举一反三**：结案后自动生成「同类风险再辨识提醒卡」推安管（法定事故后重新辨识情形），链接 hazard_id 域。
4. **S1 联动**：指标注册表加 `incident.count.serious`（重伤及以上，上限型，年内进行中·当前达标/超标）与 `incident.four_checks.complete_rate`；D7-03 从人工项升级自动（四不放过+调查四要素+report_file 齐备性判定）——S1 清单零改，取数器接上即出数。

| P5 | 案例警示受众 | 涉事部门+同类作业部门定向；全员版只在死亡/重大损失事故时（法定警示教育） |
| P6 | 调查初稿触发方式 | 事件详情按钮+Agent 对话双入口，手动触发不自动跑（稀发事件值得人工点一下） |
| P7 | 未遂/异常事件要不要设上报奖励口径（体系 6.3 内部报告奖励机制） | 本域只登记不挂钩奖励；奖励机制若做属 S4 隐患报告议题，另议 |

## 9. 风险与对策

- **登记文化稀疏**（事故为零目标是常态，未遂事件靠人报）：统计卡把未遂单列成主体指标；群快报把登记成本降到一句话——先降门槛再谈齐全。
- **感知噪音**：确认门兜底（候选=草稿行，安管确认才算登记），与 R1 同一原则。
- **初稿幻觉**：时间线只引用留痕记录且逐条带链接；定性四栏强制留空；初稿标注「仅供调查组参考」。
- **CAPA 与 S4 隐患整改双轨重复**：口径写死——事故 CAPA 留本域闭环；调查中新发现的**独立**隐患转 S4 登记（capa 备注注记隐患编号），两边不互写。
- **S1 无数据态误判**：incidents 未接入前 S1 取数器返回 NoData（≠未达标），接入后自动转实数——核查引擎已有该语义，无新增风险。
