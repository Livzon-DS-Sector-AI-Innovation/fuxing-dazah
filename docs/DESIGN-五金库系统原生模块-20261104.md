# 五金库系统原生模块——设计方案（2026-11-04）

> **定位**：五金库（五金备件/仪器仪表/化玻试剂/劳保用品/耗材等非生产用物资）脱离飞书多维表格，作为**第一个系统原生仓储域**直接落在本平台——本地数据库为唯一权威，全流程无纸化，线上申领、库存实时查询。
>
> **已定口径**（2026-11-04 09:42 研讨会 + 用户指令）：
> 1. 载体拍板：**转系统，不用多维表格**（畅总原话方向：搭系统平台无纸化办公，多维表格迁移工程大，**先从五金库开始做**，五金库是第一个转到系统的库）。
> 2. 入库免审批：仓管员核对厂家送货单数量/品牌后**直接入库**，随即通知车间办事员领取；不设审批环节。
> 3. 领用分两轨：**常规领用**（一级库备件）走电子领料单+审批；**现到现领**（一进一出类）办事员直接领，不走审批——否则上万种代码全部走审批不现实。
> 4. 库存要**实时计算**，要有**预扣数**：申请即预扣、审批通过发料后实扣、驳回释放。
> 5. 入库数据源优先级：**ERP 数据接出 > 手动登记**（核心诉求=不增加仓管员工作量：ERP 必录——财务付款依赖，若再在系统录一遍就是两份工作）。ERP 非实时（月底结算延迟 2-3 天）→ 双通道：能接就自动导 + 手动/拍照核对兜底。
> 6. 申购流程**维持 BPM 不动**（蔡总审批等现有链路不变），系统不做申购审批。
> 7. 所有出入库**必须录 ERP**（财务付款、盘点账实匹配）；ERP 现状分工：入库=仓管员做，出库=车间做、仓管员审。
> 8. **入库单由 ERP 数据导入生成**（2026-11-04 用户补充拍板）：仓管员不在本系统重复录入入库。ERP 接口形式未确认期间，以「人工导出文件→上传导入」走同一链路过渡；纯手动登记仅作异常兜底。
> 9. **库存变动只随出入库单发生**（用户补充拍板）：入库单=ERP 导入；出库单=飞书审批领料单——**审批通过前预扣库存，通过后实扣**；盘点调整等以独立单据类型另列。
> 10. **收货单据 OCR 比对入库单**（用户补充拍板）：打印体送货单拍照识别（供应商/品名/规格/数量）→ 与 ERP 导入的入库单**自动比对**——一致确认入账、差异人工处置；OCR 同时承担内部物料代码自动匹配入口。
> 11. **两类物资定案**（2026-11-04 用户确认）：**共用类=清单内 492 项**——实际入库占库存，**出库须审批开单**；**车间单独需求类=清单外**（仪器仪表/化玻试剂/劳保/耗材/专属物资等）——**不实际入库**，到货即由使用部门直接领走，**不开审批领料单**，仅留直发台账流水。
> 12. **P1-P8 已全部定案**（2026-11-04 用户选项拍板，见第十二节定案记录）：审批=新建飞书审批定义；编码=用采购 ERP 编码、清单先导入后回填；期初=零库存纯增量；在途=以 ERP 单为准（不做在途预登记）；入口挂仓储组；二级库一期不管；申购方案二公式。
> 13. **ERP 暂无法接入（2026-11-04 变故）**：ERP 数据接不出，入库主通道改为**拍照 OCR 直接入库**（送货单→入库单，零手工录入）；极简登记兜底；`erp_import` 通道保留为 ERP 恢复后的升级路径（同一单据模型无缝切换）。仓管员在 ERP 的录入动作**照旧不变**（财务账仍依赖），系统账以 OCR 确认的入库单为准。

## 一、业务域总览：三类物资、两级库

### 1.1 两类物资（`managed_class` 字段，2026-11-04 用户定案）

| 类 | 口径 | 库存行为 | 出库/审批 | 主数据 |
|---|---|---|---|---|
| `stocked` **共用类** | **=物资清单内 492 项**（7 大类），通用、量大、周转快 | **实际入库，占库存**（预扣/实扣/FIFO/库位/物料卡） | 出库**须审批开单**：飞书审批领料单，审批中预扣、通过后实扣 | **全量主数据**（本系统权威） |
| `direct` **车间单独需求类** | **=清单外**：仪器仪表/化玻试剂/劳保用品/耗材/垃圾袋等一进一出（上万代码）+ 空压机干燥器/滤芯等专属物资（`direct_dept` 标所属车间） | **不实际入库、不占库存**：ERP 入库单确认时同单生成出入双流水（净零，台账留痕供月度对账/ERP 核对） | 到货即由使用部门**直接领走，不开审批领料单**；领用部门=ERP 入库单「入库部门」 | 不建全量主数据：流水自由文本品名/规格，匹配到主数据则挂内部代码，匹配不到不强求 |

> **两类边界=物资清单本身**：新物料要纳入共用管理须先入清单（主数据维护）；清单外到货一律按车间单独需求处理。
> 依据：会议原话「一进一出的有上万种代码，现到现领办事员直接领」「专属物资半个入库半个出库直接领走」+ 用户 2026-11-04 定案「共用的就是清单里面的，这批出库需要审批开单；车间单独需求不实际入库，到货即由使用部门直接领走，清单中没有，这部分不开审批领料单」。

### 1.2 两级库边界

- **公司一级库（五金库本库，约 200㎡，平台下放大件管道/阀门，平台上货架放小件）**：系统管到库位。
- **车间二级库**（车间个性化物资、一级库放不下的、车间备品间暂存）：**一期系统不管**（车间自管，制度留痕），仅 `hardware_materials.secondary_holder`（二级库归属车间，文本备注）做台账级标注——P6 拍板。

### 1.3 与 ERP 的分工（现状实态 + 系统定位）

| 动作 | ERP（财务账，必须录） | 本系统（实物账，实时） |
|---|---|---|
| 入库 | 仓管员录（2 个工作日内） | **入库单由 ERP 数据导入生成**（仓管员零重复录入）；到货实物核对靠送货单 OCR 比对 |
| 出库 | 车间录、仓管员审 | 出库单=飞书审批领料单：审批中**预扣**、通过后**实扣** |
| 盘点 | 财务年度盘 | 仓储月度盘（差异表导出供财务） |

系统是**车间视角的实时库存权威**（查库存不再打电话）；ERP 仍是**财务账权威**。两账核对 = 三期自动 + 一期 `erp_status` 人工标记。

- `hardware_returns`：退库单 `WJK-TK-*`，退库人/部门负责人签/仓管员验收（不合格拒退），退回批次合并原 lot 或新 lot。

## 三、库存口径与 FIFO

**变动收口原则（2026-11-04 用户拍板）**：库存只随两类单据变动——**入库单**（ERP 数据导入生成，确认后增）与**出库单**（飞书审批领料单，审批通过后减）；盘点调整/退库/报废以独立单据类型另列。无单据不动账。

```
on_hand(m)   = Σ receipt_items.remaining_quantity（未报废批次余额；仅 stocked 共用类有批次）
reserved(m)  = Σ requisition_items.need_qty  WHERE 单头 status ∈ (pending, approved)
available(m) = on_hand − reserved          ← 车间查询页展示口径（只反映共用类）
预警          = available < safety_stock
```

> 无在途量口径（P8 定案，随 ERP 通道暂停进一步简化）：库存以 **OCR 确认的入库单**为准——拍照确认即入账，无中间态；上线零库存起步（P4 定案），存量实物靠首次盘点校准。

- **预扣**在申请提交时即生效（pending 占用），驳回/取消释放，发料时转实扣（remaining_quantity 按批次扣减）——对应「审批通过前预扣、通过后实扣」。
- **FIFO**：发料建议按 `arrived_at` 升序分配批次（临近效期优先），仓管员可手动调整分配。
- 库存页对车间展示：available 为主数、on_hand/reserved 明细展开——「还有多少个 DN25 阀门、要不要买」一步可答。

## 四、核心流程

### 4.1 入库（拍照 OCR 采集主通道，免审批，每单 30-60 秒）

```
① 到货拍照：仓管员对厂家送货单拍照（打印体）→ 上传（Web 工作台/对话直接发图）
② OCR 采集：vision 结构化提取（供应商/单号/到货日期/多行品名+规格+数量）
     → 品名规格自动匹配 492 项主数据（共用类挂物料；清单外落 direct 自由文本行）
     → 生成入库单草稿（多行、每行带匹配置信度，低置信标黄）
③ 一屏确认：仓管员核对草稿（实物在手上，照单点收改错）→ 双签（使用部门经办人共同确认）
④ 确认入账（accepted）：
     stocked 共用类：生成批次+流水，库存+，选库位上架+物料卡
     direct 车间单独需求类：不占库存，同单生成出入双流水（直发 target_dept=领用车间）+ 推送办事员领取卡
⑤ 兜底通道：手写送货单/识别失败 → 极简登记表单（选物料/输数量/拍照留证）或对话登记（两段式确认卡）
⑥ 不合格：拍照留证+原因 → rejected → 通知采购退换货（采购部职责）
```

- **库存只在这一步 + 领料出库两处变动**（第三节收口原则）；OCR 与 manual 单分列报表可查。
- 制度「验收未完成前不得入库」= status 机强制：draft 不动库存，accepted 才生成批次。
- OCR 技术：复用系统现有 vision 链路（S6 违章分级同源），打印体表格结构化提取直接出 JSON；识别结果全部落 `ocr_result` JSON 留痕（原 `ocr_compare` 字段更名——比对职能随 ERP 通道暂停而弱化，ERP 恢复后恢复比对）。
- **仓管员在 ERP 的录入动作照旧**（财务付款依赖，制度 2 个工作日内）；系统不替代 ERP，两账月度人工核对（对账页），ERP 恢复接入后转自动（第六节）。

### 4.2 领用（两轨）

```
常规领用（共用类 stocked，唯一需要审批开单的出库）：
  车间 Web/对话发起领料申请（选物料/数量/用途）
  → 提交即预扣 + 创建审批（P1：飞书审批实例）
  → 部门主管审（超额 req_type=excess 加生产总监节点）
  → 通过：仓管员发料台看到待发料单 → FIFO 建议批次 → 实发量确认 → 领用人点收 → 实扣
  → 驳回：释放预扣 + 卡片通知申请人

车间单独需求（direct 清单外）：不申请、不审批、不实际入库——
  仓管员确认 ERP 入库单（OCR 比对）时即完成出入双流水，领用部门=ERP 入库部门，到货直接领走；
  车间月度对账页可查本部门直发（一进一出）明细。

紧急（共用类抢修）：仓管员直接发料（urgent_issue 流水，标紧急）
  → 系统生成待补申请单 → 24h 内申请人补审批 → 补上转正常；逾期标 overdue_unpatched
  → 提醒推送 + 「仓储部有权暂停该部门后续领用」提示（5.3.4）
```

### 4.3 退库 / 盘点 / 呆滞 / 计划 / 温湿度：见 2.6，二期交付页面。

## 六、入库数据源策略（ERP 暂不可接入，2026-11-04 变故后）

**主通道：拍照 OCR 直接入库**——送货单是打印体（识别准确率高，会议确认），拍照→结构化提取→生成草稿→仓管员一屏确认，**零手工录入、每单 30-60 秒**，比原 ERP 导入方案更快（无 ERP 录入延迟，确认即入账，实时性反而更好）。

| 通道 | 用途 | 说明 |
|---|---|---|
| **OCR 采集（主）** | 打印体送货单 | vision 结构化提取（供应商/单号/日期/多行品名规格数量）→ 自动匹配主数据 → 草稿 → 确认入账；Web 工作台与对话发图双入口 |
| 极简登记（兜底） | 手写单/识别失败/无单 | 表单：选物料+输数量+拍照留证；或对话登记（两段式确认卡）。单列 `manual` 报表 |
| `erp_import`（预留） | ERP 恢复接入后 | A 文件/B 定时/C API 三档不变（见下），与 OCR 通道**并存对账**：ERP 单到达自动匹配已有 OCR 入库单（按供应商+日期+品名数量近似匹配）核对差异 |

**ERP 恢复后的升级路径（原三档设计保留）**：A 人工导出文件上传 → B 定时批量取文件 → C API 直连（`platform/integrations/erp/` 落点）；`erp_doc_no` 唯一约束幂等去重。切换零迁移：单据模型同一套，`source` 字段区分，OCR 通道不退役（转为实物核对+差异比对环节）。

**与 ERP 的账务关系（现阶段）**：
- 仓管员在 ERP 的录入动作**照旧**（财务付款依赖，制度 2 个工作日内）——系统不替代 ERP；
- 系统账（实物账）以 OCR 确认入库单为准，ERP 账（财务账）月度人工核对（对账页：按月份列系统入库 vs 仓管员自报 ERP 已录清单）；
- movements 的 `erp_status`（pending/entered）保留：出库侧车间在 ERP 做出库后标记，月底对账页列未录清单。

## 九、AI 介入提效设计（复用三源基建，为后续库奠基）

**总原则（三源定调）**：
1. **安全 AI 成熟模式**：AI 只标记/建议、人拍板（MSDS 错别字审核模式——71 条标记无一自动改）；写操作一律两段式确认（草稿→确认卡→回写）；成果推送走速递格/晨报模式；
2. **仓储模块开发现状**：AI 基建已全——`ai_config/scenario_registry`（LLM 场景开关+模型选路）、**`receipt_recognition` 送货单识别管线已存在**（原辅料域：图片方向预判+字段识别+审计）、两段式草稿（`warehouse_agent_drafts`）+通用确认门（`confirm_requests`）、`push_center`（generator 注册制）、智能中心（alert_rules/replenishment_suggestions/daily_briefings）、`agent/skills` 与 MCP——**五金库只做场景注册+工具挂载，零新建 AI 基建**；
3. **SuperAgent 底座（app/platform/superagent）**：Source 插件注册制（kind/scope/poll/fields）、Executor 注册制（一期=确定性函数）、effects/policy/watchdog 齐备；R1 报警联动已验证「cron 扫描源→白名单∪闭环规则→执行器」模式——五金库预警/催办/报告按同模式接入，**不自成体系**。

### 9.1 五层介入模型（按流程 × AI 能力）

| 层 | 五金库介入点 | 模式来源 / 复用什么 | 分期 |
|---|---|---|---|
| **L1 采集**（vision） | 送货单拍照 OCR 结构化提取（入库主通道） | **复用 `receipt_recognition` 管线骨架**，新场景 key `hardware_receipt_recognition` 注册进 scenario_registry（开关/模型选路/审计全继承）；实物照片初筛（破损/锈蚀/渗漏辅助验收） | 一期 / 初筛二期 |
| **L2 理解对齐**（LLM） | ①品名规格→主数据匹配：编码精确→名称规格模糊→同义词→人工四级链；②车间口语解析（「25 的阀门」「540 法兰」）；③低置信**标黄只标记不代改** | warehouse agent pipeline「识别-对齐-提交」模式；同义词沿用 3x 平台沉淀机制；MSDS 审核模式 | 一期 |
| **L3 交互**（agent 对话） | 查库存 / 代发起领用 / **对话直发送货单照片入库**（草稿回显→确认卡入账） | 仓库机器人 tools 注册表挂三工具；两段式确认门 | 一期 |

| **L5 自动执行**（superagent） | 见 9.2 事件源/执行器 + observe→auto 分权 | superagent Source/Executor 注册制 | 二期起步 |

### 9.2 SuperAgent 接入（事件源 + 执行器，R1 同模式）

**事件源**（Source 注册，`hardware_alert_scan` cron 扫描）：
- 安全库存击穿（available < safety_stock）
- 呆滞到期（连续 3 月无领用，季度清单）
- 紧急领用 24h 未补单
- OCR 草稿积压（待确认超 N 单）
- 审批通过未发料超时

→ 白名单∪闭环规则（R1 模式：可自动处置的白名单 + 已闭环去重）→ 产生 AgentTask → 确认卡或直达执行器。

**执行器**（Executor 注册，确定性函数先行，LLM worker 二期）：
- `hardware_digest_push`：日/周报速递格（入库/出库/预警/待办，AI 总结文本+结构化数字）
- `hardware_plan_draft`：每月 25 日自动生成采购计划草案（P7 公式+AI 注释）
- `hardware_urge`：催办（紧急补单/待确认草稿/待发料）

### 9.3 observe→auto 分权路线（逐步放权，每场景独立开关）

| 阶段 | 放权内容 | 开关粒度 |
|---|---|---|
| 0（一期） | 全部 AI 动作 **observe**：只出建议/草稿/标记/纯通知推送，入账/出账/计划全部人确认 | scenario_registry 场景开关 |
| 1（稳定后） | 低风险 auto：报告/速递定时推送、催办、呆滞报告；`direct` 类**高置信** OCR 直接入账（匹配置信度阈值可配，stocked 类永不自动） | superagent 白名单 + policy |
| 2（成熟） | 补货建议直接生成计划草案待一键审核；盘点差异归因自动附单 | 同上 |

红线（沿用底座治理）：AI 永不直接动账（stocked 入账/出账/退库必经人确认）；全部 AI 动作审计（superagent 审计 + warehouse_agent_audit 模式）；总开关 SUPERAGENT_ENABLED 式一键熔断。

### 9.4 奠基资产（五金库为第一个系统原生库，沉淀四件可复用能力）

1. **「拍照→OCR→结构化→主数据对齐→确认入账」参数化管线**：scenario key 即库域参数——原辅料/成品迁移系统时零新建（原辅料 receipt_recognition 即同族）；
2. **四级主数据匹配器**（编码/名称规格/同义词/人工兜底）：任何库域主数据对齐通用件；
3. **「扫描源→规则→确认卡/执行器」三步模板**（superagent Source+Executor）：任何库域的预警/催办/报告类任务同构复用；
4. **observe→auto 场景粒度放权模板**：AI 上能力的标准节奏，避免一上来全自动的信任风险。

### 9.5 通知（复用 push_center generator 注册）

入库 accepted→推车间办事员领取卡；审批通过→推仓管员发料+申请人；驳回→推申请人；紧急 24h 未补→提醒；安全库存低于→周报；温湿度每日提醒填写。

### 9.6 定时任务（TaskDefinition）

月度计划 25 日快照、呆滞季度扫描、紧急未补单检查、温湿度提醒；（superagent 事件源与执行器走底座自己的调度，见 9.2）。
