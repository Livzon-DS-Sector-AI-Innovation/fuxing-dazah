## 0. 一句话

把 3.x 平台上有真实数据的三份资产接进 dazah：**408 人承包商实名台账**（身份证/手机/工种/年龄全实）做 S14 的人员视角+三组交叉核验；**1400 人全员主档**（部门/岗位实、身份证空）做岗位字典与人源辅助；**64 个风险分区轮廓**做一次性静态地理资产，供未来点位落图。

### 1.3 全员主档（1400 人）

`GET /api/tiji-system/user/page?current&size`（blade-auth 平台 token，total=1400）。实测字段：`nickname`（姓名）/**`jobNo`/`accountName`（工号）**/**`deptName`（部门，如"精制工程一部"）**/**`postName`（岗位，如"1#冻干线冻干出料操作工"）**实；`idCardNo` 空、`locationCardNo` 空、accountStatus/userStatus 状态位有。
**结论：可作部门×岗位字典与姓名级人源辅助，不可作身份证级个人主档。**

### 1.4 风险分区（64 个）

`GET /api/tiji-risk-prevention/openapi/risk-district/page`：顶层 `distId/distName/riskLevel/riskLevelDesc`，`rails[{id,name,pointsList,pointDTOS,floorNo,outSide}]`。**坐标以 `pointDTOS` 为准（经度 x≈119.29、纬度 y≈25.46，福州福兴厂区）**；`pointsList` 是本地米制平面坐标（x≈16-19 万），勿用。riskLevel 实存（2026-10-26 复测：46 低/4 一般/14 空）——资产收录但首期不参与着色（14 空值易误导）。
> 勘误（2026-10-26 F2 验收）：本节 v1 曾误记「本地平面坐标无经纬度、无风险等级字段」——初测只看了 pointsList 所致；F2 开发实测 pointDTOS/riskLevel 存在并已改用经纬度渲染（纬度 cos25.46° 纠正 + y 翻转北上）。

## 2. 3x-A3 承包商实名台账接入 S14

### 2.1 定位

S14 现在只有「准入审批单」视角（contractor_admission Bitable：准入 AI 审核+结论回写+黑名单）；本项补「**在场人员花名册**」视角——平台台账是实名底册，dazah 在其上做三组交叉核验。数据权威在平台，dazah **只读不镜像**。

### 2.2 数据通道

- 复用 `WorkTicketPlatformClient.list_contractor_users()`（all-page 全量一次拉，408 人量级）。
- 新建 `service/contractor_workers.py`：CachedReader 短 TTL 缓存（参照 cert_direct/cache.py 模式，TTL 建议 10min——人员台账变动低频但作业票筛查共用同一缓存实例）。
- 不建 PG 表、不建 Bitable 表、不做定时同步。

### 2.3 三组交叉核验（核心价值）

| # | 交叉 | 数据源对 | 产出 |
|---|---|---|---|
| X1 | **保险覆盖** | 408 人（cardNo/name）× 进厂申请单保险有效期（models/contractors.py `保险有效期至` + 准入附件 insurance 列） | 在场人员保险覆盖率、未覆盖/临期（≤30 天）人员清单——把现有周三 08:30 保险预警格从「报备单填报率」口径升级为「**在场实名覆盖率**」口径（P1 拍板） |
| X2 | **特种持证** | 408 人按 workTypeName 分组（电工/焊工/高处等特种工种）× cert 域 `special_op` 表（特种作业证书，含外包人员） | 特种工种人员的持证覆盖率与缺口清单（无证在册=高风险） |
| X3 | **超龄预警** | 408 人 age/joinJobDate | ≥60 岁在场清单（≥55 黄）——工地超龄用工是安监检查实项 |

匹配键优先级：cardNo 精确 > name+contractorName 组合 > name 弱匹配（沿用 personnel_screening 的三级匹配约定与打码展示口径）。

### 2.4 前端（S14 域页）

- 域页新增「在场人员台账」区块（DomainLedgerPage 同页第二表，参照 S6 违章副台账的 secondary 模式）：统计卡 5 张（总人数/承包商数/保险覆盖%/特种工持证率/超龄数）+ 人员表（姓名/承包商/工种/年龄/入场/保险状态/持证状态）。
- 行点击详情 Drawer 复用 detailFields 配置驱动模式。

### 2.5 Agent 工具

`query_contractor_workers(contractor?, work_type?, age_above?, insurance_missing?, cert_missing_only?)` 注册 read_tools——「现场现在有哪些承包商的电工」「保险没覆盖的外包人员名单」直接可答。

### 2.6 边界

不做：人员写入（平台是他们主档）、承包商单位档案展示（空壳）、合同/评价维（S14 既有 Bitable 已有评价子表）。

## 3. 3x-B1 全员主档（1400 人）

### 3.1 定位收敛

**人源字典，不是个人主数据**。dazah 人员主数据仍在飞书（hr/oh/持证表）；平台主档身份证为空，个人级强匹配不可行。三个用途按需启用：

| 用途 | 说明 | 启动时机 |
|---|---|---|
| **岗位字典**（首启用） | 1400 人去重 `postName` = 全厂岗位目录（细到"1#冻干线冻干出料操作工"），dazah 目前无岗位字典——S7 岗位危害因素表、S5 六维度准入、oh 体检分组的岗位对齐都需要 | 随 3x-A3 同批做（一个模块两接口） |
| 分母校准 | S1 核查引擎 D 系指标的人员分母候选（应培训人数/应体检人数） | S1 指标调优时 |
| 体检应检对账 | oh 人员表 vs 1400 主档——应检未登记名单 | oh 域页增强时 |

### 3.2 通道与形态

`GET /api/tiji-system/user/page`（100/页×14 页全量），TTL 缓存（日级）。首期只落**岗位字典**：`service/org_directory.py` 拉取+去重+缓存岗位清单（postName+deptName 映射），API `/safety/contractor-workers/org-posts`（或并入 A3 端点响应）供前端/Agent 查询。个人明细不落库不展示（身份证空+隐私）。

## 4. 3x-B2 风险分区底图资产

### 4.1 定位

**一次性静态资产抓取，不开发任何页面/接口**。64 分区轮廓+名称落 JSON 资产文件，附坐标系说明（本地米制平面坐标、原点随平台 jsmap 底图、无经纬度、无风险等级字段）。未来作业票点位落图/驾驶舱厂区图立项时直接取用，省一次探测。

### 4.2 动作

一次性脚本：拉 64 分区全量（size=100 一页）→ 解析 pointsList 嵌套 JSON → 归一化为 `{distId, distName, rails:[{name, polygon:[[x,y],…]}]}` → 存 `docs/assets/tiji-risk-districts-20261026.json` + 本文档 §4 记录坐标系事实。**不进 git 以外的库表，不建刷新任务**（分区属一次性建模，实测无维护迹象）。

## 9. AI 介入管理（作业票审核同构：定时任务 → 规则判定 → AI 摘要 → 卡片推送 → 复查闭环）

### 9.1 每日承包商在册核验（核心 AI 编排，新增调度任务 `safety.contractor_watch`，每日 08:35 FIXED_TIME）

```
08:35 拉取 408 人（缓存旁路）
   → 规则交叉（纯规则，零 AI）：X1 保险 / X2 特种持证 / X3 超龄
   → 异常按承包商聚合分组
   → AI 摘要（新场景注册，temp 低）：每组一段风险描述+处置建议
     （例：「福清一建在册 12 人：2 人保险 7 天内到期建议催缴；焊工施某证 11 月初到期，
       建议到期前完成复训换证」——引用事实数据，不做定性）
   → 群卡推送（P5 拍板目标群/并入速递）；零异常日单行「✓ 在册核验无异常」
   → 落库：contractor_watch_runs（date 幂等）+ contractor_watch_findings
     （worker_id + finding_type + status['open'|'resolved']）
   → 次日复查（复刻作业票 rectify 模式）：前日 open findings 重比对——
     保险已补/证书已更/人员销户 → resolved；仍在 → 未整改（卡片标注重复天数）
```

红线：AI 只产摘要与处置建议；**不自动清退人员、不写平台、不改台账**——全部人工在平台/线下处置，dazah 只跟踪消除状态。

### 9.2 准入审核联动增强（二期）

既有 contractor_admission AI 审核的 prompt 上下文追加该单位在册交叉摘要（「该单位在册 8 人，2 人保险临期，1 名电工无证在册」）——AI 结论引用实名事实，判定维度仍走准入既有三维度。低成本增强，随 P1 口径切换一并评估。

### 9.3 B2 地点→分区 AI 建议映射（先审后用，S6 要点卡同款）

驾驶舱图卡「未映射 N 处」入口触发批处理：未映射地点清单（近 30 天去重）→ AI 按 64 分区名+厂区常识逐条建议 dist_id + 置信度 → **确认列表页人工勾选确认** → 入 `location_district_map(source='ai_confirmed')`。映射资产只增不改，人工可撤销。

### 9.4 B1 岗位 AI 归一（二期，按需）

1400 个 postName 批量归类到标准岗位族（特种作业相关/危化工艺/一般操作/辅助/管理）→ 人工修正表 → 支撑未来岗位×风险暴露视图。首期不做（A3 的 X2 用平台 workTypeName 已够）。

# v3 细化（2026-10-26）：#2 AI 建议映射 · #4 岗位 AI 归一

两项同构：**AI 批量建议 → 人工确认 → 资产表**，共用一套「AI 资产确认」模式（确认列表组件 + suggestion 中间表 + 确认/忽略 API）。

## 12. #2 地点→分区 AI 建议映射（§9.3 落地细化）

### 12.1 数据流

```
触发（手动：驾驶舱图卡「未映射 N 处」入口 / 系统配置触发；或运维脚本）
  → 收集：扫近 N 天（默认 30）三源（作业票/消防/中控）地点文本
    → 去重 → 减去已映射（location_district_map）与已忽略 → 待建议清单（带出现次数+kinds）
  → AI 建议：分批（20 条/批）调场景 facility_map_suggest（temp 低）
    prompt = 64 分区清单（distId+distName）+ 待映射文本
    输出 JSON：[{text, dist_id|null, confidence: high|mid|low, reason}]
    ——允许 null（无法判断不硬配，§F2 摸底已证 92% 未映射是设备级写法，AI 按厂区常识+分区名近义判断）
  → 落 PG 新表 location_district_suggestions：
    id/location_text/count/kinds/dist_id(可空)/confidence/reason/batch_id/status(pending|confirmed|ignored)/created_at
  → 确认页（图卡入口进入）：列表（文本/次数/kinds/AI 建议分区名/置信度/理由）
    单条确认 / 单条忽略 / 批量确认 high；确认→写 location_district_map(source='ai_confirmed')+suggestion 置 confirmed；
    忽略→下轮收集排除；已 confirmed 的文本永不再出现
  → 幂等：同文本存在 pending/confirmed 记录不重复调 AI；重复触发只处理新增文本
```

### 12.2 要点

- 映射表模型不动（dist_id 非空约束保留），建议可空值放独立 suggestions 表——两表职责分离（建议=过程，映射=资产）。
- 驾驶舱图卡「未映射 N 处」从纯展示升级为入口（点击→确认页路由 `/safety/system?tab=facility-map-confirm` 或图卡内 Modal；建议后者，免新页）。
- 消防 85% 未映射多为「楼栋+部位」写法，AI 命中率预期低于中控；预期单轮新增确认 30-60 词。
- 验收口径：一轮真实批处理+人工确认后，重跑 pins 未映射率显著下降（近 7 天事件口径 <5% 为目标线）。

## 13. #4 岗位 AI 归一（§9.4 落地细化）

### 13.1 标准岗位族（枚举一次定死）

`特种作业相关 / 危化工艺操作 / 一般生产操作 / 质检与实验 / 设备维护 / 物流仓储 / 辅助后勤 / 管理职能 / 其他`

### 13.2 数据流（与 §12 同构）

```
手动批量触发 → org_directory 全量唯一 postName（开工首日摸底唯一数，预估 150-300）
  → AI 场景 org_post_classify 分批归类（30/批）→ JSON [{post_name, family, confidence, note}]
  → PG 新表 org_post_families：post_name 唯一 / family / confidence / note / source('ai'|'manual')
  → 确认页（同 §12 组件复用）：AI 归类即待确认清单，人工可改族后确认（改过置 source='manual'，重跑不覆盖）
  → 消费：org_directory API 响应挂 family 聚合维度（族×人数）；query_org_posts 工具加 family 参数
```

### 13.3 诚实定位

当前直接消费方=Agent 问答与字典维度（「厂里特种相关岗位有哪些」）；岗位×风险暴露视图等更强消费方均已被 10-26 清算丢弃——本项价值是给未来留资产，**排序在 #2 之后**，可与 #2 共用一批开发。
