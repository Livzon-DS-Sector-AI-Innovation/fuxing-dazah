## 1. 一句话认识这个项目

**这是一家制药工厂（原料药事业部）的综合数字化管理平台**：一个 Web 系统（Next.js 前端 + FastAPI 后端 + PostgreSQL 数据库），深度集成了**飞书**（员工在飞书里办公，系统在飞书里推送消息、卡片、机器人对话），并内置了一套 **AI 能力体系**（用大模型做 URS 审核、隐患辨识、入库单识别、知识问答等）。

用三个"角色"来理解它要服务谁：

| 角色 | 他们怎么用这个系统 |
|---|---|
| **车间/职能员工** | 在电脑浏览器里打开 Web 平台，做设备点检、报表查看、流程操作 |
| **一线业务人员**（仓管、QC、安全员） | 主要在**飞书**里工作——发照片给机器人、点卡片确认、在多维表格里填台账 |
| **AI Agent**（智能体） | 通过 MCP 接口调用系统工具，或者作为飞书机器人里的"安全助手"回答问题、代操作 |

三个重要的架构定案（决定了这个项目的"性格"）：

1. **模块化单体**（modular monolith）：所有业务在一个后端进程里，按模块划分代码边界，**不做微服务**。每个模块有独立的数据库 schema、独立的权限声明、明确的协作接口。
2. **飞书是一等公民**：登录用飞书 SSO、消息用飞书卡片、很多业务台账本体就在**飞书多维表格（Bitable）**里——本地数据库部分只是镜像和分析层。
3. **AI 是横向能力**：不是某个模块的专属功能，而是有一套统一的"AI 插件包"模式、审计机制、模型配置中心，横跨 safety、warehouse、toolbox 等多个模块。

├── core/              # 【技术设施层】跟业务无关的底座

**记忆口诀**：`core` 管"怎么跑"，`platform` 管"公共能力"，`modules` 管"业务"，`shared` 管"大家共同的约定"。

### 3.3 应用启动流程（main.py 的 lifespan）

FastAPI 应用启动时会执行一段"生命周期"代码（lifespan），本项目的启动顺序是理解全局的钥匙（见 `backend/app/main.py`）：

1. **配置与日志初始化**：读 `.env.{APP_ENV}`，启动强校验必填项（如 SECRET_KEY、飞书凭证），配不齐直接拒绝启动。
2. **MCP 工具注册**：import 各模块的 `mcp_tools`，把函数注册成 AI 可调用的工具。
3. **启动后台循环**：飞书组织架构同步、设备保养计划等常驻任务。
4. **注册飞书事件回调**：各业务模块向飞书事件分发器注册"我对哪类事件感兴趣"。
5. **建立飞书 WebSocket 长连接**：最多 3 条（平台全局 / HR 独立凭证 / 安全+仓储独立凭证）。
6. **注册定时任务**：统一调度引擎开始按 cron 表达式跑任务。
7. **权限引导（bootstrap）**：扫描所有模块的 `permissions.py`，把权限定义同步进数据库，创建超管角色。

> **为什么要懂这个**：以后排查"为什么定时任务没跑""为什么飞书收不到消息"，第一步就是看启动日志里这几步有没有报错。

### 3.4 一个 HTTP 请求的完整旅程

以"前端请求设备列表"为例，一个请求进来后会经过：

```
浏览器 GET /api/v1/equipment/list?page=1
  │
  ▼ ① AuditMiddleware：生成 request_id（UUID），写访问日志，计时
  │
  ▼ ② 路由匹配：找到 equipment 模块的 api/equipment.py 里对应函数
  │
  ▼ ③ 依赖注入（FastAPI Depends）：
  │     - get_db：开一个数据库会话（请求结束自动 commit/rollback）
  │     - get_current_user：从 Authorization 头解 JWT → 查出当前用户
  │     - require_permission("equipment:inspection:list")：校验权限
  │     - apply_data_scope(...)：按角色数据范围自动加 WHERE 过滤
  │
  ▼ ④ api 层：只做参数校验（Pydantic），调 service 层
  │
  ▼ ⑤ service 层：业务规则编排，调 repository 层
  │
  ▼ ⑥ repository 层：纯数据库读写（SQLAlchemy 查 PostgreSQL）
  │
  ▼ ⑦ 返回：success_response(data) → 统一格式 {code, message, data, meta}
  │
  ▼ ⑧ 全局异常兜底：任何异常都会被 main.py 的 handler 转成统一错误格式
```

**关键设计约定**：
- **api 只管 HTTP，service 管业务，repository 管数据库**——三层职责不许混。
- **统一响应体**：所有接口都返回 `{code, message, data, meta}`（分页信息放 `meta`），前端永远不用猜格式。
- **统一异常**：业务代码里 `raise NotFoundException("xxx 不存在")` 即可，不用手写 404 返回。

### 3.5 业务模块的标准结构

每个业务模块长得都一样（以 equipment 为例，`backend/app/modules/equipment/`）：

```
equipment/
├── __init__.py       # 导出 router（模块对外的唯一门面）
├── api/              # 路由层：只管 HTTP（拆成多个文件，一实体一文件）
├── schemas/          # Pydantic 模型：请求/响应的数据形状
├── models/           # SQLAlchemy ORM：数据库表定义
├── repository/       # 数据库读写：只有 SQL 逻辑，没有业务规则
├── service/          # 业务逻辑编排
├── permissions.py    # 本模块权限声明（启动时被平台自动扫描注册）
├── public_api.py     # 给其他模块调用的稳定接口（跨模块唯一合法入口）
├── mcp_tools/        # 本模块的 AI 工具（@mcp.tool()）
├── feishu/           # 飞书回调注册与通知
└── scheduler.py      # 定时任务定义
```

**三条铁律**：
1. **跨模块调用只能走对方的 `public_api.py`**——不允许 `from app.modules.hr.models import ...` 这种穿透式 import，保证模块边界。
2. **单文件超过约 300 行就拆成同名目录**（如 `api.py` → `api/` 目录）。
3. **所有模块在 `app/shared/module_registry.py` 注册**（模块代码、中文名、数据库 schema、负责人），这个注册表驱动了数据库 search_path、权限自动发现等一堆机制。

### 3.6 数据库设计：多 schema 架构

这是本项目数据库设计的最大特色：

- **每个业务模块独占一个 PostgreSQL schema**（不是每个模块一个数据库）。比如 equipment 模块的表都在 `equipment.` schema 下，safety 的在 `safety.` 下。
- ORM 模型里写法：`__table_args__ = (..., {"schema": "equipment"})`。
- 数据库连接时通过 `search_path = public,identity,permission,production,equipment,...`（见 `core/database.py`）让所有 schema 对应用可见。
- **所有表都有统一基类** `app/shared/base_model.py` 的 `BaseModel`：UUID 主键、创建/更新时间、创建/更新人（外键到 identity.users）、`is_deleted` 软删除标记。

**表结构变更（migration）怎么做**：改完 `models/` 里的 ORM 类后，运行 Alembic 生成迁移脚本（`backend/alembic/versions/` 下一个 Python 文件），部署时自动执行 `alembic upgrade head`。注意 safety 模块有自己独立的迁移目录（`app/modules/safety/migrations/`，从旧仓库合并而来），在 `alembic.ini` 里单独注册。

> **名词卡——schema**：PostgreSQL 里数据库（database）内可以分多个"命名空间"叫 schema，每个 schema 下有自己的表集合。本项目用它做模块间的物理隔离，比"所有表堆在一起加前缀"干净得多。

### 3.7 认证与权限：飞书 SSO + JWT + RBAC

**登录流程**（`app/platform/identity/`）：

```
用户在浏览器点"飞书登录"
  → 跳转飞书授权页 → 飞书回调 /auth/callback
  → 后端拿授权码换飞书用户身份 → 找到/创建本地用户（identity.users）
  → 用 SECRET_KEY 签发本地 JWT（有效期默认 24 小时）
  → 前端存 token，之后每个请求带 Authorization: Bearer <token>
```

- **JWT（JSON Web Token）**：一个自包含的签名令牌，后端不用存 session，解签就能知道"这是谁"。
- **代理登录（impersonate）**：管理员可以签发一个"以别人身份"的 JWT，用于排查"为什么他看不到这个功能"这类问题。

**权限模型**（`app/platform/permission/`）：带数据范围的 RBAC。

- **RBAC（基于角色的访问控制）**：用户 → 角色 → 权限。权限编码格式 `模块:资源:动作`，如 `warehouse:material:create`。
- **自动注册**：每个模块在自己的 `permissions.py` 里声明权限列表，平台启动时自动扫描汇总入库——加权限不用去后台配置。
- **数据范围（data_scope）**：角色可限定"只能看自己 / 本部门 / 本部门及子部门 / 全部"，由 `apply_data_scope()` 在查询时自动注入 WHERE 条件，业务代码无感。
- **Redis 缓存**：用户权限集缓存进 Redis，Redis 挂了自动降级直查数据库。

### 3.8 定时任务：自研统一调度引擎

本项目**没有用** APScheduler 这类现成库，而是自研了一个引擎（`app/platform/scheduler/`）：

- `SchedulerEngine`：一个单 asyncio 循环（每秒 tick 一次），驱动所有注册的任务。
- 三种调度策略：**CRON**（cron 表达式，用 croniter 库求值）、**INTERVAL**（固定间隔）、**FIXED_TIME**（每天固定时刻，如每天 08:00）。
- 任务两种来源：代码里注册的零参协程任务（`TaskDefinition`），或数据库驱动的动态扫描器（`TaskGenerator`）。
- 时区统一 Asia/Shanghai。

> 项目里还有少量旧式"模块内 while True 循环"（如 `safety/scheduler.py`）与统一引擎并行运行，属于渐进迁移状态——**新任务一律注册到统一引擎**。

### 3.9 与飞书的集成（重点）

飞书集成分"平台级"和"模块级"两种凭证：

| 层级 | 凭证 | 用途 |
|---|---|---|
| 平台级 | `FEISHU_APP_ID/SECRET` | SSO 登录、通讯录同步、全局通知（`platform/integrations/feishu/`） |
| 模块级 | `SAFETY_FEISHU_*`、`WAREHOUSE_FEISHU_*` 等 | 安全助手机器人、仓储机器人各自独立应用，互不干扰 |

核心机制（`backend/app/modules/safety/feishu/event_client.py` 是最完整实现）：

1. **事件订阅不用飞书官方 SDK 的 WS 客户端，而是自研 WebSocket 长连接**：原生 `websockets` 库 + 协议握手，换取 WS URL 后保持连接，飞书把"有人给机器人发消息了""表格里有条记录变了"等事件实时推过来。
2. **`@on_event(事件类型)` 装饰器**：各业务 handler 在 import 时自动注册，启动时 import 一遍即可生效。
3. **失败处理**：handler 失败重试 3 次（间隔退避 1s/2s），仍失败则节流告警管理员（每类每小时最多一次）。卡片按钮回调**不重试**——飞书要求 2.9 秒内响应，超时就算了。
4. **卡片交互模式**："纯 ACK + PATCH 原卡"——收到按钮点击后立刻 ACK，再通过 API 更新卡片内容（直接在回调里返回新卡片不生效，这是踩过的坑）。
5. **多维表格（Bitable）客户端**：封装了批量读（search）、记录增改、建列等操作；写操作**必须串行**（飞书限制单表不支持并发写）。

### 3.10 MCP：给 AI Agent 的另一扇门

**MCP（Model Context Protocol，模型上下文协议）** 是一个开放协议，让大模型 Agent 能够以标准方式调用外部工具。

本项目的实现（`app/platform/mcp/`）：

- 用 **FastMCP** 库，把模块函数包装成 MCP 工具，以 ASGI 方式挂载在 `/mcp/production`、`/mcp/warehouse` 等路径。
- 认证：`MCP_AGENT_API_KEYS` 环境变量配置 API Key 列表，请求头 `api-key` 校验——这是**服务对服务**的认证，跟用户 JWT 是两套体系。
- 设计原则：**MCP 工具往往是只读查询**（如 warehouse 的 `query_mcp.py` 只注册了 4 个只读查询），写操作留在飞书机器人里走人工确认——防止 AI 绕过确认门直接改台账。

### 4.2 AI 插件包模式（本模块最重要的代码范式）

所有 `ai_*` 子包都长一个样，这是本项目 AI 功能的**标准姿势**：

```
ai_urs_review/
├── schemas.py       # 输入/输出的强类型 Pydantic 模型
├── prompts.py       # 所有提示词集中在这（代码里不散落 prompt 字符串）
├── rules.py         # 业务规则兜底：代码强制优先于 AI 输出
├── plugin.py        # 若干可独立测试的 Plugin 类，统一契约 run(input) -> output
└── orchestrator.py  # 编排器：service 只调它，它再按顺序调各 Plugin
```

设计要点（这些思想适用于全项目所有 AI 功能）：

1. **AI 只做判断，不做决定**：评分等级计算、否决项强制不合格这类关键结论由**代码**算，AI 只负责理解文本、写摘要。规则在 `rules.py` 里做最后一道兜底（清洗枚举值、强制覆盖）。
2. **低温度（temperature=0.05）**：保证同样输入出同样结果，审核场景要可复现。
3. **所有 AI 调用都走 `AuditedAIService`**（`ai_audit/`）：自动记录每次调用的模型、token 用量、耗时到审计表；主模型故障自动降级到备用模型；内置防注入守卫（防止文档内容里藏指令劫持 AI）。
4. **AI 输出解析失败有自动修复**：如大模型返回的 JSON 被截断时，有截断 JSON 状态机修复逻辑（`ai_urs_review/plugin.py` 的 `_repair_truncated_json`）。
5. **"AI 依据不足 → 转人工"是合法出口**：插件抛 `UnknownValueError` 语义化表达"这个我看不准"，业务流程转人工复核。

### 4.3 URS 智能审核（四步流水线）

**URS = User Requirement Specification（用户需求规格书）**：制药企业买设备前，使用部门写的需求文档。本模块做的是对 URS 的 **EHS 合规审查**。

业务流转（`service/ehs_change/urs.py` 状态机）：

```
草稿 draft → 提交 submit
  → Step1 风险画像评估（confidence < 0.8 则转人工复核）
  → Step2 标准适配（匹配适用条款，否决项由代码强制标记）
  → Step3 逐条审核（AI 预填 + 人工确认）
  → Step4 结论生成（评分 = 通过项/适用项 × 100；A≥90 / B≥75 / C≥60 / D<60）
  → 通过 approved / 驳回 rejected（可申诉 appeal，重跑 Step1+2）
```

四步流水线对应的四个 Plugin（`ai_urs_review/`）：

| Plugin | 干什么 |
|---|---|
| `RiskProfileAssessor` | 五维风险画像：机械/电气/数据/环境/化学 + 总体 + 置信度 |
| `StandardAdapter` | 把内置标准条款库（30~40 条，含 4 类**否决项**）适配到该设备 |
| `ItemReviewer` | 逐条审核：通过/不通过 + 整改建议 |
| `ConclusionGenerator` | 算分定级（代码算），AI 只写结论文本 |

配套：审核报告导出 PDF（`service/ehs_change/urs_pdf.py`）、飞书卡片交互（`feishu/urs_card.py`）、机器人菜单点击后 30 分钟内的"上传上下文"（`feishu/urs_upload_context.py`，解决同名文件归属歧义）。

### 4.4 多维表格"直读"设计（理解本模块架构演进的关键）

**背景**：业务人员习惯在飞书多维表格（Bitable）里填台账（隐患表、特殊作业表……）。旧链路是"表格记录变更事件 → 同步镜像到平台数据库"，问题是镜像经常不一致。

**新设计（直读）**：不镜像了，**业务运行时直接读 Bitable + 内存里判定 + 只回写结果列**。公共底座在 `service/bitable_direct/`：

| 文件 | 职责 |
|---|---|
| `gates.py` | 环境变量开关（`SAFETY_<域>_DIRECT_ENABLED` 等），默认全关=行为与旧链路一致，**一键回滚** |
| `reader.py` | 只走批量 search 接口（禁逐条读——实测单条读 4~5 秒），500 条/页 + 页数上限防死循环 |
| `writer.py` | 串行回写 + 字段 ID 缓存 + 幂等建列（飞书单表写不支持并发） |
| `locks.py` | Redis 分布式锁，防止两条记录同时被处理 |
| `filters.py` / `fields.py` | 过滤条件构造、各种字段类型（人员/单选/富文本）取值原语 |

已迁移直读的域：**隐患系统**（`hazard_direct/`）、**特殊作业日报**（`special_op_direct/`）、消防报警（`fire_alarm/`）。

### 4.5 特殊作业日报

**特殊作业**：制药/化工行业的高风险作业八大类——动火、受限空间、高处、吊装、临时用电、动土、断路、盲板抽堵。

每日两次（08:00 / 17:00）执行"**直读 → 判定 → 分组 → 渲染 → 推送**"五步（`service/special_op_direct/daily.py`）：

1. 直读飞书"全厂特殊作业一览表"；
2. **规则引擎**判定每条作业的风险等级（作业类型关键词推断、特级/一级分级、夜间/周末加权），**AI 只做增强解读**；
3. 按车间/风险分组渲染成"速递卡"（折叠布局，构建失败自动回退旧长卡）；
4. 推送到管理群，并把"日报风险等级（AI）"回写表格列。

### 4.6 法规知识库 RAG 与法规爬虫

**knowledge/（RAG 检索增强生成）**——让 AI 回答问题时有法规原文可依：

```
用户提问
  → Layer 1：实体抽取 + 知识图谱导航，先圈定可能相关的法规条款范围
  → Layer 2：混合检索
       ├─ 向量检索（NumPy 内存矩阵余弦相似度，2048 维 × ~2100 个文本块；
       │   当前规模刻意不用 pgvector，超过 10 万块再换）
       └─ BM25（经典关键词检索算法，字符 bigram 实现）
     → RRF 融合（两路结果按排名合并，k=60）
     → reranker 重排（用重排模型精排）
  → 注入法规上下文 → 大模型生成带出处的回答
```

配套：文档从飞书 Drive 下载解析 → 切块入库（`regulation_chunks` 表）→ 向量化。带全局并发闸门和三级降级（向量 → PG 全文 → 空）。

**regulation_crawler/**——自动盯梢各部委官网新法规：策略模式三种爬虫（API 直连 / HTTP 解析 BeautifulSoup / **Playwright 无头浏览器**，后者专门对付有 JS 反爬挑战的站点），AI 管线做分类、信息提取、行业相关性评估、新旧版本变更对比，结果写入 Bitable → 推送飞书卡片 → 进 RAG 知识库。

### 4.7 飞书"安全助手"业务 Agent

`business_agent/` + `feishu/business_agent_bot_handler.py`：机器人收到私聊消息后，**所有**对话都进入一个 pydantic-ai 驱动的业务 Agent，由它决定调哪个工具（查隐患、URS 审核、职业健康、日报查询、办公操作……）。

- **工具分层**：读工具（查询类）、写工具（必须过确认卡）、办公工具（读写表格/文档）。
- **"软硬分离"约定**：人设、语气写在 `agent.md`（软约束，随便改）；权限护栏、危险操作拦截写在 `permissions.py` / `rules.py`（硬约束，代码强制）。
- 带会话记忆压缩（长对话自动摘要）和长期记忆子系统（`safety/memory/`）。

## 5. 仓储模块（warehouse）详解

> 仓储模块是"飞书 + Bitable + AI"三件套最极致的应用。**理解它先记住一句话：飞书是操作端，Bitable 是台账权威，本地平台是分析展示与对账层。**

### 5.1 核心架构定案

来自《仓储V3.0设计方案》（`docs/仓储V3.0设计方案.md`）：

1. **审批 = 飞书确认卡二值确认**（确认/取消），不做审批流引擎。
2. **Bitable 是台账权威（source of truth）**：出入库台账本体在飞书多维表格里；本地 PostgreSQL 只存镜像和分析数据。写路径永远是"**先写 Base，成功后落本地镜像**"（`bitable_adapter.py` / `base_mirror.py`）——Base 写失败则整体失败、本地零变更。
3. **对账 Base 胜出**：每日对账引擎（`reconciliation.py`）比对此地库存与 Bitable 台账，发现差异以 Bitable 为准生成修复动作。
4. **手机端走飞书**，不做独立 Web 移动端。

本地数据库里的主要实体（`models.py`，`warehouse` schema）：

| 实体 | 说明 |
|---|---|
| `WarehouseMaterial` | 物料主数据（原料/辅料/包装/中间体/成品五类，含安全库存） |
| `WarehouseStock` | 现有库存（物料+批次+库位唯一；状态 normal/quarantine/frozen；含效期） |
| `WarehouseMovement` | 出入库流水（数量恒为正，方向用 inbound/outbound/adjust 区分） |
| `WarehouseMovementPlan` | 出入库计划单（planned → in_progress → completed；计划单本身不直接动库存） |
| `WarehouseStocktake` | 盘点单（草稿可改，确认后调库存并生成调整流水） |
| `WarehouseQcStatus` | QC 状态**只读镜像**（权威在 Bitable，本表只用于列表展示） |
| `WarehouseConfirmRequest` | 确认门（pending → confirmed/cancelled/expired 状态机） |

### 5.2 入库识别流水线（AI Agent 的代表场景）

仓管员在飞书里给机器人发一张**送货单照片**，之后发生：

```
recognizer.py   视觉模型识别送货单图片 → 物料名/数量/批号等结构化数据
  ↓
aligner.py      物料名对齐主数据（纯确定性算法，不用 AI：
                ERP 编码精确匹配 > 名称归一化 > 前缀匹配 > difflib 相似度）
  ↓
draft_flow.py   识别结果落库为"草稿"，推送确认卡（草稿有状态机，
                每次状态迁移写审计；超时自动过期）
  ↓
用户点"确认" → submit.py 组装字段写入 Bitable material_receipt 台账
             → 先 Base 后镜像，本地落库存镜像
```

> **注意 aligner 的设计选择**：能用确定性算法的地方就不用大模型——对齐是"物料名 vs 主数据表"的匹配问题，规则算法更快、更稳、可解释。

### 5.3 QC 请验放行闭环（模块的旗舰流程）

原料/辅料到货后必须经质量控制（QC）检验合格、质量受权人（QA）放行才能用于生产。系统闭环：

```
入库确认 → 自动推 QC 群"到货请验"卡
  → 每 60 分钟扫描：取样/出报超期自动提醒
  → QC 出报合格 → 推 QA 确认门卡片 → QA 点确认
  → 回写 Bitable 放行字段 → 推仓库群"可上架"
  → （不合格 → 生成不合格处理确认门）
```

全流程状态经 `WarehouseQcStatus` 镜像到本地，供驾驶舱/列表展示（只读）。

### 5.4 领料 FIFO 与对话式出库

**FIFO（First In, First Out，先进先出）**：先入库的批次先领用，防止物料过期。对话式领料流程（`agent/tools/picking.py`）：

```
仓管员对机器人说："精制一部领料 XXX 500Kg"
  → 读 material_stock 中该物料 QA 放行的批次
  → 按入库日期升序生成 1..N 个批号建议（500Kg 不够一个批次时自动跨批拆分）
  → 仓管员点确认门 → 写入 material_outbound 台账
```

类似的还有 GMP 出库登记（`agent/tools/gmp.py`）、成品出库（`finished.py`，确认后自动推发货通知）、供应商准入（`supplier.py`，QA 确认门）。共性模式：**缺字段 AI 追问 → 草稿 → 确认卡 → 先 Base 后镜像**。

### 5.5 确认门、推送中心与兜底闭环

- **确认门（`confirm_request.py`）**：全模块复用的"二值确认"基建——任何写操作前先创建确认请求，推送卡片，用户点了才执行；带过期和完整审计。
- **推送中心（`push_center/`）**：统一的订阅式推送基建（晨报 08:00、效期冻结 00:15、库存快照 00:30、异常扫描 00:45……），单泵轮询引擎 + 推送日志表。
- **智能分析（`intelligence.py`）**：预警规则、异常检测、补货建议——**规则先行，LLM 只负责解读文案**，模型挂了规则照常出结果。

### 6.2 读写分离的数据流（前端最重要的概念）

Next.js 的 App Router 里组件分两种，本项目据此制定了严格的读写分流规则：

| | **Server Component（服务端组件）** | **Client Component（客户端组件）** |
|---|---|---|
| 是什么 | 在服务器上渲染好再发 HTML 的组件（page.tsx 默认是这种） | 标了 `'use client'` 的组件，跑在浏览器里 |
| 适合 | 拉初始数据、布局组装 | 有交互（点击/表单/状态）的部分 |
| 本项目规则 | **读数据**：直接调 `lib/api/` 的 fetch 函数 | **交互数据**：用 React Query 调同一套 `lib/api/` |
| 写数据 | ✗ 不允许 | **必须走 `actions/` 里的 Server Action**，禁止客户端直接 fetch 写接口 |

一个典型页面的数据流：

```
读：page.tsx (Server) → lib/api/warehouse.ts 的 fetchXxx() → 后端 GET /api/v1/...
写：用户点按钮 → actions/warehouse.ts 的 Server Action（'use server'）
    → 调 lib/api → 后端 POST → 成功后 revalidatePath() 让页面重新拉数据
```

**Zustand vs React Query 怎么选**：服务端数据（列表、详情）用 React Query（自带缓存/重试/失效刷新）；真正的客户端 UI 状态才用 Zustand。仓储模块甚至做到了"零全局状态"——全靠 React Query + 组件局部状态。

### 6.3 类型契约：后端改了接口，前端怎么知道？

```
后端 FastAPI 自动生成 openapi.json（接口说明书）
  → pnpm generate:api（scripts/generate-api.mjs，openapi-typescript）
  → 生成 src/types/generated/schema.ts（全部接口的 TypeScript 类型）
  → 前端新代码一律从这里 import 类型，不再手写接口返回值类型
```

这是手写 fetch 封装（没生成 HTTP client 库）+ 生成类型的组合——请求逻辑保持直观可控，类型又有单一代码事实源。

### 6.4 前端工程规范速记

## 8. 工程规范与协作边界

1. **模块边界**：跨模块调用只走 `public_api.py`（后端）/ `index.ts`（前端组件）；禁止穿透 import。
2. **质量基线**：全仓 mypy 与 ruff 基线本就不干净，改动验收口径是"**对照基线零新增**"问题。
3. **时间**：一律用 `app.core.time` 的 `now()/today()`（Asia/Shanghai），禁止裸 `datetime.now()`（防止服务器 UTC 导致 8 小时偏移）。
4. **响应/异常**：接口返回统一走 `success_response`/`error_response`；业务错误 raise `AppException` 家族。
5. **AI 功能五条军规**：prompt 集中在 `prompts.py`；关键结论代码兜底；温度 0.05；调用必过审计客户端；"依据不足转人工"是合法出口。
6. **写 Bitable**：串行写、幂等建列、失败可回滚（gates 开关体系）。
7. **提交 PR 到 main 前**：先把当前分支更新到最新再提 PR（根 CLAUDE.md 规定）。

### 9.4 后端技术名词（小白详解版）

#### Web 框架与运行

- **FastAPI**：Python 目前最流行的 Web 框架。你只需写普通函数、标好参数类型，它就自动完成"接收请求 → 校验参数 → 调你的函数 → 返回 JSON"，还免费生成在线接口文档（`/docs` 页面）。
  比喻：餐厅服务员——客人点单（请求），它核对菜单（参数校验），把单子递给后厨（业务代码），再把菜端出去（响应）。
- **uvicorn / ASGI**：FastAPI 写好的应用自己不会"开门营业"，要靠服务器软件跑起来。ASGI 是 Python 异步服务器的行业标准"插座"，uvicorn 是符合这个标准的"电器"。生产环境就是 `uvicorn app.main:app` 这样把系统跑起来的。
- **async / await（异步编程）**：普通代码"一行干完才干下一行"；异步代码在"等数据库回复、等飞书接口返回"这种纯等待的时刻，先转去处理别的请求，结果回来再继续。
  比喻：烧水时不盯着水壶，先切菜，水开了再回来泡茶。
  本项目从数据库到飞书调用全链路异步，一个进程就能同时服务大量请求。
- **lifespan（生命周期钩子）**：应用"开机/关机"时自动执行的一段流程。开机时按顺序拉起定时任务、飞书长连接、调度器；关机时逐个关闭。
  比喻：商场开店——开门前开灯、开电梯、启动收银；打烊时逐个关掉。

#### 数据库

- **ORM（SQLAlchemy）**：Object-Relational Mapping，不直接写 SQL 语句，而是用 Python 类/对象操作数据库表，SQL 由它代为翻译。
  比喻：SQL 是自己开车去仓库搬货；ORM 是雇了搬运工，你说要什么他帮你搬。
  本项目所有表定义在 `modules/*/models/`，用的就是 SQLAlchemy 2.0。
- **Pydantic**：用"类型标注"做数据校验的库。声明"姓名是字符串、库存必须 ≥ 0"，不符合的数据直接拦下。FastAPI 的参数校验和本项目所有接口的请求/响应模型都靠它。
- **事务（transaction）**：一组数据库操作"要么全成功、要么全失败"，不许做一半。
  比喻：转账 = 扣你的钱 + 加对方的钱，必须捆绑发生。
  本项目每个请求结束自动提交（commit），出错自动回滚（rollback）。
- **schema（数据库命名空间）**：PostgreSQL 里数据库内还能再分层，每层叫一个 schema，各有各的表。本项目每个业务模块一个 schema（`equipment.`、`safety.`……），物理隔离，谁也碰不脏谁。
- **Alembic / migration（迁移）**：数据库表结构的"版本管理（git）"。改了代码里的表定义，就生成一个迁移脚本记录"这次给 users 表加了手机号列"；部署时按顺序执行，生产库自动长成和代码一致的样子。
- **软删除（soft delete）**：删除不真删，只把 `is_deleted` 标成 true。
  比喻：图书馆下架的书不销毁，只是挪去地下库，要用时还能找回。
  本项目所有表默认如此，可审计、可恢复。
- **UUID 主键**：每条记录的唯一"身份证号"（如 `86c012a0-0aed-...`），随机生成。不用 1、2、3 自增数字的好处：不暴露"你有多少数据"，分布式场景也不会撞号。
- **asyncpg / psycopg**：Python 连 PostgreSQL 的"网线"（驱动）。asyncpg 配异步引擎用，psycopg 用于同步脚本（初始化、数据修复）。

#### 认证与权限

- **JWT**：登录成功后服务器发你一张"防伪手环"（一段带签名的长字符串），之后每个请求出示手环，服务器验签就知道你是谁，不必反复查密码。本项目 HS256 签名、24 小时过期。
- **SSO（单点登录）**：一次登录处处通行。本项目点"飞书登录"直接进平台，不用再记一套账号密码。
- **RBAC（基于角色的访问控制）**：权限不直接发给个人，而是发给"角色"，人再领取角色。
  比喻：公司不给每个人单发"能进财务室"的许可，而是设"财务岗"，上岗自动有对应门禁。
  权限编码格式 `模块:资源:动作`，如 `warehouse:material:create`。
- **数据范围（data_scope）**：比"能不能用功能"更细一层——"能用，但能看哪些数据行"（仅本人 / 本部门 / 部门及子部门 / 全部）。查询时自动加过滤条件，业务代码无感。
- **impersonate（代理登录）**：管理员以他人身份登录。用于排查"为什么他看不到这个功能"——用他的视角复现问题。
- **依赖注入（DI）**：在函数参数里声明"我需要一个数据库会话和当前用户"，框架看到声明就自动准备好塞进来。
  比喻：酒店前台，你说要毛巾和矿泉水，不用自己去仓库搬。
- **中间件（middleware）**：所有请求都要排队经过的"安检门"。本项目两道：CORS（放行跨域请求）和 Audit（发 request_id、记访问日志）。
- **request_id（链路追踪）**：每个请求进门时领一个唯一编号，它产生的所有日志都带这个编号。出问题时拿编号一搜，这个请求从头到尾干了什么一目了然。

#### 缓存、存储与任务

- **Redis**：存在内存里的超高速"便签本"，放需要频繁读的小数据（用户权限、运行配置），比查数据库快得多。
- **分布式锁**：多个进程抢做同一件事时，先到 Redis 抢一把"钥匙"（`SET NX`），抢到的才干活，干完归还。
  比喻：公共更衣柜的钥匙，同一时刻只有一人能用。
  防止两条相同的记录被重复处理。
- **MinIO / S3（对象存储）**：专门存文件（图片、PDF、附件）的仓库服务。S3 是亚马逊定的接口标准，MinIO 是可自建的开源实现。本项目浏览器不直连 MinIO，一律走后端中转，权限可控。
- **cron / croniter**：cron 是 Linux 世界的定时任务表达法（`0 8 * * *` = 每天 8 点），croniter 是 Python 里解析它的库。统一调度引擎用它驱动所有定时任务。
- **状态机**：把业务建模成"有限的几个状态 + 规定好的跳转路径"。
  比喻：红绿灯只在固定几种颜色间切换，不可能从红灯直接跳紫灯。
  URS 审核、入库草稿、确认门都用它，防止"没审核就想通过"这类乱序操作。
- **EventBus（事件总线）**：程序内部的"广播站"——有人发布消息，订阅的人自动收到，模块之间不用互相直接拉扯。
- **幂等（idempotent）**：同一操作做一次和做多次，结果一样。
  比喻：电梯按钮按十次也只来一部电梯。
  网络可能重试、任务可能补跑，接口设计成幂等才安全（如"列已存在就跳过"的建列）。
- **Protocol（结构化接口）**：Python 的类型约定：不看你"是谁"，只看你"会不会这些动作"（有没有这些字段/方法）。直读服务用它把"数据从哪来"和"怎么判定风险"解耦。

#### 可观测与运维

- **日志分级**：DEBUG（细节流水）/ INFO（正常运转）/ WARNING（可疑）/ ERROR（出错）。生产只看 INFO 以上，深挖问题时再开 DEBUG。
- **Loki / Grafana**：日志的"集中仓库 + 仪表盘"。各容器日志统一收进 Loki，在 Grafana（3200 端口）里搜索、画图。
- **JSON Lines**：生产环境的日志格式——一行一条 JSON，机器好解析、程序好统计。

### 9.5 前端技术名词（小白详解版）

#### 框架与渲染

- **React / 组件（component）**：React 把页面拆成一个个可复用的"积木"（组件）：一个按钮、一张表格、一个页面都是组件。数据一变，用到它的积木自动重绘，不用手动改页面。
- **Next.js**：React 的"全家桶框架"。React 本体只管画界面；路由、服务端渲染、打包优化这些工程问题由 Next.js 统一解决。本项目用它的 App Router 模式（版本 16）。
- **App Router（目录即路由）**：Next.js 的路由约定——`src/app/` 下建文件夹就是建页面。`app/(dashboard)/warehouse/board/page.tsx` 自动对应网址 `/warehouse/board`，不用手工注册路由。
- **Server Component（服务端组件）**：在服务器上渲染好、再发给浏览器的组件。它可以直接安全地调后端取数，代码不会发给用户电脑。
  比喻：厨房把整道菜做好端上桌，而不是寄半成品让客人自己炒。
  本项目 `page.tsx` 默认就是它。
- **'use client'（客户端组件）**：声明"这个组件要在浏览器里跑"。只有需要处理点击、表单输入、动效的组件才加这个标记。
- **React Compiler**：React 19 自带的编译器，自动做渲染性能优化，不用再手写 memo / useMemo 这类优化代码。

#### 数据流（本项目前端的核心规则）

- **Server Action**：写在服务端的函数，浏览器组件里却能像调普通函数一样调它。它是本项目**所有写操作（增/删/改）的唯一合法通道**，改完数据顺手调 `revalidatePath()` 刷新页面。
- **revalidatePath（缓存作废）**：告诉 Next.js"这个页面的数据过期了，下次访问重新拉最新"。改完数据不调它，用户看到的还是旧数据。
- **React Query（TanStack Query）**：专门管理"从服务器拿来的数据"的库：自动缓存、失败自动重试、数据过期自动重新拉。
  比喻：秘书替你记住所有问过后端的结果，记在本子上（缓存），到时间或数据变了自动帮你重新问。
  本项目客户端组件取数一律用它。
- **Zustand**：轻量的"全局状态仓库"——多个组件都要共享的记忆（当前选中的标签、弹窗开关）放这里。本项目用得很克制：服务端数据交给 React Query，Zustand 只放真正的界面状态。
- **SSE（Server-Sent Events）**：服务器到浏览器的"单向推送水管"：连接建立后服务器随时推消息过来。Web 端 Agent 对话逐字输出回答用的就是它。

#### UI 与样式

- **antd（Ant Design）**：蚂蚁开源的企业级 React 组件库。表格、表单、弹窗、日期选择器都是现成的，风格统一、开箱即用，本项目 UI 以它为主（V6）。
- **Tailwind CSS**：不写传统 CSS 文件，把样式"单词"直接拼在标签的 class 上：`class="mt-4 text-sm text-gray-500"` = 上边距 16px、小字号、灰色。
  比喻：从"按句写作文"变成"按词堆乐高"。
- **design token（设计令牌）**：把颜色、字号、间距定成一套有名字的标准值（如主色叫 `primary`），全站引用同一套，改一处全局生效。规范在 `frontend/DESIGN.md`。
- **ECharts**：成熟的图表库，折线图/柱状图/饼图几行配置出一张。驾驶舱和报表用它。

#### 类型与工程

- **TypeScript / 类型**：给 JavaScript 加"类型说明书"。普通 JS 里你以为拿到字符串其实是数字，要到运行时才炸；TS 在写代码和编译时就报错拦截。
- **openapi.json / openapi-typescript**：后端 FastAPI 自动生成"接口说明书"（openapi.json），openapi-typescript 把它翻译成 TypeScript 类型文件（`types/generated/schema.ts`）。后端一改字段，前端用到处的类型检查立刻标红——不用等上线才发现对不上。
- **vitest / Testing Library**：测试运行器 + 组件测试工具。Testing Library 模拟真实用户：渲染组件 → 模拟点击"提交" → 断言页面出现"成功"。本项目前端测试与源码同目录（`xxx.test.tsx`）。
- **happy-dom**：在 Node 里模拟出的"假浏览器"，让组件测试不用真开浏览器就能跑。
- **pnpm**：Node 的包管理器（npm 的现代替代品），安装快、磁盘省（所有包全局存一份，项目里放链接）。
- **NEXT_PUBLIC_ 前缀**：Next.js 规则——只有 `NEXT_PUBLIC_` 开头的环境变量会被打包进浏览器代码，其余只在服务端可用。数据库密码这类敏感配置绝不能加这个前缀。

### 9.6 开发通用名词（补充）

#### 接口与数据格式

- **API（接口）**：Application Programming Interface，程序之间约定好的"服务窗口"：你按约定发请求，它按约定回数据。本项目前后端之间、后端与飞书/大模型之间都靠 API 通信。
- **HTTP / HTTPS**：浏览器与服务器之间的通信协议（HTTPS 是加密版）。每次网页加载、每次接口调用都是一次 HTTP 请求。
- **GET / POST / PUT / DELETE**：HTTP 的四个"动作词"——读数据（GET，无害可重复）、新建（POST）、更新（PUT）、删除（DELETE）。本项目读接口走 GET，写操作统一由 Server Action 转成 POST 调后端。
- **状态码（200 / 401 / 403 / 404 / 500）**：HTTP 请求的"回执编号"：200 成功；401 没登录或令牌过期（先想到重新登录）；403 有身份但没权限；404 找不到资源；500 服务器内部出错。
- **REST / RESTful**：一种 API 设计风格："网址指资源、动作词表操作"。如 `GET /api/v1/warehouse/stocks` = "列出库存资源"。本项目接口基本按这个风格设计。
- **JSON**：程序间传数据的事实标准格式，长这样：`{"name": "许康福", "roles": ["admin"]}`。本项目所有接口进出、AI 返回的结构化结果都是 JSON。
- **YAML**：另一种配置文件格式，用缩进表达层级（`docker-compose.yml` 就是）。
- **序列化 / 反序列化**：内存里的对象与可传输文本（JSON）互相翻译。接口返回数据叫序列化，解析收到的 JSON 叫反序列化。
- **Webhook**："有事我主动通知你"。对方发生事件时，主动向你预留的网址发一个 POST 请求。飞书事件推送、法规爬虫的接收端都属这类。

#### 版本管理与协作

- **Git**：代码的"时光机 + 分身术"。每次提交（commit）是一个存档点，可随时回看、回滚。
- **分支（branch）/ 合并（merge）**：分支是从主线分出的"平行世界"，在里头开发新功能不影响主线；开发完合并回主线。本项目主线是 `main`，开发在 `feature/xxx` 分支。
- **PR（Pull Request）**："我改完了，请审查并合并"的正式申请，同事可以逐行评论提意见。本项目规定：提 PR 前先把分支更新到最新。
- **Code Review**：别人通读你的代码、提修改意见的环节，质量把关与知识共享的双重保险。
- **冲突（conflict）**：两条分支改了同一处代码，合并时 git 无法自动决定听谁的，需要人工裁决。

#### 构建与部署

- **环境变量**：给程序传配置的"外部开关"（数据库地址、各种密钥），不写死在代码里，开发/生产各一套。本项目用 `.env.development`、`.env.{APP_ENV}` 文件管理。
- **Docker / 镜像 / 容器**：镜像 = 装好系统和全部依赖的"系统盘"（只读模板）；容器 = 用系统盘启动的"运行实例"。
  比喻：镜像是菜谱加备料，容器是照着做出的一盘菜——在哪台机器做味道都一样，彻底解决"我本地好好的，服务器跑不起来"。
- **docker compose**：用一个 YAML 文件描述"要开哪几个容器、怎么连"（本项目：app + db + redis + minio + 日志栈），一条命令全部起停。
- **构建（build）/ 打包**：把源代码加工成可运行产物。前端 `pnpm build` 产出优化后的静态文件；后端装好依赖准备运行。
- **CI/CD**：持续集成/持续部署——提交代码后机器人自动跑检查、测试甚至部署（本项目配置在 `.github/`）。
- **端口（port）**：一台服务器上的"门牌号"。本项目 8000 是后端、3200 是 Grafana，访问时指明找哪扇门。

#### 质量工具

- **包管理器 / 依赖**：依赖（dependency）= 项目用到的别人写的库；包管理器负责自动下载、升级、锁定版本（后端 uv，前端 pnpm）。
- **语义化版本号**：`1.4.2` 三段数字 = 大改（不兼容）. 加功能 . 修 bug。看版本号就知道升级风险。
- **lint（ruff / eslint）**：代码"体检仪"——不查逻辑，专查风格和低级错误：没用到的变量、import 顺序不对、过时写法。
- **类型检查（mypy / tsc）**：在运行前静态检查"类型用得对不对"，把"把字符串当数字算"这类错误扼杀在编码阶段。本项目 mypy 开 strict（最严）模式。
- **单元测试 / 集成测试**：单测 = 拿最小零件（一个函数）测；集成测试 = 把零件组装起来测（连真数据库、发真 HTTP 请求）。本项目后端测试用真实 PostgreSQL，测完事务回滚不留痕。
- **mock（替身）**：测试时用"假的"替换真的外部依赖——不真调大模型、不真发飞书消息，测试又快又稳又免费。
- **fixture（测试夹具）**：测试前的"道具准备"函数，比如先造好一个测试用户、一个可回滚的数据库会话。
- **断言（assert）**：测试里的"我认为应该是这样"检查句，不满足就判测试失败。
- **回归 / 回归测试**：修好一个 bug 后再跑一遍测试，确认它没有"死而复生"、修复动作也没弄坏别处。
- **重构（refactor）**：不改功能、只优化代码内部结构。
  比喻：家具不换，重新布局房间，住起来更顺手。
- **日志（log）**：程序运行时的"行车记录仪"，出了问题靠它还原现场。

#### 架构思维

- **缓存（cache）**：把昂贵的计算/查询结果存起来，下次直接用。
  比喻：常用电话号码贴在工位上，不用每次翻通讯录。
  Redis、React Query 都是这个思想。
- **并发 vs 并行**：并发 = 一个人交替照看两锅菜（轮流处理）；并行 = 两个人各看一锅（真正同时）。单核也能并发，并行需要多核/多进程。
- **限流 / 闸门（gate）**：控制单位时间内的请求/任务量，防止把下游打挂。本项目 AI 检索有全局并发闸门，直读域有环境变量开关。
- **功能开关（feature flag）**：用配置决定功能"开不开"，出问题不用回滚代码、改配置即可。本项目的 `SAFETY_<域>_DIRECT_ENABLED` 直读开关就是标准实现。
- **解耦（decoupling）**：让两块代码少知道对方的存在，改动互不牵连。手段：public_api 接口、事件总线、Protocol。
- **单一事实源（source of truth）**：一个数据只认一个权威出处，其他都是副本。本项目：Bitable 是仓储台账的 source of truth，本地库存表只是镜像。

## 10. 上手路径建议与常见任务速查

### 10.1 建议学习路线（由浅入深）

**第 1 步：跑起来（半天）**
- 按第 7.1 节把前后端本地跑起来，登录进去点一遍各模块页面。
- 打开 `http://localhost:8000/docs` 看 Swagger 接口文档，对照 `app/api/router.py` 理解路由组织。

**第 2 步：走一遍请求链路（1 天）**
- 挑一个简单接口（如 `GET /api/v1/system/modules`），从 router → service → repository → models 完整读一遍。
- 读 `app/main.py` 的 lifespan，对照 3.3 节理解启动流程。

**第 3 步：深入你负责的两个模块（2~3 天）**
- safety：先读 `ai_urs_review/`（AI 插件模式的标准样板）+ `service/bitable_direct/`（直读底座），再按需深入。
- warehouse：先读《仓储V3.0设计方案》+ `models.py` 实体关系，再读 `agent/pipeline/` 入库流水线。

**第 4 步：读规范文档（穿插进行）**
- `frontend/CLAUDE.md`（前端架构规范）、`frontend/DESIGN.md`（视觉规范）。
- `docs/` 下的设计方案文档（仓储 V2.0/V3.0、安全模块直读改造等）。

### 10.2 常见任务速查

**给某模块加一个查询接口**
1. `models/`（如需新表，同时 alembic 生成迁移）→ 2. `schemas/` 定义响应模型 → 3. `repository/` 写查询 → 4. `service/` 写业务 → 5. `api/` 加路由（挂权限依赖）→ 6. 前端 `lib/api/` 加 fetch 函数 + `pnpm generate:api` 更新类型。

**加一个定时任务**
1. 写一个零参 async 函数 → 2. 在模块里定义 `TaskDefinition`（CRON/INTERVAL/FIXED_TIME 三选一）→ 3. 在 `main.py` lifespan 里注册到 `SchedulerRegistry` → 4. 本地跑起来看日志确认触发。

**加一个飞书卡片交互**
1. 读 `safety/feishu/` 下现成的卡片 handler 找样板 → 2. 用 `@on_event("card.action.trigger")` 注册回调（记得"纯 ACK + PATCH 原卡"模式）→ 3. 写操作必须过确认门/审计。

**加一个 AI 功能**
1. 建一个 `ai_xxx/` 子包，按"schemas + prompts + rules + plugin + orchestrator"五件套组织 → 2. 在 `ai_config/` 登记场景与模型 → 3. 一律注入 `AuditedAIService` → 4. 单测用替身 ai_service，不真调大模型。

**排查"线上没反应"**
1. Grafana（:3200）按 request_id 或模块搜日志 → 2. 检查启动日志的 lifespan 各步 → 3. 飞书问题看长连接是否在线、handler 是否抛错 → 4. 直读域检查 gates 环境变量开关。
