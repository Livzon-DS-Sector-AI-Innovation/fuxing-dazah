# 安全模块「直读数据看板」— 查询链路全面直读方案

> 日期：2026-10-13
> 状态：设计方案（批次范围待拍板后开工）
> 决策依据（用户 2026-10-13 拍板）：**放弃 1.0 镜像查询链路**——镜像同步不准确、经常丢数据、无意义；页面/看板要直读多维表格。
> 上游口径：`DESIGN-安全模块Web退役与新面板-实施方案-20261012.md`（3.0：页面=纯只读监控视图，直读 Bitable，零操作按钮）。本文把该口径落到**查询链路**：让"页面直读"从口号变成代码事实。

## 0. 一句话结论

安全模块的直读查询底座已经建成大半：25 条 `bitable_connections` 全部在库，9 个域有现成直读查询实现（5 个已接线 API 只差开关），真正要**新写**的只有 4 处查询路径和 5 个总览采集器，其余是开关翻转 + 逐页验收。完成后页面与总览看板 100% 直读多维表格，任何新环境（零镜像数据）打开即有全量真实数据。

## 1. 背景与动机

1. **镜像丢数据不可信**（用户原话）：事件镜像依赖 WS 事件到达，事件丢失无兜底；定时对账任务在直读改造中已陆续下线，镜像既不完整也无对账。
2. **新环境页面全空**：2026-10-12 本机重建开发库（未导入旧库 dump），13 张镜像表 0 行 → 持证/职业健康/应急演练/MSDS/隐患台账/特殊作业台账/消防报警等页面全空。生产库靠几个月存量镜像撑着，掩盖了"查询链路依赖镜像"的结构问题。
3. **3.0 已定页面只读化**：操作在表格与机器人，页面只剩监控展示——查询经过镜像中转已无任何理由。
4. 直读的现实收益：本地零数据环境立即可用全量真实数据；不存在"同步延迟/丢事件"；数据口径与业务表格单一来源。

## 2. 现状盘点（2026-10-13 逐文件核实）

### 2.1 直读底座（已建成，全模块共用）

`service/bitable_direct/`：`reader.py`（`fetch_all_records` 分页全量 / `fetch_window_records` 时间窗 / `open_reader(domain,kind)` 配置中心解析连接）、`filters.py`（下推过滤能力矩阵，日期仅天粒度无区间算子）、`gates.py`（开关读取 env > DB，30s TTL）、`fields/errors/writer/locks`。

标准域直读八件套（key_risk_op 为完整参考实现，提交 a9a8f98a）：
`{domain}_direct/{reader,query,cache,views}.py` — reader 全量拉取 → `map_bitable_fields` 映射 → views（与 ORM 对齐的 view dataclass）→ query（内存等值/日期窗/keyword/分页/统计）→ cache（进程内 `CachedReader` 单例，`monotonic` 时间戳，默认 60s，0=关）；service 层双切（`direct_enabled()` → query，else repo SQL）；API 层 meta 标 `mode=direct|mirror + elapsed_ms`。

## 3. 目标架构

### 3.1 查询链路单一口径

```
页面/看板/导出 → API → service 双切(direct 默认开) → {domain}_direct.query
                     → CachedReader(TTL) → bitable_direct.reader → 飞书多维表格
后台推送链路(日报/轮询/回写) → 不动，继续用自己的工作数据（镜像或直读各自的现状）
```

- 页面响应 schema 不变（views 与 ORM 字段对齐是既有约定，前端零改动或极小改动）。
- 镜像表**不删不迁**：降级为后台链路内部状态；页面/看板/导出不再读。

### 3.2 缓存与配额策略（沿用既有实现，不新造）

- 小表（≤5k 行）：`fetch_all_records` 全量 + 60s TTL（hazard/special_op/cert/chemical/oh/contractor/emergency_drill/msds）。
- 时序大表（fire_alarm/central_alarm 万级）：`fetch_window_records` 按日窗；页面日期筛选默认近 30 天，翻页在窗口内内存分页。
- TTL 可配 `SAFETY_<DOMAIN>_DIRECT_CACHE_TTL_SECONDS`（0=关）；导出/对账用 `strict=True` 绕缓存。
- API meta 带 `mode + elapsed_ms + rows`，配额问题可观测。

### 3.3 失败语义（看板红线）

- Bitable 请求失败：列表/统计接口返回显式错误码与 message（不静默给空列表——空列表会被当成"数据为零"）；前端列表页加 ErrorState，看板沿用二期单域降级（域卡显示"数据源异常"，其余域正常）。
- 开关语义不变：direct 开关回滚即回镜像路径（灰度安全网保留，直到收官批次再讨论移除）。

### 3.4 隐患趋势序列的实现口径

`collect_hazards` 的 30 天新增/闭环序列：bitable 日期只有天粒度等值算子、无区间下推 → 全量拉取后**内存分桶**（HazardView 已含创建/闭环时间字段）。隐患表行数为数百级，可承受；若后续增长，再切 `fetch_window_records`（报告时间字段倒序窗口）。

## 4. 分批实施计划

> 每批独立可验收、可单独回滚（开关翻回）；批内先翻 A 类开关（零代码收益）再做新写路径。

### 批次 1｜看板核心：隐患 + 特殊作业 + 总览（新写量最大，收益最大）

1. `api/hazards.py` + `service/hazard.py` 双切：list/stats 过滤条件下推或内存过滤走 `hazard_direct.bitable_repo`（`query_hazards` 已支持 department/status/rectification_status/keyword/日期；stats 用 `count_hazards`）；详情/导出走全量 view。
2. special_op 台账直读：`special_op_direct` 补 `query.py`（审批中+已审批状态过滤、类型/等级/部门/日期/keyword 内存查询，排序对齐 `sort_like_mirror` 口径）+ ledger/ledger_stats API 接线。
3. overview 采集器直读化：`collect_hazards`（count_hazards + 内存 30 天分桶）、`collect_special_ops`（直读 stats）、`collect_chemicals`（`chemical_inventory_direct` CachedReader）。
4. 翻开关：`SAFETY_KEY_RISK_OP_DIRECT_ENABLED=true`（页面+总览立受益）。
- DoD：本地零镜像数据前提下，hazard-ledger / special-ops / overview 三页全量有数；开关开/关双路径同查询数值 diff=0；pytest/ruff/mypy 零新增。

### 批次 2｜报警 + 持证

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| Bitable API 配额/限流 | 全域 TTL 缓存；大表只走日窗；meta 可观测（elapsed_ms/rows）；页面默认时间窗 |
| 全量拉取延迟（首访冷态） | 小表数百~数千行实测秒级；central_alarm 总览已直读（热态 ~1.4s 全 9 域）验证过可行性 |
| 隐患趋势全量分桶随表增长变慢 | 行数百级可承受；增长后切窗口查询（报告时间字段） |
| 字段映射漂移（表格加列/改名） | `bitable_field_mappings` 已有治理；strict 解析报错显式暴露，不静默缺列 |
| 双路径数值不一致 | 每批验收含开/关同查询 diff=0 比对脚本 |
| 导出大数据量 | strict 直读绕缓存一次拉全量，复用既有导出模板与文件名修复 |

## 7. 明确不做

- 不删镜像表、不做数据迁移（平台表冻结口径延续）。
- 不动后台推送链路（日报/督办轮询/AI 分析回写/WS 事件镜像各自现状）。
- 页面零业务操作按钮（3.0 已定，本方案不重开）。
- knowledge 知识库页继续走 ragplus 检索链路，不进本方案。
- 不新建前端框架/页面——总览驾驶舱与各台账页已存在，本方案换的是**数据来源**。
